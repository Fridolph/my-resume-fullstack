## 为什么改

Owner 观察：`DELETE /resume/:id` 原本写 `deletedAt`（软删除）。**用户**用软删是对的（账号要能追溯、要能恢复），
但**简历**不该如此 —— 简历正文是用户自己生成的内容，软删只会让库里持续积累看不见的简历与草稿，形成污染。
用户点删除就是不要了，直接删。

两条口径的差别值得记住：**"要不要留痕"取决于这条数据是不是"系统的事实"** ——
账号是（审计、恢复、责任边界）；简历内容不是（用户自己的产物，删了就删了）。

## 范围

- `Resume` 去掉 `deletedAt` 字段与 `@@index([workspaceUserId, deletedAt])`（索引收窄为 `[workspaceUserId]`）
- `resume_drafts.resumeId` 外键改 `onDelete: Cascade`：草稿属于简历，简历没了草稿没有存在意义；
  也避免硬删被 `Restrict` 直接拦住
- 迁移里**清理历史软删数据**：`deleted_at IS NOT NULL` 的简历连草稿一并物理删除
- `ResumeService`：`ownedResume` / `list` 去掉 `deletedAt: null`；`remove` 改为真正的 `delete`
- 文案：删除确认与提示不再说"数据保留、可追溯"，改为如实的"删除后无法恢复"
- 同步测试：`resume.service.test.cjs` 里的软删断言

## 非目标

- **`users` 的软删不动**（账号可追溯、可恢复）
- `resume_workspaces`（用户级容器）不动：删简历只影响该简历与其草稿
- 不做"删除回收站 / 恢复入口"（硬删后本就不该有）

## 影响与回滚（已向 Owner 说明并获确认）

- **迁移不可逆**：回滚只能把列加回来，被清理的数据无法恢复；因此清理语句只作用于 `deleted_at IS NOT NULL`（即已被用户删过的）
- 外键由 `Restrict` 改 `Cascade` 后，任何"删简历"路径都会连带删草稿 —— 这是想要的行为，但也意味着**删简历的破坏面变大**，所以列表删除的二次确认（含 3 秒倒计时）保持不变
- 应用环境：Owner 确认在本机本地库直接应用（已有明确授权）

## 发现（旁支，不阻塞本卡，需要 Owner 决定是否单独开 Issue）

**历史迁移在空库上不可重放**：`20261013120000_internal_int_ids` 里有

```sql
SELECT setval('roles_id_seq', (SELECT COALESCE(MAX("id"), 0) FROM "roles"));
```

空表时 `MAX(id)` 为 NULL → `COALESCE` 给 0 → `setval(seq, 0)` 报
`22003: value 0 is out of bounds for sequence "roles_id_seq" (1..9223372036854775807)`。

影响：

- `prisma migrate dev` 需要 shadow database 重放**全部**迁移 → 在新环境上直接失败（本卡因此改用**手工迁移 + `migrate deploy`**）
- 全新环境用 `migrate deploy` 从头重放时同样会失败

**不能直接改这个文件**（已应用的迁移会被 checksum 校验），要用后续迁移修正或走 Prisma 的 resolve 流程。建议单独开 Issue。
