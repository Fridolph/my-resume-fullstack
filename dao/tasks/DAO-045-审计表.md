## 目标与边界

- 目标：把**少量关键动作**持久化到独立审计表，建立责任边界。
- 覆盖动作：创建简历 · 发布 / 取消发布（当前是「设为默认展示」）· 删除简历 · 权限变更。
- 非目标：软删除 / 回收站 / 内容快照（那是**恢复能力**，与审计是两件事）· 数据库备份验证 · 读操作留痕。

## 现状（已核实）

`apps/server/prisma/schema.prisma` 的注释明确写了本仓的设计取舍：

> **删除是物理删除**（没有 `deletedAt`）：简历正文是用户自己生成的内容，删掉就是不要了 ——
> 需要留痕的是**账号**（`User` 仍有 `deletedAt`：审计、恢复、责任边界），不是简历。

后果：**简历删除后，"谁删的、什么时候删的"在库里没有任何痕迹**。
`User` 有 `deletedAt`（账号留痕），但**简历维度的关键动作完全没有记录**。

## 三个必须处理的风险

### ① 审计行不得对 `Resume` 挂级联外键

简历是硬删除；`onDelete: Cascade` 会让"删除动作把删除记录一起删掉" —— 审计等于没有。
必须**保存独立的资源标识与元数据**，不依赖资源外键存活。

> 同时明确边界：**审计 ≠ 数据备份**。它能帮追责，**不能**恢复简历内容。

### ② 业务写入与审计写入必须同事务

```
发布成功 → 审计也成功；审计写入失败 → 发布一起回滚
```

是否对所有动作都采用强一致，按动作重要性决定（**设计阶段明确**，不要默认全强一致）。

### ③ 草稿自动保存频繁，不能每次复制全文

先记**版本元数据**（如 `revision`），不每次写全量内容。审计里**不得出现 PII**。

## Owner 已拍板的产品决定（2026-10-16）

| 问题 | 决定 | 对设计的影响 |
| --- | --- | --- |
| 保留多久 | **一直保留在历史中** | 审计表**只增不删**；不设 TTL、不做定期清理。这也把「删号时怎么处理」逼成一个必须正面回答的问题 |
| 谁可以查看 | **仅超管**（`super_admin`） | 需要权限键（如 `Audit.Log:view`），**不能**沿用简历域的 `Resume.*`；接口要独立授权 |
| 用户删号 | **要有记录** | 账号删除本身是一个**审计动作**；且审计行**不得因账号删除而消失**（同样不能对 `User` 挂级联外键）。`actorId` 需能在账号消失后仍指向"曾经是谁" |
| 强一致范围 | **暂不确定**，参考业内最佳实践，边做边完善 | 采用**分层策略**：破坏性/不可逆动作（删除、权限变更）走同事务强一致；可重放或高频动作（草稿保存）走最终一致或只记元数据。**在设计里显式标注每个动作属于哪一档**，而不是全强一致 |

### 由"一直保留 + 删号要有记录"推出的两条硬约束

1. **不能对 `User` 或 `Resume` 挂级联外键** —— 否则"删号/删简历"会连带删掉审计行，
   与"一直保留"直接冲突。审计行保存的是**独立的标识与元数据快照**（如操作时的昵称/邮箱快照），
   而不是靠外键去 join 一个可能已经不存在的行。
2. **"一直保留"与"用户删号时如何处理个人信息"存在张力** —— 需要明确：
   审计里保留的是**责任信息**（谁、何时、对什么动作），而**不是**简历内容或多余 PII。
   这正好与"审计不写 PII"的要求一致，两者互相支持而非矛盾。

## 验收标准（设计确认后补齐）

1. 创建 / 发布 / 删除三个动作各产生一条审计记录，含 `actorId` / `action` / `resourceId` / `requestId`
2. **删除简历后，该删除动作的审计记录仍然存在**
3. 强一致动作：审计写入失败时业务一并回滚
4. 审计记录中**搜不到**简历全文或 PII
5. `onDelete` 语义经审查确认无级联删除审计行的风险
