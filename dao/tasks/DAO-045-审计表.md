## 目标与边界

- 目标：把**少量关键动作**持久化到独立审计表，建立责任边界。
- 覆盖动作：创建简历 · 发布 / 取消发布（当前是「设为默认展示」）· 删除简历 · 权限变更。
- 非目标：软删除 / 回收站 / 内容快照（那是**恢复能力**，与审计是两件事）· 数据库备份验证 · 读操作留痕。

## 现状（已核实）

`apps/server/prisma/schema.prisma` 的注释明确写了本仓的设计取舍：

> **删除是物理删除**（没有 `deletedAt`）：简历正文是用户自己生成的内容，删掉就是不要了 ——
> 需要留痕的是**账号**（`User` 仍有 `deletedAt`：审计、恢复、责任边界），不是简历。

后果：**简历删除后，"谁删的、什么时候删的"在库里没有任何痕迹**。
`User` 有 `deletedAt`（账号留痕），但**简历维度的关键动作完全没有记录**。

## 三个必须处理的风险

### ① 审计行不得对 `Resume` 挂级联外键

简历是硬删除；`onDelete: Cascade` 会让"删除动作把删除记录一起删掉" —— 审计等于没有。
必须**保存独立的资源标识与元数据**，不依赖资源外键存活。

> 同时明确边界：**审计 ≠ 数据备份**。它能帮追责，**不能**恢复简历内容。

### ② 业务写入与审计写入必须同事务

```
发布成功 → 审计也成功；审计写入失败 → 发布一起回滚
```

是否对所有动作都采用强一致，按动作重要性决定（**设计阶段明确**，不要默认全强一致）。

### ③ 草稿自动保存频繁，不能每次复制全文

先记**版本元数据**（如 `revision`），不每次写全量内容。审计里**不得出现 PII**。

## 需要 Owner 拍板的产品决定（开工前置）

1. **保留多久**？永久 / N 个月 / 按动作分级？
2. **谁可以查看**？仅超管 / 管理员可见列表 / 需要独立权限键？
3. **用户删号时审计怎么处理**？保留（`actorId` 置空但记录在）/ 一并删除 / 匿名化？
4. 哪些动作**必须强一致**（同事务），哪些可以最终一致？

> 这四个问题不答清就落 schema，等于替产品做决定 —— 本卡在此停下等答复。

## 验收标准（设计确认后补齐）

1. 创建 / 发布 / 删除三个动作各产生一条审计记录，含 `actorId` / `action` / `resourceId` / `requestId`
2. **删除简历后，该删除动作的审计记录仍然存在**
3. 强一致动作：审计写入失败时业务一并回滚
4. 审计记录中**搜不到**简历全文或 PII
5. `onDelete` 语义经审查确认无级联删除审计行的风险

## 测试计划（按风险）

| 风险 | 验证 |
