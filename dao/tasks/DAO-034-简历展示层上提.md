## 目标与边界

- 目标：把简历的**展示能力**从 web 的 layer 提到共享层，使 admin 的 `/resume/:id` 详情预览能与公开站**用同一套组件**。
- 范围（两批）：
  - **批 1（已完成）**：展示域类型 + 文档⇄内容映射 + 区块定义与键名桥接 → `packages/common`
  - **批 2（待做）**：纯展示组件（hero 三档 + parts、各 section 三档、能力图表、背景层、区块外壳）+ 其所需 composables + 样式 → `packages/ui`
- 非目标：
  - **不上提编辑态**：`ResumePageContainer`（含 `sortablejs` 拖拽）、`ResumeColumn`、`ResumeSectionTray`、
    `settings/**`、`draft/**`、能力编辑三件套、`useResumeContent`/`useResumeReorder`/`useResumeDraft`
  - 不上提 mock（`mock/**`）与 `apis/resume-draft.ts`
  - admin 详情页本身属下一个任务（本卡只到"能引用"）
- 关键约束：`packages/ui` 是**零第三方运行时依赖**的共享层 —— 这也是"编辑容器留在 web"的直接原因。

## 批 2 的设计要点（动手前先记下来，避免又变成"顺手动容器"）

1. **容器要拆**：`ResumePageContainer` 把两件事揉在一起 ——
   *按 `display` 算三栏排布*（详情页也要）与 *拖拽/隐藏/排序交互*（依赖 sortablejs，只有编辑态要）。
   建议把**排布计算抽成纯函数**（`common`），web 的容器与 admin 的只读容器都用它；交互留在 web。
2. **`useResumeDisplay` 不能整体上提**：它掺了 mock 默认值、localStorage 持久化与防抖自动保存 ——
   那是"配置的读写管理"（编辑态）。只读渲染只需要"给定 display 配置 → 算出可见区块与排布"。
3. **样式归属**：`layers/11-public-resume/app/assets/css/resume.css`（294 行，`.resume-*` 类与 CSS 变量）
   由 layer 的 `nuxt.config.ts` 引入。上提后宿主（web / admin）都要引入 —— 放 `packages/ui` 自己的
   `nuxt.config.ts` 里，两端自动生效；届时 web 那份要去掉，避免双份。
4. **组件自动导入**：展示组件两端的名字要一致；web 删除原组件后，自动导入会解析到 `packages/ui` 的同名组件，
   `resumeSectionComponents` 注册表随之搬到 ui（它引用展示组件）。

## 已知限制（详情页，如实记录）

1. **未按文档注入主题 CSS 变量**：详情页目前用 `resume.css` 的默认值，与文档里配置的配色可能不一致
   （公开站是由页面把主题变量注入 `<body>`，那套逻辑还在 web 的页面里）。
2. **`display.sections.overrides` 未搬运**：契约里能力模块可以指定展示视图（文字 / 条状 / 雷达），
   而 `ResumeDisplayConfig` 没有对应字段 —— 详情页的能力模块用默认视图。
   两条都需要在共享层补字段/逻辑，属后续工作。
