## Grill：开工前对齐

- 目标：把 `AUDIT_ACTIONS` 里剩下的三个账号域动作接线，并清空覆盖率测试的 `PENDING` 清单。
- 边界：只动 `apps/server`（audit / user / common 装饰器）与 `packages/common` 白名单，加一个角色变更接口。
- 不做：admin 端角色变更 UI；`changePassword` / `forceLogout` 的审计（属会话域）；批量授权（尚无入口）。
- 涉及文件 / 模块：`audit/audit.service.ts`、`user/{user.service,user.controller,user.module,dto/user.schema}.ts`、`common/error-codes.ts`、`audit/__tests__/*`、`docs/server/{07,openapi.json}`。
- 风险与未知：**`role.change` 在当时没有对应的业务入口** —— 审计无处可接。
- 验收：三条动作各产生一条审计且与业务同事务；审计内无被操作者 PII；`PENDING` 清空；`pnpm check` 全绿。
- 第一刀：先定 `role.change` 的资源归属与 metadata 粒度，再决定要不要为它补业务接口。
- 过门判断：`可开工`

## 设计与决策

| 决策 | 理由 / 证据 | 确认者 | 日期 |
| ---- | ----------- | ------ | ---- |
| 资源 = **被操作的用户**（方案 A），三个动作一致 | 审计主体是"人"不是"配置"；`(resourceType, resourceId, occurredAt)` 直接回答"用户 X 的权限被谁在何时改过" | Owner | 2026-10-16 |
| `role.change` 的 metadata 记**角色键集合**的 `before`/`after` 全集 | 角色键稳定；权限随 `ROLE_PERMISSION_PRESETS` 漂移，写进审计会记录"当时的定义"而非当时的实际能力 | Owner | 2026-10-16 |
| 批量变更 = **每条受影响用户一条** | 查询入口是"某个用户的历史"，聚合记录会让单个人查不到 | Owner（按建议倾向） | 2026-10-16 |
| 快照存 `{ nickname }`，**不 join** | `User` 现在只是软删；审计要活得更久，须自包含。且不冗余采集 PII | Owner（按建议倾向） | 2026-10-16 |
| **为 `role.change` 补业务接口** `PATCH /api/user/:id/roles` | 接口不存在则审计无入口；补齐后"改角色"才是可追责的真实动作 | AI（在已确认边界内） | 2026-10-16 |
| 请求体传**完整集合**而非增量 | 幂等；服务端不必从 diff 反推增减 | AI | 2026-10-16 |
| 授权复用 `Settings.Users:edit`，不新开权限键 | "能编辑用户"本就包含"能改角色"；另开键会让两者定义开始漂移 | AI | 2026-10-16 |
| `roleKeys` 仅允许 `admin`/`user`，禁改超管与自己 | 与 `createUserSchema` 同口径；超管身份不可经接口授予或复制 | AI | 2026-10-16 |
| 事务内**先** `SELECT … FOR UPDATE` 锁用户行，再读角色 | READ COMMITTED 下"删+建"会交错成两意图的**并集**（权限只多不少）。兑现了 `docs/server/07` §5 早先留下的"改角色需共同设计事务/锁" | AI | 2026-10-16 |
| 集合无变化时不写审计 | 审计记变更；`before === after` 只会稀释审计 | AI | 2026-10-16 |
