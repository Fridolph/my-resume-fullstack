# Dao 任务运行面

`dao/` 是本模板的最小项目级 Harness。它不是第二套项目管理系统，也不替代 GitHub Issue、PR、测试平台或聊天记录。

它只做一件事：为当前关键事件保留一个人和 AI 都可读取的事实源，使任务在开工、开发、交接、验证与收口之间不断棒。

## 最小结构

```text
dao/
├── CURRENT.md                 # 当前关键任务的唯一指针
├── tasks/                     # 一项关键事件一张任务卡
│   ├── TEMPLATE.md
│   └── DAO-001-*.md
└── experiments/               # Harness 假设、开放问题与验证记录
```

当前阶段不创建数据库、CLI、自动化 daemon 或额外 Web 页面。Markdown + Git 已足以验证“同一任务事实源”是否真的减少协作黑盒。

## 标准闭环

新 AI 伙伴或新项目先从 `dao-intro` 进入；已有传承包的项目按回锚模式读取 `.dao/`，再根据任务情况进入 `dao-grill`。任务运行面按以下闭环推进：

```text
dao-intro
-> dao-grill（按需）
-> planned -> designed -> in-progress
-> self-tested -> review-ready -> done
                         \-> blocked
-> dao-review（收口判断）
-> dao-commit（仅集成边界）
-> dao-return-dao（按需归母）
```

这是一套人工可执行的 v0 协议：状态、确认门、交接与验证必须可回读；工具、PR、提交和聊天记录是承载器，不替代任务卡事实源。`dao-intro` 负责认根、认人、认位，不负责替代任务过门。

## 单一事实源规则

- 每个关键事件只对应一张 `dao/tasks/DAO-*.md` 任务卡。
- `CURRENT.md` 只指向当前任务卡，不重复目标、状态或证据；任务卡才是唯一事实源。
- Issue、PR、提交和聊天记录可以关联到任务卡，但不与任务卡竞争状态主位。
- 同一时刻只有一个“当前关键任务”。若确实需要并行，先拆为独立任务卡，并由 Owner 明确切换 `CURRENT.md`。

这里的“关键”不是所有小改动。明确的小修仍可直接按项目工程规范处理；只有存在协作切换、风险、跨文件影响或值得回看的阶段变化时，才需要建卡。

## 什么可以写入任务卡

只记录会影响下一步判断的事实：

- 目标、范围、非目标和验收条件。
- 已确认的状态迁移和阻塞。
- 改变实现方向的决策与理由。
- 可复查的验证摘要及其命令、链接或样本位置。
- 下一位接手必须知道的第一刀。
- 值得形成语义锚点或归母候选的结论。

不要把逐步思考、完整终端输出、所有聊天内容、重复进度播报写进卡片。原始日志留在 CI、终端、Issue 或外部系统；任务卡只保留可定位的摘要和引用。

## 谁可以判断、谁需要确认

Agent 可以：

- 基于 `dao-grill` 起草任务卡。
- 写入可复查的机器验证摘要。
- 生成交接草案、状态迁移建议和集成 Dao Commit 候选。

人应确认：

- 任务目标、非目标和优先级。
- 范围扩大、风险接受、外部发布或不可逆动作。
- `done` 状态、Dao Commit 最终锚点、以及经验是否归母。

这不是要求人审核每一行。Human in the loop 放在会改变承诺、责任或不可逆历史的门上；其他客观事实可由 Agent 先记录并标明来源。

## 确认门后的续跑

确认不是让任务重新开始的信号，而是当前任务的一条可记录输入。任务仍由 `CURRENT.md` 指向同一张卡，状态仍保持真实位置；不要为“等待 Owner”另造状态或把它误写成 `blocked`。

只有当 Owner 的决定会影响范围、风险、承诺或收口时，才在任务卡填写“确认门与续跑”。最小内容是：

1. 需要 Owner 确认什么，以及可接受回答；
2. 确认后应处于哪个真实状态；
3. 确认后 Agent 必须执行的第一刀；
4. 收到确认后写回的事实。

续跑顺序固定为：Owner 最小确认 -> Agent 回读 `CURRENT.md` 与任务卡 -> 写回确认事实与状态迁移 -> 执行已声明的第一刀 -> 继续原任务的验证和收口。

如果确认改变了原目标、非目标或验收，先在“Grill”与“设计与决策”中写清改变，再继续；不能把“确认”理解为对未说明扩展范围的默认批准。

## 与 Skills 的接法

| 节点            | Skill            | 对任务卡的影响                                                        |
| --------------- | ---------------- | --------------------------------------------------------------------- |
| 初次传承 / 回锚 | `dao-intro`      | 生成或校准项目级 `.dao/` 传承包；确认前只预览，不写入                 |
| 开工对齐        | `dao-grill`      | 起草“目标到下一步”与过门判断                                          |
| 中断续跑        | `dao-handoff`    | 更新“交接”区，写清下一位第一刀                                        |
| 收口判断        | `dao-review`     | 更新“验证 / 收口判断”区                                               |
| 集成锚点        | `dao-commit`     | 仅在 `feature -> dev` 或 `dev -> main` 合并 / squash 时关联净变化锚点 |
| 经验归位        | `dao-return-dao` | 更新“沉淀候选”区，不直接改母仓                                        |

日常任务卡不产生 Dao Commit 候选；只有任务所在的集成单元准备合并时，才补集成锚点。当前先由人或 Agent 手工回写任务卡，以验证字段是否足够。只有同一写回动作在多个项目反复出现且证明有价值时，才考虑做 CLI 或自动化。

## 任务状态

状态仍遵守项目 `AGENTS.md`：

```text
planned -> designed -> in-progress -> self-tested -> review-ready -> done
                         \-> blocked
```

状态是对“任务是否能进入下一门”的判断，不是工时百分比。每次迁移都需要在任务卡留下最少一条依据。
