## 2. 当前方案

`ResumeWorkspace → Resume → ResumeDraft` 分别承载本人工作区、简历身份及当前文档。正文与展示使用有版本的 JSONB 文档，数据库关系与唯一约束保证草稿归属；前端使用共享契约，不能直接消费 Prisma 类型。

F02-S03 当前实现流程：

```text
输入：路径 id、{ expectedRevision, document }、认证身份
1. schema 校验输入；Service 在事务前检查编辑资格
2. 开事务，按 id + 本人工作区 + 账号有效性查简历；查不到 → 404
3. 读当前草稿并解析；保留服务端最新 PDF 配置，清除已删除模块的纸面引用
4. updateMany 条件：resumeId + 所有权 + expectedRevision + 完整旧 document 相等
5. 更新 document/schemaVersion/updatedBy，并使 revision + 1
6. 受影响行数不是 1 → 抛 409，停止后续写入并回滚
7. 更新简历时间，读取响应，提交事务并返回新 revision
```

完整旧 JSON 的 CAS 用于保护正文、网页展示、PDF 等共享文档的读改写；revision 仍表达正文保存版本。不能只凭“展示不推进 revision”推导保存不会发生冲突。

F02-S05：先读审计所需的最小快照，再删除，最后使用同一事务客户端写审计。审计失败则业务回滚；不保留整份正文作为删除审计。

## 3. 存储与兼容

正文采用结构化 JSON 文档而不是每个内容字段建表；schemaVersion 负责结构解释，revision 负责正文保存并发，两者用途不同。新增文档字段需评估旧数据读取与客户端兼容，不必然新增迁移。

重命名目前最后写入生效，不冒用正文冲突保证；简历硬删除不能用应用代码回退恢复，应依赖明确的数据备份策略。
