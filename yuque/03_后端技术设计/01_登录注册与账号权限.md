## 1. 场景与职责

引用需求中的 F01 场景；展开认证授权、状态、持久化、事务与异常。具体 HTTP 字段以 API 文档和其链接的运行时 schema 为准。

## 2. 当前方案

- `AuthController → AuthService` 负责认证与签发；`JwtAuthGuard → JwtStrategy → restoreUser` 恢复身份。
- JWT 存 `sub/sessionVersion`，签名不是加密；角色权限从数据库恢复，代价是受保护请求有身份查询成本。
- `User/Role/Permission/UserRole/RolePermission` 表达身份关系；改密与强制下线推进 sessionVersion。用户软删除与简历硬删除是不同规则。
- 角色集合变更传完整集合；事务内先锁目标用户行，再读写角色并记录审计，避免并发删建导致集合混合。
- 登录限流当前是内存存储，不能写成 Redis 分布式限流。

F01-S02 的程序化流程：

```text
输入：Bearer token
Guard：若路由显式公开则放行；否则交 Strategy 验签、检查过期和载荷
Service：按 sub 查询未删除账号，比较 sessionVersion
失败：身份不可用或版本不同 → 401；数据库故障保留服务故障语义
成功：生成当前 userId、资料、roleKeys、permissionKeys，挂到请求上下文
Controller/Service：继续检查本用例权限及资源归属
```

## 3. 授权与现有差异

本人资料与管理资料共用更新 schema，但 Service 决定目标是否允许；用户查询当前仅登录门，属于待评审缺口。输入 DTO 留在 server，不把所有 DTO 都说成已迁 common。

登录 schema 当前实际要求 account 3～64 字符（trim），password 6～20 字符且不 trim；源文件中“4～64”注释已过时，以运行时规则为准。

## 4. 业务审计依赖

- pino 请求日志 + 幂等 ensureTraceId；日志初始化只在根模块一次完成，保持同一请求标识。
- AuditService 管记录/查询，动作字典与 metadata 白名单约束输入；Controller 负责审计查询授权。
- 强一致操作传同一事务客户端；先取必要快照再删除。审计不是数据库业务对象的完整副本。
- 日志故障、审计故障、访问统计故障的处理不同：按业务承诺决定是否阻止主操作，不能统一 fire-and-forget。

F07-S02 规定关键业务留痕；F07-S03 查阅需要 super_admin 与 Audit.Log:view。日志与全局异常仅在错误出口和运行风险中引用。
