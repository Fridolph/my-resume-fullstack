## 1. 场景与职责

引用需求中的 F06 场景；这里只展开页面、交互和请求设计，不重新定义业务规则。范围为当前 Nuxt 4 实现，Next.js 迁移另行设计。

## 2. 当前实现

- admin `/settings/user`，`apis/user.ts` 负责本人资料调用；头像消费通用上传接口。
- 页面有 saving、avatarUploading 状态；资料通过 useAsyncData 获取并在成功后 refresh。未显式接入加载/读取失败分支；refresh 只证明刷新本人资料 query，其他身份展示是否同步需验证。
- 普通保存每次组装 username、nickname、email、phone，并非只提交变更字段。空邮箱被转成 null，但后端 email 只支持不传或合法字符串；响应类型 MyProfile 的 nullable 被前端更新类型沿用，未能约束 PATCH 输入。
- 409 依赖 message 中的字段名定位错误，但服务端唯一冲突提示为通用文本，邮箱/手机冲突可能回退到用户名栏，不能宣称已准确回填。
- 头像选中即上传，随后独立 PATCH avatar、refresh；它与普通资料保存是两条流程。API 支持多文件，这里引导一次一个。
- 需补 Owner 桌面/移动实看，不能由 typecheck/build 代替。

## 3. 目标设计与恢复边界

普通资料：读取本人资料 → 编辑字段 → 按确认后的输入契约提交 → 成功刷新资料及需要同步的身份展示。未传保留；哪些字段允许清空由需求/API 共同确定，不能从响应 nullable 推断。是否改成只传变更字段，应作为后续设计选择，不能记成当前事实。

头像：选图 → 上传 → PATCH avatar → 刷新资料；上传失败不 PATCH，PATCH 失败不显示整体成功，并明确重试与残留文件边界。普通字段的未保存输入是否会被头像成功后的 refresh 覆盖，也需纳入验证。

当前资料页没有接入手机号严格校验 schema；不能将通用工具存在或服务端注释视为页面已调用。后续需对齐前端体验校验、服务端边界校验和字段错误契约，并补读取失败/保存失败的恢复方案。

## 4. 验证与影响范围

需求页的验收样本为共同基线；机器检查覆盖类型、构建及已有自动化测试，Owner 另验桌面/移动关键路径。历史执行证据见实现导读，本文不宣称已执行。仅样式变更先核对 UI/前端/测试；若改变请求、权限、结构或恢复语义，需同步 API 与后端评估。

优先样本：无邮箱账号只改昵称、合法邮箱更新与清空、邮箱/手机唯一冲突、头像上传成功但 PATCH 失败、普通资料未保存时更换头像。源码入口为资料页 save/onAvatarPicked、apis/user.ts 的 ProfileUpdateInput、后端 updateUserSchema 和唯一冲突 Filter。
