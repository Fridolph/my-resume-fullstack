## 3. 共享业务语言

| 术语 | 本项目当前含义 | 容易混淆的边界 |
| --- | --- | --- |
| 作者 | 拥有简历的登录用户 | 登录不自动获得编辑全部简历的权限 |
| 角色 / 权限 / 所有权 | 身份类别 / 被授权能力 / 资源归谁 | 前端隐藏按钮不能替代后端授权 |
| 草稿 | 当前可编辑文档 | 当前公开读也读取这份文档，没有独立发布快照 |
| 发布 | 作者允许简历被公开读取 | `publishedAt` 控制；不是发布一个应用版本 |
| 默认展示 | 从本人简历中选择一份默认展示 | `isDefault` 与发布分开；默认必须已发布 |
| 分享链接 | 独立 token、期限、权限与撤销记录 | 链接过期不使另一条公开 URL 自动失效 |
| revision | 正文保存的并发版本 | 不是 schemaVersion，也不是可恢复的历史版本 |
| schemaVersion | 文档结构的版本 | 不用于判断某次编辑是否冲突 |
| 公共打印预设 | 当前用户跨简历复用的纸面默认配置 | 不是所有用户共用的全站设置 |
| 审计 / 访问事件 | 关键业务操作留痕 / 访客行为统计 | 前者部分要求同事务，后者当前尽力记录 |

## 4. 仓库交付目录与语雀映射

当前交付根目录为本项目 `yuque/`；按六个业务模块写需求，前端与后端技术设计分别成页。业务审计并入账号权限的关联场景，公共组件不另开文档。完整导航见 [目录入口](README.md)。

```text
yuque/
├── README.md
├── 00_项目概览与交付流程.md
├── 01_需求文档/          六个业务大模块
├── 02_前端技术设计/      同模块，关注页面、交互、状态和请求
├── 03_后端技术设计/      同模块，关注授权、数据、事务和并发
├── 04_API接口文档/       40 路由目录，优先补登录、草稿、发布分享
└── 05_实现与验证/        源码入口、证据、待验项与学习题
```

部署与发布、完整机器契约和迭代复盘按真实演练逐步补，不预建空页或宣称完成。语雀页遵循此阅读结构，尚未执行线上上传。

本地 Markdown 是编辑源，语雀作为审阅后的发布副本；源码引用上传时可改为基线 commit 的 GitHub permalink。状态仍只由原任务卡承载，避免双份台账。

## 5. 用一次真实增量需求演练企业交付

以下是建议工作方式，具体审批、分支和发布约束以 [AGENTS](../AGENTS.md) 与 [开发流程](../docs/dev/01_开发流程_分支与提交.md) 为准。

| 阶段 | 各角色共同评审什么 | 最小交付物 | 进入下一步的条件 |
| --- | --- | --- | --- |
| 需求澄清 | 用户问题、业务样本、价值、非目标 | 场景编号、规则、失败出口、待决项 | Owner 确认产品意图 |
| 验收与用例评审 | 正反例、权限、并发、旧数据、移动端 | Given/When/Then 用例矩阵 | 每条规则有可观察的验收方式 |
| 前后端技术评审 | UI 状态、契约、授权、持久化、兼容与回退 | 分开的前后端设计、API、决定记录 | 无阻塞性未决项，设计足以开做 |
| 迭代计划 | 按风险与依赖切最小纵向闭环 | Issue、任务卡、短分支、测试计划 | 一轮一个用例；不虚构过去的 Sprint |
| 实现与自测 | 逐步兑现同一场景的承诺 | 契约、后端、前端、测试、证据 | 本仓按 §3.3 顺序推进；稳定契约可用于并行讨论和 Mock |
| 联调与提测 | 成功、失败、权限、冲突和用户恢复 | 联调记录、缺陷列表、review 包 | 机器验证完成，UI 交 Owner 实看 |
| 验收与 Review | 场景是否成立、风险是否可接受 | Dao Review、未验证边界、提交 | 不能用“有代码”替代验收 |
| 部署与上线 | 环境、迁移、依赖、回退、可观测性 | 发布清单、环境证据、正式版本 | `dev → main`、tag、release 由 Owner 执行 |
| 迭代复盘 | 哪些判断被事实推翻、哪些能力可复用 | 学习记录、缺陷改进、skill 候选 | 项目经验先留本仓；跨项目规则另作归母判断 |

`planned → designed → in-progress → self-tested → review-ready → done` 表达任务成熟度。需求变更先更新共享场景，再评估产品、UI、前端、后端、测试、运维各自“需修改 / 需知会 / 无影响及依据”。

### 5.1 测试计划与证据分开

每个用例保留：场景编号、输入/前置状态、预期、验证层、执行命令、环境、结果、提交、证据位置、未覆盖项。用例草稿不填“通过”；本轮引用的历史通过记录不写成今日执行。

- 契约/单元：校验、授权决策、状态分支、冲突后停止写入。
- 真库集成：迁移重放、约束、事务回滚、级联、实际并发。
- HTTP：全局 Guard/Pipe/Filter、状态码、响应包装与二进制。
- 浏览器：路由/SSR、缓存、错误恢复、桌面/移动端关键链路。
- Owner 意图验收：布局、可读性、操作手感、业务结果。

### 5.2 部署上线章节目前该写到哪里

已有 `compose.yaml`、质量命令、健康接口、环境校验、日志与 release-it；未发现受 Git 跟踪的 `.github/workflows`，本轮未取得生产部署验收记录。Redis 出现在项目定位中，但当前限流使用内存，源码明确尚未接 Redis storage。

部署文档初稿按以下顺序补，不直接运行部署命令：

1. 确认部署平台、域名/TLS、服务拓扑、制品与版本号、数据保护范围。
2. 记录 PostgreSQL 迁移、上传目录持久化与备份；区分空库安装和已有库升级。
3. 核对 API 地址、CORS、JWT、反代可信 IP；仅列变量名，值留环境管理。
4. 核对 Chromium 系统依赖与中文字体、PDF 并发/超时、日志采集和事件保留。
5. 在确认的测试环境演练登录、草稿冲突、公开读、分享撤销、上传、PDF 与审计。
6. 明确应用回滚与数据恢复不同；新增列通常先保留，删表不能作为默认回滚方案。
7. Owner 决定正式集成与发布，记录验收人、版本、时间和上线后观察结果。

## 6. 教学推进与面试取材

先完成 DAO-028 §18.6 的复述，再按 `F02 草稿保存 → F02 删除与 F07 审计 → F04 取消发布与分享撤销 → F05 PDF 一致性` 阅读。F01/F06 适合作为独立小闭环练习。

每次只选一个场景：你先说下一层应保证什么，再读真实文件，最后用一个失败例子验证。每轮记录“原理解、源码事实、纠正、验证、未决问题”；不要一次性把所有参考答案当成学习完成。

面试表达按“用户问题 → 不变式 → 方案与代价 → 关键实现 → 验证证据 → 尚未解决的边界”。可讨论 revision 条件更新、完整 JSON CAS、同事务审计、永久撤销、二进制响应与 PDF 摘要；不要宣称已完成 AI Agent、发布快照、生产高可用或全链路 CI/CD。

## 7. 本轮 skill 实验

个人环境中的 `fullstack-requirement-design` 本轮只补两项通用判断：已有项目重建文档时记录证据与时间；需求/前端/后端/API/实现/测试/发布文档分开承载但共享场景编号。项目源码与本目录不依赖 skill 的安装路径。

本次试用发现：仅有角色表不足以防止把早期设计、当前代码、关闭 Issue 和环境验证混为一谈。后续用一个真实需求检查 skill 是否能保持前后端独立视图、发现契约漂移、按风险切片并给出未验证边界，再决定进一步修改。
