## 1. 目标与非目标

**目标**：超管在 admin 里能查到"谁、在什么时候、对什么、做了什么"，并能**按行为**与**按用户**筛选、翻页。

**非目标**（本轮不做，避免范围发散）：

- 不做审计的**写**（写入口在业务事务里，页面只读）；
- 不做导出 CSV / 图表 / 时间线可视化；
- 不做"恢复到某条记录之前的状态"（审计只增不改，没有回滚语义）；
- 不改审计表结构（表已在 `20261016120000_audit_log` 落地）；
- **不顺手做用户管理界面**（那是独立任务，见 §6）。

## 2. 已确认的前提（Owner 2026-10-16）

1. **只有超管能正常进入并查看**；
2. `admin` 与 `user` 角色**能看到这个入口，但点进去报 403** —— 正好把 Nuxt 的 403 / 404 页面能力立起来；
3. 第一版**简一点**：一个 `UTable` + 分页 + 按用户 / 按行为查询。

## 3. 授权：三层各管一件事

沿用 `docs/dev/02` §3.4 的三层落点，**每层都不能省**：

| 层 | 位置 | 负责 | 失败表现 |
| --- | --- | --- | --- |
| UI | `admin-navigation.ts` | 入口显隐 | **刻意不隐藏**：对已登录用户都显示（见下） |
| 页面 | 路由 middleware | 挡"直接敲 URL" | `createError({ statusCode: 403 })` → 错误页 |
| 接口 | `GET /api/audit-logs` | 真正的授权 | 后端 403 → 页面也落 403 页 |

**为什么入口不隐藏**（这是 Owner 明确要的形态）：隐藏入口只防"误点"，不防"敲 URL"；
而显式给出 403 反而**更诚实**——让 `admin` 知道系统里存在审计这件事、且自己无权看。
代价是导航里出现一个"永远进不去"的项，可接受。

**页面守卫判断什么**：`roleKeys.includes('super_admin')` **且** `permissionKeys.includes('Audit.Log:view')`
——与后端 `assertAuditViewer` 同口径（角色 + 权限缺一不可），避免两端判定漂移。

> ⚠️ 依赖 B4（权限守卫 fail-closed）。**本任务的 403 必须是"真的挡"**：
> 如果 admin 的 `middleware/permission.ts` 还是"无权限数据时放行"，这一层就是假的。
> 所以 B4 与本任务**同轮做**，或先做 B4。

## 4. 403 / 404 页面能力（本任务的第二个产出）

两个应用**目前都没有 `app/error.vue`** —— 所有错误都落在 Nuxt 默认黑底页。本任务建 `apps/admin/app/error.vue`。

### 4.1 设计

单文件、按 `statusCode` 分支（Nuxt error page 的标准形态），**不按状态码建多个页面**：

| 状态码 | 标题 | 说明 | 主动作 | 次要动作 |
| --- | --- | --- | --- | --- |
| `403` | 无权访问 | 需要超级管理员权限才能查看审计记录 | 返回首页 | —（**刻意不给**，见 §4.2） |
| `401` | 需要先登录 | 当前身份无效 | 去登录 | — |
| `404` | 页面不存在 | 地址可能已变更 | 返回首页 | — |
| 其他 | 出了点问题 | 显示 `error.message`（可能是 500） | **重试**（`clearError({ redirect: 当前路径 })`） | 返回首页 |

### 4.2 两个刻意的取舍

- **全屏、不套后台布局**（所有状态码一致，参考 greensketch-basic 的 `error.vue` 形态）：
  错误页要表达的是"这一步走不通"，此时侧栏会让人以为"后台还活着、只是这块空了"。
  代价是 403 时没有侧栏入口 —— 但页面上有"返回首页"，回得去。
  （设计初稿曾打算 403 套侧栏、404 不套；实现时统一成不套，少一条分支、也少一类"布局里又出错"的风险。）
- **403 只告知、不给「切换账号」**（Owner 2026-10-16）：
  这一页回答的是"**这个功能存在，但你现在进不去**"，不是替用户做登录决策。
  所以只有一个「返回首页」，外加一句"该功能仅对超级管理员开放"。
- **文案按 `statusCode` 分类、按 `errorCode` 描述**：状态码决定动作（去登录 / 回首页 / 重试），
  `errorCode`（约定塞进 `statusMessage`）决定用哪句话 —— 顺序是
  **错误码文案 > 状态码文案 > 兜底**，两者都从共享层 `API_ERROR_CODE_MESSAGES` / `API_ERROR_MESSAGES` 取，
  不在这里另抄一份。

### 4.3 SSR 语义

错误必须在**服务端**就定状态码，不能先 200 再客户端跳转 —— 否则爬虫 / curl 看到的仍是 200：

```text
middleware（SSR 阶段执行）
  → 身份已由 plugins/auth.ts 从 cookie 恢复
  → 非超管：throw createError({ statusCode: 403, statusMessage: '仅超级管理员可查看审计', fatal: true })
  → Nuxt 渲染 error.vue，响应状态码 = 403
```

**已知坑（本仓踩过）**：`useAsyncData` 会吞掉 404/403（`admin/app/pages/release-notes.vue:100` 的注释已记）。
所以**守卫不能放在数据请求之后** —— 必须先判权限、再发请求。

## 5. 后端改动（本任务唯一需要改后端的地方）

现状：`GET /api/audit-logs` 支持 `page` / `pageSize` / `resourceType` / `resourceId` / `actorId` / `from` / `to`
—— **没有 `action`**。而"按行为查询"是本任务的明确需求。

### 5.1 契约变更（向后兼容：新参数可选）

```text
auditQuerySchema
  + action: z.enum(Object.values(AUDIT_ACTIONS)).optional()

AuditService.list(query)
  where: { ...(query.action ? { action: query.action } : {}) }

AuditQuery（audit.types.ts）
  + action?: AuditAction
```

- 枚举值**直接取共享层字典**，不另抄一份字符串数组 —— 加新动作时自动可用；
- `AUDIT_ACTIONS` 已在 `apps/server/src/audit/` 被使用，无需新依赖；
- 同步更新 `docs/server/openapi.json` 的 query 参数。

### 5.2 为什么不是"前端拉全量再筛"

审计表是**只增不改**的，量级只会涨。前端筛选意味着分页失效、`total` 失真。
筛选必须在 SQL 层（`(resourceType, resourceId, occurredAt)` 已有索引；`action` 目前无索引，
但配合时间范围后扫描量可控 —— 若实测慢，再加 `(action, occurred_at)` 复合索引，本轮不加）。

## 6. 「按用户查询」怎么落（本设计的关键取舍）

难点：`actorId` 是 **cuid 文本**，没法让人手输；
而天然的"用户下拉"依赖 `GET /api/user` —— **该接口现在是 `throw TODO`，请求 500**（见阶段计划 C4）。

三个选项：

| 方案 | 做法 | 代价 | 判断 |
| --- | --- | --- | --- |
| A | 输入框手输 cuid | 零 | ❌ 没人记得住 cuid |
| B | 先做用户列表接口，再做下拉 | 要把 C4 的前置一起做（Service + 分页 + 权限 + 序列化） | 范围翻倍，且与审计无关 |
| **C（推荐）** | **下钻式**：表格里"操作者"可点，点一下即以 `actorId` 筛选，顶部出现可清除的条件胶囊 | **零新接口** | ✅ 满足需求、也是最自然的排查路径 |

**为什么 C 是对的**：排查审计的真实动作是"看到一条可疑记录 → 看看这个人还干过什么"，
而不是"先想好要查谁"。下钻正好是这个顺序；用户列表那件事等 C4 落地后，
可以再补一个下拉（届时 `actorId` 只是多一个输入来源）。

**v1 的筛选能力**：

- 「行为」下拉（需 §5 后端改动）；
- 「时间范围」= `UInputDate` 的 **range 模式**（Owner 确认进 v1；顺带作为后续日期控件的用法样板）；
- 「操作者」= 表格下钻 + 可清除胶囊；
- 「资源」= 同样下钻（`resourceType + resourceId`），顺手就有。

⚠️ **日期边界是这一版唯一容易错的地方**：选择器给的是 `YYYY-MM-DD`（日历日），
后端 `from` / `to` 是**时间点**。若两端都取当天 00:00，"到 10 月 16 日"会把 10 月 16 日整天排除，
用户看到的是"今天没记录"。所以 `from` 取当天 00:00:00、`to` 取当天 23:59:59.999（本地时区）。

## 7. 页面结构

```text
apps/admin/layers/13-settings/app/pages/audit/index.vue   ← 路由 /audit
  ├─ UPageHeader（标题 + 说明 + 右侧"刷新"）
  ├─ 筛选区：USelect（行为）+ 当前条件胶囊（可 ✕ 清除）
  ├─ UTable：服务端分页
  └─ UPagination / 空态 / 错误态 / 加载态
```

**为什么放 `layers/13-settings`**：它已是"系统级配置"的域（`settings/*`），
且 `Settings.Users:*` 与 `Audit.Log:view` 是同一类"管理面"能力。新建 layer 只为 1 个页面不划算。

配套文件：

| 文件 | 职责 |
| --- | --- |
| `layers/13-settings/app/apis/audit.ts` | `createAuditApi().list(query)`；`silent: true` + `retry: 0`（失败要落到页面错误区） |
| `layers/13-settings/app/composables/useAuditLog.ts` | 查询状态、分页、筛选条件与 URL 同步 |
| `layers/13-settings/app/config/audit-labels.ts` | 动作 / 资源 / 摘要的**展示映射** |
| `app/error.vue` | 403 / 404 / 通用错误 |

### 7.1 展示映射要有穷尽性保证

```ts
// 键集合直接来自共享层字典，值是中文文案
const AUDIT_ACTION_LABELS: Record<AuditAction, string> = { … }
```

`Record<AuditAction, string>` 而不是普通对象 —— **往 `AUDIT_ACTIONS` 加一个动作，这里不补就会编译失败**。
这是本仓已有的同类做法（`audit-coverage.test.ts` 的思路：把"忘了"变成"红"）。
文案属于展示层，**不进 `packages/common`**（共享层不认文案）。

## 8. 表格列

| 列 | 内容 | 备注 |
| --- | --- | --- |
| 时间 | `occurredAt` 本地时间（`YYYY-MM-DD HH:mm`），`title` 给完整时间 | 后端已按新→旧排序 |
| 操作者 | `actorSnapshot.nickname`（可点 → 下钻）+ 角色快照（`actorRoleKeys`，小标签） | 角色是**当时**的快照，不是当前角色 |
| 行为 | `AUDIT_ACTION_LABELS[action]` + 原始 `action` 作 `title` | 中文可读，原文可查 |
| 资源 | `resourceType` 中文 + `resourceId`（可点 → 下钻） | 简历 id 是整数、用户 id 是 cuid，都按字符串显示 |
| 摘要 | 按动作从 `metadata` / `resourceSnapshot` 取关键字段，穷尽 `switch` | 见 §8.1 |
| 请求 | `requestId` 前 8 位 + 复制按钮 | 用于和访问日志对齐 |

### 8.1 摘要（审计的价值就在这里）

| action | 摘要文案 |
| --- | --- |
| `resume.create` | `新建（locale: zh）` |
| `resume.delete` | `删除前：revision 9 · 3 个模块 · 曾是默认` |
| `resume.set_default` | `顶掉了 #3` |
| `user.create` | `角色：admin` |
| `user.delete` | `删除前角色：user` |
| `role.change` | `user → admin,user` |
| 其他 / 字段缺失 | `—` |

缺失字段一律显示 `—` 而不是空白：**"没有这个信息"与"渲染坏了"必须能区分开**。

## 9. 状态与交互

| 状态 | 表现 |
| --- | --- |
| 加载 | `UTable` 的 loading（保留表头，避免跳动） |
| 空 | "没有符合条件的记录" + 若有筛选条件则给"清除筛选" |
| 错误 403 | 直接 `showError({ statusCode: 403 })` → 错误页（不要 toast 后留在空表格上） |
| 错误 5xx | 页面内错误区 + 重试按钮（不复用 403 页：这是"坏了"，不是"没权限"） |
| 筛选变化 | 回到第 1 页（否则会停在一个不存在的页码上） |

**筛选与分页写进 URL query**（`?action=…&actorId=…&page=2`）：刷新 / 分享 / 后退都成立。
代价是每次改筛选多一次 router 跳转 —— 可接受。

## 10. 验收标准

> ⚠️ **admin 端没有测试**（`package.json` 无 `test`，全应用 0 个 `*.test.*`），
> 所以本任务的验收**全部是人工 + typecheck**。这条不是免责，是要写进交接包的缺口。

| # | 步骤 | 期望 |
| --- | --- | --- |
| 1 | 超管登录 → 点导航「审计」 | 表格有数据、分页可翻、总数与页数一致 |
| 2 | 选一个「行为」 | 只剩该动作的记录；页码回到 1；URL 带上 `action` |
| 3 | 点某行的「操作者」 | 只剩该 actorId 的记录；顶部出现胶囊；点 ✕ 恢复 |
| 4 | 刷新页面 | 筛选与页码保持 |
| 5 | `admin` 登录 → 点导航「审计」 | **403 页**（不是白屏 / toast / 空表格），带侧栏 |
| 6 | `user` 登录 → 直接敲 `/audit` | 同上 403 |
| 7 | 未登录 → 敲 `/audit` | 跳登录页（`guest` middleware 已有） |
| 8 | 敲一个不存在的路径 | **404 页**，无侧栏 |
| 9 | 手动移除超管的 `Audit.Log:view` 后再进 | 前端 403 页；或用 curl 确认后端也 403（**双层都要挡**） |
| 10 | 后端停掉 → 进页面 | 页面内错误区 + 重试（**不是** 403 页） |
| 11 | 造一条没有 `metadata` 的记录 | 摘要列显示 `—`，不报错 |

机器侧：`pnpm check`（含 `typecheck`）通过 + `pnpm --filter @rs/server test` 不回归。

## 12. 已确认的决定（Owner 2026-10-16）

1. **导航项对所有人可见**，非超管点进去拿 403 —— 403 本身就是答案。
2. **403 页不给"切换账号"**，只告知 + 返回首页。
3. **路由是一级 `/audit`**（不进 `/settings`），排在导航第 3 位（简历之后）。
4. **时间范围筛选进 v1**，用 `UInputDate` 的 range 模式，作为后续日期控件的用法样板。
5. **错误页参考 greensketch-basic 的 `app/error.vue` 形态**（全屏空格 + 主按钮），
   但文案解析用**本仓的 errorCode 体系**（`@rs/common` 的两张表），不引入那套 i18n key。
