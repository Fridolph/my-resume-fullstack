## 1. 现状

| 项 | 现状 |
| --- | --- |
| admin 主导航 | **已挂载** Resume 项（`to: '/resume'`），注释为「业务域入口：my-resume 的简历编辑域」 |
| `/resume` | 骨架页（`layers/11-resume/app/pages/resume/index.vue`），只列了 `status: 'planned'` 的模块清单 |
| 创建能力 | **没有 UI 入口**；只能靠接口或 seed 造简历 |
| 可复用的既有资产 | `ResumeSchemaForm.vue`（schema 驱动表单，174 行）、`resume-editor-schemas.ts`（7 个模块的字段定义，269 行）、`resume-sections.ts`（区块注册表）—— 都在 web 的 `11-public-resume` layer 里 |

## 2. 目标结构：把 resume 域做成第二个 settings

`settings` 的模式是「父页 + 二级左侧栏 + `<NuxtPage />`」：

```vue
<!-- settings.vue -->
definePageMeta({ layout: 'has-sidebar', title: 'Settings' })
<template>
  <section class="flex min-h-0 flex-1">
    <aside class="hidden w-60 shrink-0 border-r border-default bg-default lg:block">
      <UNavigationMenu orientation="vertical" :items="settingsNavigation" :ui="…" />
    </aside>
    <NuxtPage />
  </section>
</template>
```

resume 域照此改：

```
/resume              → 列表 + 入口（父页，二级侧栏在这里）
/resume/new          → 创建大表单            ← 本轮目标
/resume/new/import   → 上传 → 分析 → 概览 → 确认  ← 本轮只做占位
/resume/:id          → 单份详情（未来）
/resume/:id/layout   → 展示配置（未来）
/resume/:id/versions → 版本历史（未来）
```

二级导航配置新建 `layers/11-resume/app/config/resume-navigation.ts`，仿 `settings-navigation.ts`：

```ts
export const resumeNavigation = [
  { type: 'label', label: 'Drafts' },
  { label: '所有简历', icon: 'i-lucide-list', to: '/resume' },
  { label: '新建简历', icon: 'i-lucide-plus', to: '/resume/new' },
]
```

### ✅ 决策（P1）：**本期做静态侧栏**

以下思路保留作为后续迭代依据 —— 现在**不要**做「多份简历」的动态侧栏：

若侧栏要**列出多份简历**（动态项），父页就不能用静态 `navigation` 配置，必须改成**数据驱动**。
建议**先按静态菜单做**，等「多份简历」需求明确再换。理由：静态 → 动态是局部重构，
而**猜错结构**才是真坑（比如先做成按 `status` 分组，后来发现要按时间轴，就要重写）。

## 3. 创建表单：模块化大表单

按 `resumeSectionSchema` 的预设类型分块：

| 区块 | 契约 type | 说明 |
| --- | --- | --- |
| 基本信息 | `profile` | **必填**（姓名是唯一真正必填的内容） |
| 核心竞争力 | `highlights` | 可空 |
| 教育经历 | `education` | 可空 |
| 工作经历 | `experience` | 可空 |
| 项目经历 | `projects` | 可空 |
| 个人能力 | `capabilities` | 可空；⚠️ 编辑层键名是 `skills`（见 §6） |
| 自我评价 | `evaluations` | 可空 |

### 复用边界（已核实后修正）

⚠️ 最初设想「字段表也复用」是不成立的：web 的 `resume-editor-schemas.ts` 面向 **`ResumeContent`**
（`{ profile, highlights, skills }`），而创建页提交的是**契约模型**
（`ResumeDocument['content'].sections[]`，键名 `capabilities`）—— **两套数据结构**，字段表不能照搬。

**确定的分工**：

| 层 | 归属 | 说明 |
| --- | --- | --- |
| 表单**数据描述**类型 | `packages/common` 的 `ui/form-schema.ts`（`FormFieldSchema` / `FormSegmentSchema`） | 纯数据、可脱离 Vue，两端共用 |
| 表单**渲染** | `packages/ui` 的 `MySchemaForm` / `MySchemaFieldInput` | 通用「root + segments」渲染，含增删与上下移 |
| **字段表** | 各端自写 | web 面向 `ResumeContent`；**admin 面向创建输入** |

创建页只负责：组织区块顺序、维护稀疏输入状态、提交时调 `POST /resume`。

> 搬迁已完成：`MySchemaForm` 从 web 的 `editors/` 移到 `packages/ui`，web 侧改为自动导入；
> 类型移到 `@rs/common`，`resume-editor-schemas` 保留 `Resume*` 别名指向新类型。
> 实测 web 编辑抽屉渲染正常（表单内 100 个输入控件、0 console error）。

## 4. 上传 → 概览 → 确认（本轮只做占位）

### 用独立路由，不用弹窗

流程是「上传 → 解析/AI 分析（等待）→ 概览 → 确认」**多步 + 有等待**，
弹窗里套等待态、回退与刷新都很难处理。独立路由天然有 URL、可回退、可刷新。

```
/resume/new/import
  ① 上传：拖拽 + 选择，支持 pdf / md / word / txt
  ② 解析中：本地提取文本 → AI 分析中（骨架屏 / 进度）
  ③ 概览：识别结果统计（基础信息 XXX、工作经历 N 条、项目 N 条…）
        每项可勾选「要 / 不要」，并提示「接下来会预填入表单，你可以再改」
  ④ 确认：回到 /resume/new，数据已预填
```

⚠️ **状态怎么传给表单**：建议**同一路由内分步**（`/resume/new?step=import`，用组件内状态推进），
**不要跨路由传**（容易丢、刷新即失效）。除非将来需要跨页保留，再引入 store。

### ✅ 决策（P3）：同路由内分步 + 通用上传接口

**接受的输入**：文件（`pdf` / `md` / `doc` / `docx` / `txt`）+ **可直接粘贴纯文本**。

**上传走通用接口**（不只服务简历）：
- 服务端新增一个通用上传端点，文件先落**本地 `/static/upload/`** 目录；
  后期再考虑 S3 或第三方存储（届时换存储实现，接口形状不变）；
- ⚠️ admin 侧**复用现有上传逻辑**：`apps/admin/app/composables/useFileUploader.ts`（304 行，含 `accept` / `multiple` / 校验）
  与 `components/upload/Files.vue`，API 层已有 `~/apis/files` 的 `uploadFiles`；
- 服务端现有 `@nestjs/platform-express`（含 `FileInterceptor` / `useStaticAssets`），不需要新依赖。

**本轮只放占位**：在 `/resume/new` 顶部显示一张卡片，
「上传 PDF / Word / md / txt，由 AI 帮你填 —— 敬请期待」，点击只给提示，**不做假交互**。

## 5. 自定义模块（需要动共享契约）—— **已拆出为独立 Issue（P4）**

诉求：用户自定**标题**、自选**展示方式（组件）**、自填**内容**；更细的原子粒度（是否加 tag 等）
留到后面版本。**本轮先让用户高自由度地选「展示组件 + 展示内容」。**

### 契约侧：`custom` 分支 + 有限的 `view` 枚举

`resumeSectionSchema` 目前是 `z.discriminatedUnion('type', […])`，`type` 是固定字面量。新增分支：

```ts
z.strictObject({
  ...base,
  type: z.literal('custom'),
  data: z.strictObject({
    view: z.enum(['textList', 'richText', 'tagCloud', /* … */]),  // ← 有限枚举
    items: …,   // 或 content，取决于 view
  }),
})
```

⚠️ **`view` 必须是枚举，不能让用户填任意组件名**：

- 契约是**跨端共享 + 严格校验**的（`resumeDocumentSchema` 用 `strictObject`）；
- 一旦放开成任意字符串，web 就必须对「未知 view」做兜底渲染，数据库里也会出现前端认不出的数据；
- **枚举 + 渲染注册表**（沿用 `resume-sections.ts` 的既有模式）既能满足"高自由度选展示方式"，
  又不会让契约失控。

### 影响面（要单独过门）

- 动 `packages/common/src/resume/document.ts` → `resumeDocumentSchema` 变更 → **属于共享契约改动**；
- web 展示层要加 `custom` 的渲染注册；
- 建议**单独开一个 Issue** 承载，不与本页其他部分混在一个 PR。

## 6. 提交：用稀疏输入

用刚落地的 **`resumeDraftInputSchema`（Issue #36）**：客户端只提交用户填过的部分，
服务端 `buildResumeDocument` 补全缺失字段与六类空模块，并固定写 `schemaVersion: 1`。

好处：**前端校验与交互不会被完整文档的约束绑住**（不必在表单里就凑齐合法完整文档）。

**键名约定**：提交用契约的 `capabilities`；字段定义复用编辑层的 `skills`；
两层桥接只在 `toLegacySectionKey()`（`resume-sections.ts`）。**创建页不需要处理键名转换。**

| # | 问题 | **结论** |
