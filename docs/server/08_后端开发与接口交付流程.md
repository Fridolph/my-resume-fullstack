# 后端开发与接口交付流程

日期：2026-10-10。状态：项目级学习与开发约定。

这份文档回答四个问题：数据库结构如何进入代码和真实数据库，Prisma 命令分别什么时候使用，接口如何同步到 Apifox，以及前端拿到什么才算完成交付。

## 1. 先分清四个“真源”

| 内容 | 真源 | 作用 |
| --- | --- | --- |
| 数据库结构 | `apps/server/prisma/schema.prisma` | 描述模型、字段、关系和数据库约束 |
| 结构变更历史 | `apps/server/prisma/migrations/*/migration.sql` | 记录每次可审查、可重复部署的 SQL 变化 |
| 初始化数据 | `apps/server/prisma/seed.ts` | 幂等写入角色、权限和本地学习账号 |
| HTTP 接口契约 | Controller、Zod Schema、响应类型和 OpenAPI | 定义路径、方法、输入、输出和错误 |

Navicat 是数据库客户端，不是项目结构真源。它适合查看表、检查数据、执行只读查询和排查迁移结果；正式的字段、索引、外键和约束应先写进 Prisma schema，再生成迁移。直接在 Navicat 改结构会让数据库领先代码，其他开发环境和 CI 无法复现。

### Role/Permission 的主键取舍

`Role` 和 `Permission` 属于 seed 管理的内部字典表，确实可以使用 `Int @id @default(autoincrement())`；`key` 才是业务稳定标识（如 `super_admin`、`Settings.Users:view`）。数字主键不会让权限判断更安全，也不会替代唯一的 `key`。

当前仓库已经用 cuid 建立了 `roles`、`permissions`，并由 `role_permissions`、`user_roles` 外键引用。把它们改成数字不是修改两列，而是要同时迁移主键、所有外键、Prisma 类型和 seed 的 upsert 查询；如果数据库已有角色关联，还必须保证旧关联逐行映射到新 ID。该变更不能在 Navicat 直接改，也不应和 Apifox 文档同步混做。

建议在当前数据库已存在数据时保留 cuid；如果确认数据库仍是可丢弃的学习库并希望练习字典表迁移，再单独建立 Issue，先备份并设计“新数字列 → 回填映射 → 重建外键 → 删除旧列”的迁移。无论最终选哪种，接口只返回 `role.key`，不把内部主键作为前端权限契约。

数据内容与结构要分开：业务脚本或后台接口负责业务数据，seed 负责可重复的基础数据。不要把某次手工插入的超管密码、生产业务数据提交进仓库。

## 2. Prisma 文件应该写什么

```text
apps/server/
├── prisma.config.ts
├── prisma/schema.prisma
├── prisma/migrations/<时间>_<名称>/migration.sql
├── prisma/seed.ts
└── src/generated/prisma/             # generate 产物，不手改、不提交
```

- `schema.prisma` 写模型、关系、`@unique`、默认值和数据库映射。
- migration 写“从旧结构到新结构”的历史；已应用迁移不改含义。
- seed 只写可重复执行的角色、权限和本地基础账号。
- Service 写业务规则、权限判断、密码哈希和事务编排。
- `src/generated/prisma` 是生成结果，不手改；删除后可重新生成。

## 3. 一次结构变更的标准流程

1. 在讨论文档和 Issue 中确认字段语义、默认值、约束、回退和验收。
2. 修改 `schema.prisma`。
3. 在可重置的本地开发库运行迁移开发命令。
4. 审查生成的 SQL，确认没有意外删除数据或约束。
5. 运行 `generate`，让 Service 类型认识新字段。
6. 编写 Schema、Controller、Service、seed 和 Apifox 契约。

```bash
pnpm --filter @rs/server db:migrate:dev -- --name user_session_version
pnpm --filter @rs/server db:generate
```

`migrate dev` 生成并应用开发迁移；`generate` 只生成 Prisma Client，不创建表。

共享或生产环境只应用仓库已有迁移：

```bash
pnpm --filter @rs/server db:migrate:status
pnpm --filter @rs/server db:migrate:deploy
pnpm --filter @rs/server db:generate
```

部署准备也可使用：

```bash
pnpm --filter @rs/server db:prepare
```

不要用 `migrate dev` 连接生产库，也不要在服务器临时生成迁移。

## 4. Seed、Studio 与常用命令

```bash
pnpm --filter @rs/server db:seed
pnpm --filter @rs/server db:studio
```

seed 是幂等基础数据初始化，不是每次启动脚本，也不是生产业务数据导入工具。Studio/Navicat 用于查看和排查；看到不一致先查 `migrate status` 与 `_prisma_migrations`，不要直接改结构。

| 命令 | 用途 | 是否修改数据库 |
| --- | --- | --- |
| `migrate dev --name ...` | 本地生成并应用迁移 | 是 |
| `migrate deploy` | 按已有迁移部署 | 是 |
| `migrate status` | 检查状态 | 否 |
| `migrate resolve` | 处理明确的失败/已完成状态 | 修改迁移元数据 |
| `generate` | 更新 Client | 否 |
| `db seed` | 写入基础数据 | 是 |
| `db push` | 临时原型，不留迁移历史 | 是 |

本项目常规业务不使用 `db push` 替代迁移。共享库不要随意 `migrate reset`；失败迁移先看 SQL 与真实表状态，再决定修复、重建本地库或 `resolve`。

## 5. 从接口到 Apifox

接口交付至少写清：方法与路径、认证和权限、headers/path/query/body 字段、成功响应、失败 `errorCode`、分页/软删除/并发规则和副作用。

当前响应由全局 Filter/Interceptor 统一包装，Apifox 示例必须包含 `code`、`data`、`message`、`timestamp`、`traceId`，失败时包含 `errorCode`。前端按 `errorCode` 分支，不解析中文 message。

本项目目前未接入 `@nestjs/swagger`，暂不假装自动同步。当前手动流程：

1. 在 Apifox 配置 `baseUrl`，如 `http://localhost:3000`。
2. 按 Controller 路由创建接口，方法和路径与源码一致。
3. 将 Zod Schema 的必填、长度、可空、strict 规则写入请求 Schema。
4. 登录后保存 token，其他接口统一使用 `Authorization: Bearer {{token}}`。
5. 建立 200、400、401、403、404、409 等响应示例并记录 `errorCode`。
6. 用 Apifox 实际请求本地服务，保存为接口用例；变更时更新文档并保留变更说明。

当前可直接导入的静态文档是 [`openapi.json`](./openapi.json)，覆盖健康检查、登录、身份、创建用户、资料修改、密码修改、强制下线和软删除。导入 Apifox 时选择“导入 → OpenAPI/Swagger”，先预览差异，再决定更新已有接口还是创建新接口。用户列表/详情仍是 TODO，因此没有放进可运行接口文档。

长期可单独建立 Swagger/OpenAPI Issue：后端生成 OpenAPI JSON，Apifox 使用“导入 → OpenAPI/Swagger”更新接口；不要让 Apifox 反向修改 Prisma schema。

调试响应可以帮助修正文档示例，但不应把“复制一次返回 JSON”作为契约来源。推荐顺序是：先由 Controller/Zod/统一响应定义契约 → 在 Apifox 写请求与响应 Schema → 真实调试验证状态码、字段和错误分支 → 只把稳定的实际响应补充为 examples。否则一次偶然响应可能把 token、时间、traceId 或数据库内部字段错误固化进文档。

当前用户闭环建议顺序：登录 → 保存超管 token → 创建 user/admin → 各账号登录 → 修改资料/密码 → 超管强制下线 → 旧 token 请求 `/auth/info` 返回 401 → 原密码重新登录。

## 6. 交付给前端的最小包

- Apifox 地址、环境变量、认证前置步骤和可运行示例。
- 请求/响应字段表、失败 `errorCode` 和权限要求。
- 迁移是否已应用、是否需要 seed、旧数据兼容要求。
- 已迁移到 `@rs/common` 的 TypeScript/Zod 契约；未迁移前以 Apifox 作为 HTTP 真源。
- Issue、提交链接和已知未完成项。

前端不需要知道 Prisma 模型、数据库表名或 `P2002`；后端负责把持久化错误转换成稳定的 HTTP 状态和 `errorCode`。

## 7. 完整工作流

```text
讨论文档 → GitHub Issue/任务卡 → schema.prisma → migrate dev → 审查 SQL
→ generate → Schema/Controller/Service → seed（需要时）
→ server + Apifox 人工验证 → OpenAPI/手动同步 → 前端交付
→ Owner 验证 → 回填 Issue → 提交
```

本项目学习约定中，AI 不替 Owner 执行迁移、接口验证、测试或 Apifox 写入；文档提供命令和验收入口，Owner 运行后反馈结果。
