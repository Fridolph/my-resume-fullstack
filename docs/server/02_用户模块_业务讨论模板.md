## 3. 数据规则

- 用户名：必填；建议去首尾空格、2–32 字符、大小写敏感
- 显示名：按 §8 请求字段清单设为可选，未传使用用户名；传入时去首尾空格、2–32 字符。
- 密码：必填；建议 6–20 字符且不 trim；沿用 scrypt，只保存 `passwordHash`。
- 已确认可选字段：`email`、`phone`、`avatar`、`roleKey`。
- 邮箱：校验邮箱格式、最多 64 字符，转小写后保存；当前只作为联系方式，不用于登录或身份校验，填写后必须唯一。
- 手机号：保存为字符串，仅接受中国大陆 11 位手机号；填写后必须唯一，也不绑定短信登录。
- 头像：建议保存 http/https URL，最多 2048 字符；上传与文件管理另行设计。
- 空值：建议可选资料未传时保存为 null；传空字符串时校验失败。
- 角色：已确认新增 `super_admin`；仅它能创建 `admin/user`，`roleKey` 默认 `user`；创建接口不能创建 `super_admin`。

## 8. 创建用户设计与实装

### 请求与响应

业务路由是 `POST /user`，服务器配置的全局前缀为 `api`，实际地址为 `POST http://localhost:4049/api/user`。
为便于以后扩展，可以在基础请求 baseURL里也预留 版本，比如 v1 v2 便于以后加入 AI 相关功能后能同时调用和维护不同版本的接口

版本化建议使用 Nest 的 URI 版本支持；版本升级由契约变化驱动。涉及现有 health、auth 和前端 baseURL，本轮保留 `/api`，另立版本化任务。仅修改前端 baseURL 不能让后端自动支持 v1/v2。

请求字段：`username`、`password` 必填；`displayName`、`email`、`phone`、`avatar`、`roleKey` 可选。未传 displayName 使用 username，未传 roleKey 使用 user；其余未传资料存为 null。密码保留原样，不 trim；可选资料传空字符串或 null 均为 400。

响应：`id`、`username`、`displayName`、`email`、`phone`、`avatar`、`roles`（角色的 id/key/name）、`createdAt`、`updatedAt`。不返回密码或密码哈希。HTTP 状态为 201，现有统一成功响应体的 code 为 200；这是原响应包装的行为。

示例请求（密码仅作示例）：

```json
{
  "username": "learner",
  "displayName": "学习用户",
  "password": "Learning123!",
  "email": "learner@example.com",
  "roleKey": "user"
}
```

### 表结构与扩展边界

现有 `User` 已增加三个可空列 `email String?`、`phone String?`、`avatar String?`；迁移文件为 `20261009100000_user_contact_fields`。只新增可空列，不修改既有数据和用户主键。回滚应先退回对应源码，再撤销这三列；删除列会丢弃新增资料，需先备份。AI 未执行迁移、seed 或生成命令。

`roleKey` 是创建请求的字段，通过它连接 `Role` 并创建 `UserRole`，不在 `User` 上增加单一角色列；这样数据库仍可承载多角色。

后续微信、GitHub 等账号建议使用独立 `UserIdentity` 表：`userId`、`provider`、`providerAccountId`，按提供方与稳定账号 ID 建唯一约束。联系方式、用户资料和外部身份分别演进；OAuth token、授权流程和身份绑定不属于本轮。

### 创建用例

```text
JwtAuthGuard：
  验签并检查过期
  通过 token.sub 查询未删除的数据库用户、角色、权限
  将数据库中的当前身份写入 request.user
  无效 token / 用户不存在或已删除 → 401

创建权限守卫：
  当前用户没有 super_admin 角色 → 403
  当前用户没有 Settings.Users:create 权限 → 403

createUserSchema：
  按确认后的字段规则校验请求
  拒绝未声明字段
  email、phone、avatar 未传时允许缺省
  roleKey 只允许 admin/user；未提供时默认为 user

UserController.create(createUserDto)：
  调用 UserService.create(createUserDto)

UserService.create(createUserDto)：
  用 hashPassword 将 password 转成 passwordHash
  显式构造持久化输入：username、displayName、passwordHash、email、phone、avatar、roleKey
  可选资料未传时转为 null
  调用 PrismaService.user.create（不传明文密码）
  唯一约束冲突交给全局异常过滤器返回 409
  指定角色未初始化 → 400
  其他数据库错误交给统一异常过滤器处理
  返回安全用户数据

PrismaService.user.create：
  按 roleKey 对应的角色 ID 连接已存在的 Role
  使用 Prisma nested write 一次创建 User 和 UserRole
  任一步失败 → 整体回滚
  select 仅选择响应需要的安全字段

ApiResponseInterceptor：
  使用已有统一响应包装创建结果
```

数据库唯一约束是重名判定的最终依据，避免“先查不存在 → 并发创建”时仍写入重复用户名。当前 `username @unique` 包含软删除记录，本轮不允许复用；以后如需改规则，应同时设计数据库约束。

### 超级管理员与登录接线

新增超级管理员后，登录已接数据库，角色权限以每次受保护请求时恢复的数据库身份为准。对应接线：

```text
权限预设：
  super_admin 拥有全部权限
  admin 移除 Settings.Users:create
  user 保留现有普通用户权限
  其他用户管理权限在对应方法开工时讨论

seed 源码：
  幂等初始化三种角色及关联权限
  沿用现有初始 admin 账号，将它的初始角色设为 super_admin
  不增加公开创建 super_admin 的入口

AuthService.validateCredentials：
  按用户名查询未删除用户
  用 verifyPassword 验证 passwordHash
  返回用户 ID、用户名、数据库角色键与去重后的权限键

模块接线：
  AppModule 导入 UserModule
  AuthService 与 UserService 均直接使用全局 PrismaService
  AuthService 负责密码验证、JWT 与身份映射，UserService 专注用户创建
  UserModule 不反向导入 AuthModule，避免循环依赖
```

Owner 本轮已授权按文档实装。seed 将现有初始 admin 账号绑定为 super_admin，并移除它原来的 admin 角色关联；密码不覆盖，软删除账号不会自动恢复。seed 每次运行都会确保该初始账号具有超级管理员身份，因此这仍是本地学习初始化入口。撤回角色调整时需恢复角色预设与账号关联；AI 未执行 seed。

登录与 `/auth/me` 仍保留 user、permissionKeys，并额外返回 roleKeys。旧演示账号不再是登录数据源；以前签发给固定 ID 的演示 token 需要重新登录。

### 人工验证入口（Owner 执行）

1. 确认角色与初始超级管理员已初始化，使用真实登录取得 token。
2. 超级管理员创建一个默认 `user`，再创建一个 `admin`，检查角色关联及响应字段。

5. 尝试创建 `super_admin` 应返回 400；返回体不包含密码或哈希。
6. 确认创建失败时没有残留用户或角色关联。

### 学习要点

- Controller 不仅规划路径，还负责取参、挂载 schema 与权限守卫、调用 Service。
- `z.infer` 推导 DTO 类型，但 TypeScript 类型运行时不存在；真正拒绝非法请求的是 Zod 与全局校验管道。
- Service 在写入前构造不含明文密码的数据；复杂查询出现后再引入 Repository 隔离持久化细节。
- Prisma nested write 自带事务语义，不需要再叠一层手动事务。
- 列表分页先在模块内实现；第二个分页接口出现后，再根据稳定共性抽纯类型和元数据计算，不把用户筛选塞进公共仓储。
