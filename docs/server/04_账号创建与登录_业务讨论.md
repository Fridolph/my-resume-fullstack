# 超管创号与邮箱登录

> 2026-10-10：Owner 已确认 username/email 登录、cuid 主键、nickname 昵称和仅超管创号；源码已实装，未运行验证。公开注册暂不开放。

## 1. 字段与接口契约

| 字段 | 职责与规则 |
| --- | --- |
| id | 系统生成 cuid，稳定且不可由请求指定 |
| username | 可选唯一登录名，3–32 个中文/字母/数字/下划线，统一转小写 |
| email | 可选唯一登录邮箱，trim 后转小写，邮箱格式，最多 64 字符 |
| nickname | 可修改的展示昵称，非唯一；未设置时展示回退到 username 或 email |
| password | 创号和登录 6–20 字符；不 trim |
| avatar | 创号可选，HTTP(S) URL，最多 2048 字符，未传为 null |
| roleKey | 仅用于超管创号，admin/user，默认 user；不创建 super_admin |

username 与 email 至少填写一个；phone 不作为登录字段，旧 displayName 已改为 nickname。昵称修改接口仍是后续任务。

| 接口 | 访问资格 | 行为 |
| --- | --- | --- |
| POST /api/user | super_admin + Settings.Users:create | 创建登录账号并绑定角色 |
| POST /api/auth/login | 未登录可访问 | account（用户名或邮箱）+ password，成功签发 token |
| GET /api/auth/me | Bearer token | 返回数据库当前身份、角色和权限 |

创建返回 id、email、nickname、avatar、roles、createdAt、updatedAt，不返回密码或密码哈希。HTTP 为 201，现有成功响应包装的 code 为 200。

登录和 me 返回 user（userId、email、nickname）、roleKeys、permissionKeys；登录额外返回 token。外层均使用现有统一响应。

非法/额外字段为 400；邮箱冲突为 409 Common.Conflict:unique；账号不存在、已删除、密码不匹配统一为 401 AUTH.Credentials:invalid，文案“账号或密码不正确”。认证不捕获数据库故障来伪装成凭据错误。

## 2. 完整用例与各层职责

```text
POST /user：
  JWT Guard 验签并查询当前身份
  UserCreationGuard 要求超管角色和创建权限
  createUserSchema 校验字段并规范化 username/email
  UserController 调用 UserService.create(createUserDto)
  UserService 查询角色，不存在时给出明确业务 400
  hashPassword 使用随机盐生成密码哈希
  Prisma nested write 创建用户与角色关联，一起成功或回滚
  select 只查询允许返回的字段
  并发邮箱冲突交给全局 Filter 返回通用 409

POST /auth/login：
  @Public 放行未登录请求
  loginSchema 规范化 account，密码保持原样
  AuthController 调用 AuthService.login(loginDto)
  account 含 @ 时按小写 email 查询，否则按小写 username 查询未删除用户、密码哈希、角色和权限
  if (没有用户 || verifyPassword 失败)：统一 401
  toAuthUser 显式转换安全身份，权限去重
  sign 用 userId 作 sub 签发有期限的 JWT
  返回 token 和身份信息

GET /auth/me：
  JWT Guard 验签并通过 sub 查询当前数据库身份
  账号已删除则拒绝；权限变化取数据库最新值
  Controller 返回安全身份，Interceptor 包装响应
```

密码确认只在创号表单中使用，不是登录入参。verifyPassword 读取已存哈希中的原盐、参数重新计算并安全比较，不能再次调用生成随机盐的 hashPassword 后直接比较。

JWT 是签名而非加密，当前只存 sub 和库生成的 iat/exp；不保存邮箱、昵称、密码或权限快照。每次回查数据库的代价是身份查询，收益是软删除和权限变更在下次请求生效。token 保存不等于永久登录；浏览器存储方案由前端窗口单独对接。

邮箱格式校验不证明邮箱归属，邮箱验证、限流、刷新令牌、主动注销另行设计。公开注册将采用独立入口并固定 user 角色，本轮不开放。

### 3.3 从一次创建理解各层

假设超管提交 email 为 ` Learner@Example.com `，省略 nickname、avatar、roleKey：

1. 全局 JWT Guard 验签、查当前身份；UserCreationGuard 检查操作者是超管且有创建权限。请求里的 roleKey 是新账号角色，不能代表操作者权限。
2. 全局校验 Pipe 执行 createUserSchema：邮箱变为 learner@example.com，roleKey 默认 user；未知字段拒绝。Dto 是这份校验结果的 TypeScript 类型，不会自行执行校验。
3. Controller 接到校验后的 createUserDto，委托 Service。
4. Service 找到 user 角色、生成密码哈希，设置默认昵称“新用户”和 avatar=null，再调用 prismaService.user.create。
5. data.roles.create 是同时插入 UserRole 关联记录，不是在 users 表写 roleKey。Prisma nested write 保证本次用户与关联一起成功；若关联失败，用户写入也回滚。
6. 数据库保证 email 唯一。当前实现不再预查重复邮箱，冲突统一交给 Filter 返回 409；即使加预查，也不能替代数据库约束。
7. create 的 select 直接取得创建后的安全字段，不需要再查一次用户；Service 将关联结构展开成 roles，Interceptor 包装返回。

### 3.4 从一次登录理解密码与会话

```text
login(loginDto):
  user = 按规范化邮箱查未删除用户（含 passwordHash、角色、权限）
  if user 不存在:
    抛出统一凭据错误
  if verifyPassword(loginDto.password, user.passwordHash) 为 false:
    抛出相同凭据错误
  authUser = 显式挑选安全身份，并合并去重权限
  token = 签发 sub=authUser.userId 的 JWT
  return { token, user: 安全身份, roleKeys, permissionKeys }
```

创号时 hashPassword 生成随机盐；登录时 verifyPassword 取出已保存的盐和参数再计算，比较结果。相同密码重新调用 hashPassword 会生成不同盐，不能直接比较两次哈希字符串。前端通过 HTTPS 提交密码，服务端验密；前端确认密码只防止输错，不替代服务端校验。

后续请求携带 Authorization: Bearer token，全局 JWT Guard 验签并通过 sub 恢复当前身份，挂到 request.user。这里 token 是认证凭证，前端需要保存并附加到请求，且必须处理过期；当前尚未实现刷新 token 或主动注销。

认证采用 `@nestjs/passport` / `passport` / `passport-jwt`，`@nestjs/jwt` 继续负责登录后的令牌签发。请求认证按以下顺序执行：

```text
JwtAuthGuard.canActivate：@Public() 则放行，否则调用 AuthGuard('jwt')
  → passport-jwt：提取 Bearer token，按 HS256 验签并检查过期
  → JwtStrategy.validate：检查已验签载荷的 sub
  → AuthService.restoreUser：查询未删除用户及当前角色权限
  → JwtAuthGuard.handleRequest：保留业务/数据库异常，转换 token 失败错误码
  → Passport Guard：将返回身份写入 request.user
  → 业务 Guard / Controller
```

PassportModule 使用 session=false，不创建服务器登录 session。当前用户类型通过扩展 Express.User 接入 Passport 的 Request.user 声明，避免重复声明不同类型。Guard 中只保留缺失、无效、过期三种 token 错误映射；Strategy 或 Service 的数据库故障不能转换为 401。

## 5. Apifox 创建 → 登录 → 会话

baseURL 默认 http://localhost:4049/api，所有请求使用 JSON Content-Type。

1. POST {{baseURL}}/auth/login（seed 初始化的学习账号；若此前改过密码，使用实际密码）：

```json
{ "account": "super", "password": "super!" }
```

保存响应 data.token 为 superAdminToken。

2. POST {{baseURL}}/user，Authorization 选择 Bearer {{superAdminToken}}：

```json
{
  "username": "learner",
  "nickname": "学习用户",
  "password": "Learning123!",
  "roleKey": "user"
}
```

3. POST {{baseURL}}/auth/login：

```json
{ "account": "learner", "password": "Learning123!" }
```

保存响应 data.token 为 userToken。大小写不同的邮箱应登录同一 userId。

4. GET {{baseURL}}/auth/me，携带 Bearer {{userToken}}，检查 user.email/nickname、roleKeys、permissionKeys。

5. 人工检查：错误密码/不存在邮箱同为 401；重复规范化邮箱为 409；无 token 调 me 为 401；普通用户和 admin 创号为 403；创建 super_admin、传旧 username/displayName/phone 字段为 400；所有响应均不含 passwordHash。
