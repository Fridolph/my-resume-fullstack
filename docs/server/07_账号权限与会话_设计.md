## 2. 已确认：三种角色与游客

| 身份 | 定位 | 能力与限制 |
| --- | --- | --- |
| super_admin | 项目所有者 | 管理账号、编辑业务内容；不能读取密码，修改自己密码仍须旧密码 |
| admin | 供外部体验编辑功能的账号 | 可进入 admin，体验获授权的内容编辑；不能创建、删除其他账号，只能修改自己的账号资料与密码 |
| user | 登录后的浏览者 | 可读公开业务资料、使用 AI 对话、选择 web 预设布局与主题；不能编辑简历内容或进入 admin |
| guest | 未登录状态 | 可浏览绝大部分公开 web；受保护数据与高级操作仍需登录；不是数据库角色 |

不增加 hr 角色。具体 AI 配额、admin 可编辑业务域和游客可用的展示设置，随对应模块讨论，不在本轮扩大权限。

“user 各种只读权限”指已授权的业务阅读，不代表能读取任意用户邮箱等私有资料。用户列表沿用已确认的公开字段范围；本人资料修改、旧密码改密属于账号自助能力。

user 选择布局/主题属于自己的观看偏好，不能覆盖所有人看到的全局简历配置。先由前端保存个人偏好；以后若要跨设备保存，应按 currentUser.userId 保存个人配置，不能复用全局编辑接口写入作者配置。

前端 permissionKeys 控制体验；后端每次恢复身份并检查权限和目标归属。旧数据库里 admin 即使残留账号编辑/删除权限，也不能越权管理他人。角色预设调整需要单独同步 seed 与已有关联，改文档不会改变数据库权限。

## 3. 已采用：用 sessionVersion 撤销旧 token

JWT 验签只证明载荷未被篡改、未到期。当前每次请求已查询 User，可在这次查询里比较会话版本，无需为了全部设备下线增加 Redis 或每个 token 的黑名单。

已采用字段：User.sessionVersion 为非负整数，默认 0；JWT 保留 sub，并增加 sessionVersion。角色、权限和密码仍不写入 JWT。数据库版本是服务端当前认可的版本，token 中的版本是登录时的快照。

```text
LOGIN(loginDto):
  account = 规范化登录标识
  user = 查询未删除账号及 passwordHash、sessionVersion
  if user 不存在 OR 验证密码失败:
    FAIL 401 账号或密码不正确
  token = 签名({ sub: user.id, sessionVersion: user.sessionVersion })
  RETURN token 与显式挑选的安全身份

AUTHENTICATE(token):
  payload = Passport 验签并检查过期时间
  if sub 非有效字符串 OR sessionVersion 非非负安全整数:
    FAIL 401 访问令牌无效
  user = 查询未删除账号及当前 sessionVersion、角色、权限
  if user 不存在:
    FAIL 401 账号不可用
  if payload.sessionVersion != user.sessionVersion:
    FAIL 401 会话已失效，请重新登录
  RETURN 从数据库恢复的 currentUser
```

强制下线把版本从 0 增到 1：所有版本为 0 的 token 在后续请求中返回 401；原密码重新登录拿到版本为 1 的 token，仍可使用。这撤销的是此前会话，不是禁止重新登录。

升级后没有 sessionVersion 的旧 token 应统一失效，用户需重新登录；不能默认为 0，否则旧格式 token 可绕过初次版本校验。登录与强制下线并发时，以登录读取到的版本为准：读到旧版本的 token 可能刚签发就失效，这是安全的拒绝，可重新登录。已经通过鉴权并正在执行的请求不会被追溯取消。

迁移影响：新增 User 字段、更新 Prisma Client、JWT 类型、签发与身份恢复；HTTP 登录响应可保持原形状，sessionVersion 不必返回前端。回退不仅涉及源码/字段，也涉及已经签发的 token；不能直接回到忽略版本的旧认证逻辑，否则尚未过期的已撤销 token 可能再次被接受。回退认证方案时应另行安排全量会话失效。

## 4. 用例一：本人修改密码（已按方案实装）

路由：PATCH /user/:id/password，输入为 oldPassword、newPassword，不接收操作者 ID 或角色。所有角色都仅能修改自己。密码不 trim；新密码复用当前创建密码规则，确认密码由前端负责。

```text
CHANGE_OWN_PASSWORD(id, changePasswordDto, currentUser):
  if id != currentUser.userId:
    FAIL 403 只能修改自己的密码

  user = 查询 id 对应未删除用户的 passwordHash、sessionVersion
  if user 不存在:
    FAIL 404 用户不存在或已删除
  if verifyPassword(changePasswordDto.oldPassword, user.passwordHash) == false:
    FAIL 400 旧密码不正确
  if verifyPassword(changePasswordDto.newPassword, user.passwordHash) == true:
    FAIL 400 新密码不能与旧密码相同

  newHash = hashPassword(changePasswordDto.newPassword)
  ATOMIC UPDATE User:
    WHERE id 匹配 AND 未删除
      AND passwordHash == 查询时的哈希
      AND sessionVersion == 查询时的版本
    SET passwordHash = newHash, sessionVersion = sessionVersion + 1
  if 更新行数 == 0:
    FAIL 409 账号状态已变化，请刷新后重试

  RETURN { id }
  客户端清理本地会话并要求重新登录
```

单条条件更新同时写哈希与递增版本，不需要先写密码再写版本。旧哈希和版本条件防止两次并发改密都基于同一个旧密码成功，也防止并发强制下线后仍按旧状态提交改密。成功后包括本设备在内的旧 token 都失效；新旧密码不能相同，返回 `{ id }`。

## 5. 用例二：超管强制下线（已按方案实装）

路由：POST /user/:id/force-logout，无密码请求体。当前沿用 Settings.Users:edit 加 super_admin 角色双重授权；不新增专用权限键。

```text
FORCE_LOGOUT(id, currentUser):
  if 当前身份不含 super_admin OR 不具备指定管理权限:
    FAIL 403 仅超级管理员可强制下线用户
  if id == currentUser.userId:
    FAIL 403 不能通过管理接口强制下线自己

  target = 查询未删除用户及角色
  if target 不存在:
    FAIL 404 用户不存在或已删除
  if target 含 super_admin OR 不含 user/admin:
    FAIL 403 目标用户受保护

  ATOMIC UPDATE User:
    WHERE id 匹配 AND 未删除 AND 仍为允许的目标角色
    SET sessionVersion = sessionVersion + 1
    不修改 passwordHash
  if 更新行数 == 0:
    FAIL 409 用户状态已变化，请刷新后重试
  RETURN { id }
```

数据库使用原子 increment，避免两个并发下线互相覆盖版本。以后增加在线改角色时，需要与角色修改共同设计事务/锁，不能仅靠预查询宣称跨表并发安全。

前端在下次受保护请求收到 401 时清理会话；没有 WebSocket/轮询时，已经显示的页面不会立即自动消失。当前需求是撤销 token，不追加实时推送或账号禁用功能。

## 6. 同一主域不同子域：可以共享登录

Owner 已确认部署形态为 www.example.com 与 admin.example.com；以下以 api.example.com 为统一后端示意，不代表当前部署配置已修改。

### 浏览器共享会话的建议起点

两个前端调用同一个 API 登录接口。API 设置 HttpOnly、Secure、Path=/、SameSite=Lax 的会话 Cookie；建议先不设置 Domain，使 Cookie 只发送给 api.example.com。两个前端都以 credentials: include 请求该 API，浏览器会携带同一份 Cookie，因此在 web 登录后，admin 可通过 GET /auth/info 恢复同一身份。

Cookie 不需要发给两个前端域才能共享 API 会话；也不用把 token 复制进两份 localStorage。HttpOnly Cookie 不能由前端 JavaScript 读取并拼接 Authorization，Passport 需增加 Cookie token 提取方式；可保留 Bearer 供 Apifox 使用，双凭据同时出现时的处理规则在接线前定稿。

这些地址跨 origin，但 HTTPS 下属于同 site。CORS 需显式允许两个前端 origin 并允许凭据，不能用通配符。Cookie 会自动随请求发送，写接口需校验可信 Origin，并设计 CSRF 防护；SameSite 不能代替整个 CSRF 方案。共享登录不会授予 admin 权限：user 已登录仍不能进入后台或调用编辑接口。

### SSR 是独立的接线条件

仅 API 域 Cookie 不会随页面请求发送给 www/admin 的 Nuxt 服务端，SSR 不能自动恢复登录态。后续前端对接时按实际需要选择：

- 若公开页面 SSR 不需要登录身份：SSR 输出公开内容，客户端调用 auth/info 恢复登录。
- 若要求 SSR 首屏即真实身份：可讨论 Domain=example.com 的共享 HttpOnly Cookie，让两个 Nuxt 服务端按白名单转发会话给 API；影响是 Cookie 覆盖更多子域，所有子域需受信任。
- 若需要隔离每个前端的服务端会话：再讨论 Nuxt 代理/BFF 与统一认证交接，不提前加基础设施。

Cookie 登出需由 API 用相同作用域清除，两个前端下次恢复身份时均成为未登录；若仍保留可复制的 Bearer token，单纯清 Cookie 不能撤销它，全部会话撤销仍依赖 sessionVersion。开发环境 localhost 不同端口的 Cookie 不按端口隔离，需要统一 Cookie 名称与后端入口，不能照搬生产 Domain。
