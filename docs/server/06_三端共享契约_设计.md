# 三端共享契约：错误码、Schema 与业务类型

日期：2026-10-10。状态：设计待确认，尚未迁移源码。

最新关联决策：角色只保留 super_admin/admin/user，guest 为未登录状态；不增加 HR。本人改密、强制下线与共享登录见 [账号权限与会话设计](./07_账号权限与会话_设计.md)，这些接口确认后再补各自契约，不纳入第一轮迁移。

Owner 希望 user 的 Zod 校验、业务错误码和后续业务请求/响应类型由 server、admin、web 共用。这是对上一轮“暂保留本地 Schema”的方向调整；本轮先明确契约边界，再逐文件迁移，不增加独立包或泛用框架。

## 1. 什么需要共享

| 内容 | 放置位置 | 原因 |
| --- | --- | --- |
| API_ERROR_CODES、ApiErrorCode | common/src/api/error-codes.ts | 后端抛出、前端按同一错误码处理 |
| ApiResponse、ApiErrorBody、请求错误类型 | common/src/api/types.ts（已有） | 统一响应协议，不重复定义包装类型 |
| 创建/修改用户 Schema 及对应 DTO | common/src/user/user.schema.ts | 前端表单和后端入口使用相同字段约束与规范化 |
| 用户接口响应 DTO | common/src/user/user.types.ts（按真实返回定义） | 表达 HTTP 返回的安全资料，不泄露数据库模型 |
| 后续简历请求 Schema、ResumeDetailsResponse 等 | common/src/resume/（该用例明确后再建） | 按业务域归位，三端依赖明确的接口契约 |
| Prisma 模型与查询结果类型 | server 内 | 包含 Date、密码哈希、关联结构等持久化细节 |
| 授权、查重、数据库错误映射、inferErrorCode | server 内 | 执行业务和 HTTP 适配，不属于前端输入校验 |
| 表单确认密码、选项状态、Vue props、Pinia 状态 | admin/web 内 | 属于页面呈现，不一定属于 API 请求 |

TypeScript 类型在运行时不存在，不能代替 Zod 校验。Schema 是运行时对象，DTO 从 schema 推导，避免另一份手写请求 interface。Schema 所代表的是某个操作允许接收的输入，不能直接拿整个 Prisma User 模型生成创建或更新请求。

## 2. 建议结构

```text
packages/common/src/
  api/
    error-codes.ts             共享错误码常量与类型（待迁移）
    types.ts                   现有 ApiResponse<T> 等
    constants.ts               现有错误提示与处理策略
    response.ts                现有响应构造工具
    error.ts                   现有错误归一化工具
    request.ts                 现有请求头等工具
  user/
    user.schema.ts             创建、资料修改及 userId 的校验
    user.types.ts              已明确的用户响应类型
  index.ts                     保持现有 API 工具入口

apps/server/src/
  user/dto/user.schema.ts      重新导出共享用户契约；列表 TODO 暂留模块
  common/error-codes.ts        重新导出共享错误码；保留 inferErrorCode
```

对外入口：`@rs/common` 提供现有 API 工具和共享错误码；`@rs/common/user` 提供用户 Schema/DTO/响应类型。暂不建 resume 目录或预填未确定类型，也不把用户校验重导出到根入口，避免每个使用响应工具的模块都加载 Zod。

这里的 common 已是 workspace 包，不需要再新建 types 包。纯响应类型使用 import type，运行时 Zod Schema 使用普通 import；按业务域扩展子路径，不把所有业务类型堆到一个全局 types.ts。以后新增 resume 用例时，先确认请求与响应，再新增 common/resume 并导出；Service、Guard、Prisma 不随 DTO 一起迁移。

分文件依据是职责，不是文件数量：请求 Schema 与它推导的 DTO 放一起；响应类型只描述传输形状，单独归位。字段 Schema 保持同一个用户域文件内的常量，不为了每个字段再增加文件或通用工厂。

## 3. 三端如何使用同一份契约

```ts
import { API_ERROR_CODES, type ApiResponse } from '@rs/common'
import { updateUserSchema, type UpdateUserDto } from '@rs/common/user'

const parsed = updateUserSchema.safeParse(formPayload)
if (parsed.success) {
  const updateUserDto: UpdateUserDto = parsed.data
  // 前端把校验后的请求发给资料修改接口。
}
```

上面的注释是消费示意，尚未对接具体页面。后端仍通过全局 StandardSchemaValidationPipe 校验该 schema；前端校验改善表单体验，后端校验保证请求边界，不能因为两端共享而省略后端校验。

- PATCH 中未传表示保持原值，null 表示清空；前端需构造改动字段的 payload，不能直接提交整个页面状态。
- 有转换或默认值时，原始表单输入使用 `z.input<typeof schema>`，校验后的 DTO 使用 `z.output`（z.infer 等价于 output）。
- 确认密码只属于表单：页面可扩展本地 schema，发请求前再按公共请求 schema 挑选/校验合法字段。
- 错误响应的 errorCode 仍可保留 string，以容忍服务端新增错误码；已知错误分支使用 API_ERROR_CODES 常量，不能依赖中文 message。
- 用户响应中的日期使用 HTTP JSON 的 ISO 字符串类型，不能将 Prisma Date 原样作为前端共享类型。
- 不能强迫列表、详情、创建返回完全相同的 User 类型：列表只含公开字段，详情和创建可能含邮箱、角色，应按各接口的安全字段定义。

## 5. 构建与兼容边界

当前 common 通过 tsc 输出 ESM，server 编译为 CommonJS，前端由 Nuxt/Vite 消费。新导出必须同时考虑运行时与 TypeScript 类型解析：server 当前的传统 moduleResolution 需要可解析的子路径类型入口，不能只写 package.json exports 就假设三端都能找到声明。

现有 server 已消费 common 的根入口；本轮沿用同一模块兼容机制，不直接修改 Nest 编译模式或给全仓升级构建工具。Owner 人工运行时需要确认本机 Node 与现有 require(ESM) 方式兼容；不能将“增加共享契约”描述为已解决所有 Node 20 小版本的 ESM/CJS 兼容性。

新增公共运行依赖后需重新安装；直接单独启动 server 前需重新构建 common，继续使用既有根 dev 的先构建流程。不执行测试、类型检查、构建或安装来替代 Owner 的验证。

回退：撤回 common 新文件、依赖与导出，恢复 server 内原定义和锁文件 importer；HTTP 字段与数据库均不变。风险主要是共享包产物未更新、子路径声明无法解析和客户端误把页面状态当请求体。
