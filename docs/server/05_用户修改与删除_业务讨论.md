## 1. 目标与范围

- 当前目标：设计 `PATCH /api/user/:id` 的字段白名单及本人/超管授权规则。
- 资料修改、软删除、本人改密和强制下线已写入 DTO、Controller、Service、Prisma schema/migration 与业务错误码。
- 本轮新增 `User.sessionVersion` 数据字段；不执行数据库命令、接口验证、测试、提交或推送。
- 权限预设的同步单独说明影响后推进；本轮通过角色与目标归属判断，不依赖旧 admin 的全局 edit 权限授权。
- 风险：只检查权限键会放过持有旧权限的 admin；直接展开请求体可能修改登录标识或角色；预查询后目标可能被并发删除。
- 验收：以下伪代码已由 Owner 确认；由 Owner 用三种角色人工检查本人修改、越权修改、禁止字段及不存在目标。
- 回退：本阶段只需撤回文档改动，无数据库迁移。后续资料修改实装不改变表结构。

## 2. 已确认的权限边界

| 能力 | user | admin | super_admin |
| --- | --- | --- | --- |
| 查看用户列表 | 允许 | 允许 | 允许 |
| 查看用户详情 | 仅本人（根据邮箱/角色可见范围推导，待详情接口讨论） | 仅本人（同左） | 任意未删除用户 |
| 创建 user/admin | 禁止 | 禁止 | 允许，沿用现有接口 |
| 修改 nickname、avatar | 仅本人 | 仅本人 | 任意未删除用户 |
| 在资料接口修改 username、email、roleKey | 禁止 | 禁止 | 禁止 |
| 修改自己的密码 | 允许，需要旧密码 | 允许，需要旧密码 | 允许，需要旧密码 |
| 强制下线其他用户（保留原密码） | 禁止 | 禁止 | 仅 user/admin，已通过 sessionVersion 实现 |
| 删除用户 | 禁止 | 禁止 | 仅 user/admin，禁止删除自己和任何超管 |

多角色用户只要包含 `super_admin`，删除与强制下线时就按超管目标保护，不因同时拥有 user/admin 而放行。

- 列表只展示 `id`、`username`、`nickname`、`avatar`；邮箱和角色仅本人或超管查详情可见。
- 密码和 `passwordHash` 永远不返回。
- 所有查询排除软删除记录。重复删除返回 404。
- 软删除继续占用 username/email 唯一值，不开放复用、恢复或物理清理。
- nickname 为空时，展示回退到 username，再回退到 email；头像为空时使用默认头像。

## 3. 为什么不能只判断 edit 权限

权限键回答“操作者可以执行哪类动作”，目标用户 ID 回答“这次动作作用于谁”。

```text
user/admin 修改资料：目标 id 必须等于当前登录用户 userId
super_admin 修改其他人的资料：需要超管角色及 Settings.Users:edit
```

当前 `admin` 预设含 `Settings.Users:edit/delete`，`user` 预设不含列表权限。后续预设应给 user/admin 列表查看权限，移除 admin 的全局修改和删除权限；修改本人资料通过身份与目标归属授权，不依赖全局用户管理权限。

预设是 seed 输入，改源码不会自动改变已有数据库关联。即使尚未同步 seed，后端仍必须通过角色与归属判断阻止旧 admin 权限越权。这里先记录设计，不执行或修改 seed。

## 4. 第一个接口：修改资料

```http
PATCH /api/user/:id
Authorization: Bearer <token>
Content-Type: application/json
```

```json
{
  "nickname": "学习用户",
  "avatar": null
}
```

已确认输入规则：

- `nickname` 可选；非 null 时沿用创建规则，trim 后 2–32 字符。
- `avatar` 可选；非 null 时沿用创建规则，trim 后为最多 2048 字符的 HTTP(S) URL。
- 字段未传：保持原值；明确传 `null`：清空该字段。空字符串校验失败。
- 至少传一个允许修改的字段，拒绝 `{}`。
- 使用 `z.strictObject`；username、email、roleKey、password、passwordHash、id 等未声明字段一律返回 400。
- 返回修改后的安全用户资料：`id`、`username`、`nickname`、`email`、`avatar`、`createdAt`、`updatedAt`，不返回密码或哈希。操作者已限定为本人或超管，因此可以看到该目标邮箱。

### 开发顺序与职责

1. DTO/schema：先定义“允许传什么”，复用现有昵称、头像校验，明确可选与可清空。
2. Controller：继续使用 `@Patch(':id')`，取路径 ID、DTO，以及 `@CurrentUser()` 恢复的身份。
3. Service：判断操作者和目标归属，再检查目标、构造允许写入的数据、调用 Prisma。
4. Prisma：完成数据库读写；不增加只转发调用的 Repository。
5. 全局 Filter/Interceptor：沿用统一异常与响应包装，不在每个方法重复 try/catch。
6. Owner：使用 Apifox 人工验证；确认后再进入下一个接口。

身份必须来自验签后按数据库恢复的 `request.user`，不能接受请求体传入操作者 ID、角色或权限。

### 完整程序化伪代码（已确认并实装）

```ts
updateUserSchema = strictObject({
  nickname: nicknameSchema.nullable().optional(),
  avatar: avatarSchema.nullable().optional(),
}).refine(dto => dto.nickname !== undefined || dto.avatar !== undefined)

UserController.update(id, updateUserDto, currentUser) {
  return userService.update(id, updateUserDto, currentUser)
}

async UserService.update(id, updateUserDto, currentUser) {
  const isSelf = id === currentUser.userId
  const isSuperAdmin = currentUser.roleKeys.includes('super_admin')
  const canManageUsers = currentUser.permissionKeys.includes('Settings.Users:edit')

  if (!isSelf && !(isSuperAdmin && canManageUsers)) {
    throw ForbiddenException('只能修改自己的用户信息')
  }

  const targetUser = await prismaService.user.findFirst({
    where: { id, deletedAt: null },
    select: { id: true },
  })

  if (!targetUser) {
    throw NotFoundException('用户不存在或已删除')
  }

  const data = {}
  if (updateUserDto.nickname !== undefined) {
    data.nickname = updateUserDto.nickname
  }
  if (updateUserDto.avatar !== undefined) {
    data.avatar = updateUserDto.avatar
  }

  return prismaService.user.update({
    where: { id, deletedAt: null },
    data,
    select: {
      id: true,
      username: true,
      nickname: true,
      email: true,
      avatar: true,
      createdAt: true,
      updatedAt: true,
    },
  })
}
```

这是流程伪代码；实装时 data 使用 Prisma 的更新输入类型，DTO 参数统一为 `updateUserDto: UpdateUserDto`，异常补充业务错误码。Service 的字段白名单与 schema 一起防止请求体扩展后意外写入敏感字段。

先检查归属，再查询目标，使普通用户对他人的 ID 统一得到 403，不通过错误差异判断目标是否存在。预查询负责明确的 404 提示；更新的 where 再包含 `deletedAt: null`，避免查询后目标被删除却仍被修改。当前 Prisma 支持在唯一键 id 之外附加该条件。并发删除导致更新匹配失败时，沿用当前全局 Filter 将 Prisma P2025 转为 409“操作所需的数据不存在或已发生变化”，不新增局部错误转换层，也不改全局语义。

资料更新只写一条 User 记录，数据库写入本身具有原子性，无需为此增加手动事务。修改资料不改变 JWT 的 sub，也不签发新 token。

## 5. 后续接口，逐个讨论与实装

| 次序 | 接口 | 职责 |
| --- | --- | --- |
| 2 | `PATCH /api/user/:id/password` | 本人验旧密码后改密，所有角色走相同规则；成功后所有旧 token 失效 |
| 3 | `POST /api/user/:id/force-logout` | 超管使 user/admin 的旧 token 失效，保留密码 |
| 4 | `DELETE /api/user/:id` | 超管软删除 user/admin，保护自己及所有超管 |
| 5 | `GET /api/user`、`GET /api/user/:id` | 分页列表和按身份限制的详情 |

Owner 提议密码操作统一使用 `PATCH /api/user/:id/password`，不再保留 `me/password` 候选。路由一致不代表业务资格一致：路径 id 表示目标，CurrentUser 表示操作者；前端传自己的 ID，后端必须用认证身份判断是否本人，不能相信客户端声明。

### 最新确认：本人改密与超管强制下线分开

- 所有角色改自己的密码都必须验证旧密码，路径 id 必须等于 CurrentUser.userId；超管不能通过该接口修改别人的密码。
- Owner 已选择本轮先做“强制下线”：超管撤销 user/admin 此前签发的 token，保留原 passwordHash；目标仍能用原密码重新登录。
- 此前的“发起重置 → 本人凭证设密”方案暂缓，不创建重置凭证、邮件服务或确认重置接口。
- 强制下线不是禁用账号，也不解决密码泄露；不能在界面或接口文档中称作“重置密码”。

完整伪代码、会话版本与跨子域登录设计见 [账号权限与会话设计](./07_账号权限与会话_设计.md)。本人改密和强制下线已按其中的 sessionVersion 方案实装；跨子域 Cookie 仍只保留设计，不在本轮接线。

JWT 现在携带签发时的 `sessionVersion`；身份恢复从数据库读取当前版本并比较，不一致返回 `AUTH.Session:revoked`。本人改密与强制下线都原子递增版本，前者同时更新密码哈希，后者保留原密码。旧格式 token 因缺少版本字段会被判定为无效，需要重新登录。

## 7. PATCH 空值与三端 Schema 复用（历史决策与后续方案）

### 为什么保留 !== undefined

| 请求中的 avatar | 含义 | !== undefined | if (avatar) |
| --- | --- | --- | --- |
| 未传 | 保持原值 | 不写入 | 不写入 |
| null | 清空头像 | 写入 null | 跳过，无法清空 |
| 合法 URL | 修改头像 | 写入 URL | 写入 URL |

当前头像 schema 已排除空字符串，但明确允许 null。真假值判断会丢失清空意图；判断不是为了防止异常，而是实现 PATCH 的输入语义。nickname 同理。

### 本地复用与跨端契约

nicknameSchema/avatarSchema 已在创建、修改两个输入中复用：规则改一处，两种操作保持一致。它们是同文件内的常量，不是增加了一个服务层。optional/nullable 应由各操作决定，基础字段 schema 不提前绑定可选语义。

当 web/admin 使用同一接口时，建议直接共享完整请求 schema 和由它推导的 DTO，而不只共享零散正则或长度常量。

```text
packages/common/src/
  api/                         现有统一响应与错误契约
  user/
    user.schema.ts             用户字段、创建和资料修改请求 schema + DTO
  auth/
    auth.schema.ts             登录请求 schema + LoginDto（后续单独迁移）

apps/server/src/user/dto/user.schema.ts
  从 @rs/common/user 重新导出迁移后的 schema/DTO
  列表等未确定契约暂留本模块

apps/admin、apps/web
  从 @rs/common/user 导入 updateUserSchema 和 UpdateUserDto
```

本方案使用现有 common 包并按业务域组织，不新增包，也不把用户专属规则混进通用 api 目录。采用显式子路径导出 `@rs/common/user`，避免导入现有响应工具时顺带加载用户校验模块。

跨端消费方式：

```ts
import { updateUserSchema, type UpdateUserDto } from '@rs/common/user'

const result = updateUserSchema.safeParse(formPayload)
if (result.success) {
  const updateUserDto: UpdateUserDto = result.data
  await api.patch(`/user/${userId}`, updateUserDto)
}
```

这是消费示意，不代表本轮已对接前端。编辑表单应先构造 PATCH payload：未改的字段不发送，点击清空才传 null；不能把含未改字段的整个表单对象直接当作局部更新。前端可在本地扩展确认密码、表单状态等校验，但这些额外字段不能发给 strictObject API。

- 共享 schema 负责字段格式、规范化、允许字段及 DTO；后端仍必须执行相同校验，不能信任前端已校验。
- Service 保留数据库唯一性、操作者授权、目标归属及软删除规则。这些不迁入共享包。
- 有转换时，前端原始输入使用 `z.input<typeof schema>`，校验后的请求使用 `z.output<typeof schema>`；现有 z.infer 等价于 output。
- 不直接从 Prisma 模型生成整个请求 schema：数据库允许的字段和一次操作允许修改的字段并不相同。
- common 需要新增 zod 运行依赖，packages/common/package.json 增加 user 子路径导出，锁文件同步；server 保留模块内转出口以减少调用方变更。
- 当前 common 输出 ESM，server 输出 CommonJS。现有运行方式已消费 common，但 Node >=20 并非所有小版本都具有相同的 require(ESM) 支持；迁移需沿用并确认项目实际兼容方式，不在本轮顺手调整全仓模块格式或升级依赖。
- 构建仍沿用先构建 common 的既有流程；直接单独启动 server 时由 Owner 确保共享产物已更新。
- 回退：恢复模块内 schema 与导入，撤回 common 的新增导出、依赖与锁文件改动；不影响数据库和 HTTP 请求形状。

Owner 在删除接口阶段选择先保留本地 Schema，随后提出错误码、用户 Schema 与业务请求/响应类型统一共享的新方向。当前迁移设计见 [三端共享契约](./06_三端共享契约_设计.md)，待确认具体范围后逐文件迁移；不影响已实现的资料修改与删除规则。

## 8. 下一个用例：软删除用户（伪代码已确认并实装）

### 输入、权限与成功结果

- `DELETE /api/user/:id`：路径 ID 沿用 userIdSchema，无请求体 DTO。
- 操作者必须同时具有 super_admin 角色和 Settings.Users:delete；旧 admin 即使有 delete 权限也拒绝。
- 禁止删除自己；目标只允许 user/admin，包含 super_admin 的多角色用户也禁止删除。
- 不存在或已删除返回 404；已确认目标在实际写入前发生变化，返回 409。
- 成功返回 `{ id, deletedAt }`，HTTP 200，由全局响应拦截器包装；不返回邮箱、密码或哈希。
- 只更新 deletedAt，保留 UserRole 及 username/email 唯一值。下次身份恢复拒绝该用户的旧 token。

### 开发顺序

1. Controller.remove：接收路径 ID 和 CurrentUser，不接收操作者信息或角色请求字段。
2. Service.remove：先授权，再查目标及角色，检查自删/超管保护，完成条件更新。
3. error-codes：增加删除越权与受保护目标的业务码；不存在复用 USER_NOT_FOUND。
4. 更新模块 README 与人工操作入口，不增加 Repository、数据迁移或逐方法 ORM 错误映射。

```ts
UserController.remove(id, currentUser) {
  return userService.remove(id, currentUser)
}

async UserService.remove(id, currentUser) {
  const isSuperAdmin = currentUser.roleKeys.includes('super_admin')
  const canDelete = currentUser.permissionKeys.includes('Settings.Users:delete')

  if (!isSuperAdmin || !canDelete) {
    throw ForbiddenException('仅超级管理员可删除用户')
  }
  if (id === currentUser.userId) {
    throw ForbiddenException('不能删除自己')
  }

  const targetUser = await prismaService.user.findFirst({
    where: { id, deletedAt: null },
    select: {
      id: true,
      roles: { select: { role: { select: { key: true } } } },
    },
  })
  if (!targetUser) {
    throw NotFoundException('用户不存在或已删除')
  }

  const roleKeys = targetUser.roles.map(assignment => assignment.role.key)
  if (roleKeys.includes('super_admin')) {
    throw ForbiddenException('不能删除超级管理员')
  }
  if (!roleKeys.some(roleKey => roleKey === 'user' || roleKey === 'admin')) {
    throw ForbiddenException('仅允许删除普通用户或管理员')
  }

  const deletedAt = new Date()
  const result = await prismaService.user.updateMany({
    where: {
      id,
      deletedAt: null,
      roles: {
        none: { role: { key: 'super_admin' } },
        some: { role: { key: { in: ['user', 'admin'] } } },
      },
    },
    data: { deletedAt },
  })
  if (result.count === 0) {
    throw ConflictException('用户状态已变化，请刷新后重试')
  }

  return { id, deletedAt }
}
```

updateMany 在此并非批量删除：id 为主键，最多更新一行；它允许通过影响行数判断条件是否仍成立，避免为了处理目标状态变化写局部 Prisma catch。请求开始时已删除的用户返回 404；两个并发删除请求都通过预查询时，先完成者成功，后完成者返回 409。

条件更新在语句读取到的数据库状态上重新判断删除标记和角色。当前没有在线改角色接口；未来增加角色分配时，需要让角色修改和用户删除采用共同的事务/锁策略，不能只靠这段预查询就宣称跨表并发绝对安全。当前同步授予角色与删除的强一致治理不属于本轮。

### 人工验证入口（实装后由 Owner 执行）

| 场景 | 预期 |
| --- | --- |
| 未登录 | 401 |
| user/admin 删除自己或他人 | 403，用户记录不变 |
| 超管删除自己或另一个超管（包含多角色超管） | 403 |
