## 2. B2 · CORS 白名单

### 2.1 现状（已核实）

`apps/server/src/main.ts`：

```ts
// ⚠️ 当前允许任意来源跨域，便于本地前端联调。上线前要收紧为白名单
// （`origin: [web, admin 的域名]`），否则任何站点都能直接调这套接口
app.enableCors()
```

不传参等价于 `Access-Control-Allow-Origin: *` —— **任何站点都能读到本接口的响应**。
配合"公开读无发布态"（B1），等于"任何人可跨站批量抓取全部简历"。

### 2.2 设计

新增环境变量 **`CORS_ORIGINS`**（逗号分隔的完整 origin，含协议与端口）：

| 环境 | 默认值 | 缺失时 |
| --- | --- | --- |
| `development` | `http://localhost:4041,http://localhost:4047` | 用默认值 |
| `test` | 空数组 | 允许为空（隔离测试用 curl，不带 `Origin`，CORS 根本不生效） |
| `production` | **无默认值** | **启动失败并指名道姓** |

`main.ts`：

```ts
app.enableCors({
  origin: corsOrigins,          // string[]，绝不出现 '*'（校验阶段就拒绝）
  methods: ['GET', 'POST', 'PATCH', 'PUT', 'DELETE', 'OPTIONS'],
  allowedHeaders: ['Content-Type', 'Authorization', 'x-request-id'],
  exposedHeaders: ['x-request-id'],   // ← 见下
  maxAge: 600,
})
```

**三个要点：**

1. **`exposedHeaders: ['x-request-id']` 不是可选项**。浏览器**默认不允许**前端脚本读取
   非"简单响应头"的字段 —— `x-request-id` 属于后者。不加这一行，DAO-044 做的
   "四处 ID 一致"在浏览器里就只有三处可见（响应头读不到），前端也就无法把 traceId 展示给用户。
2. **不需要 `credentials: true`**（已核实）：前端把 token 存在 `useCookie`，
   但调用接口时走 `Authorization: Bearer`，**服务端没有任何 cookie 解析**
   （`grep cookie apps/server/src/auth/` 为空）。跨域 cookie 才需要 `credentials`。
   ⚠️ 若将来改成跨域 cookie 鉴权，必须同时加 `credentials: true` 且**不能用 `*`** —— 这条写进注释。
3. **服务端渲染不受影响**：Nuxt 的 SSR 请求由服务端进程发起，不带 `Origin` 请求头，
   CORS 不参与。所以白名单配错只会影响**浏览器端**的调用 —— 症状明确、定位快。

### 2.3 与 `env.validation.ts` 的一致性

该文件的做法是"配错就启动失败"，且已有先例（`JWT_SECRET` 无兜底默认值，见 `auth.module.ts` 注释）。
`CORS_ORIGINS` 沿用同一条判据：**生产环境不允许"忘了配就放行"**。
校验规则：按逗号切分 → 去空白 → 去重 → 每项须匹配 `^https?://[A-Za-z0-9.-]+(:\d+)?$`；
出现 `*` 直接报错（`*` 正是本轮要消灭的东西）。

### 2.4 验收

- `curl -i -H 'Origin: http://localhost:4041'` → 响应含 `Access-Control-Allow-Origin: http://localhost:4041`
- `curl -i -H 'Origin: https://evil.example'` → **不含** `Access-Control-Allow-Origin`
- 预检：`curl -i -X OPTIONS -H 'Origin: <白名单>' -H 'Access-Control-Request-Method: PATCH'` → 204 + 允许
- `Access-Control-Expose-Headers` 含 `x-request-id`
- 生产环境缺 `CORS_ORIGINS` → 启动失败，错误信息点名该变量
- 单测：解析函数（逗号/空白/去重/非法项/`*` 拒绝）

## 3. B3 · 登录限流

### 3.1 依赖变更（需 Owner 批准）

| 依赖 | 版本 | 说明 |
| --- | --- | --- |
| `@nestjs/throttler` | `^6.7.1` | **官方**集成；peer 已支持 `@nestjs/core@^12.0.0`（已核实） |

按 `AGENTS.md` §2，新增依赖需先说明用途与回滚：用途是登录接口的请求频率限制；
回滚是移除该依赖并还原 `auth.module.ts` / `auth.controller.ts`（无数据变更）。

### 3.2 现状（已核实）

`auth.service.login()`：`findFirst` 查用户 → `verifyPassword`（bcrypt，**CPU 密集**）→ 签发 token。
**没有任何节流**：攻击者可无限次尝试，每次都在服务端跑一次密码哈希 ——
既是密码爆破通道，也是一条廉价的 CPU 打满路径。

### 3.3 设计

- `ThrottlerModule.forRootAsync` 挂在 `AppModule`，参数来自 env：
  `LOGIN_THROTTLE_LIMIT`（默认 `5`）、`LOGIN_THROTTLE_TTL`（默认 `60000`，**单位毫秒**）。
- **只作用于登录路由**：`@UseGuards(ThrottlerGuard)` + `@Throttle(...)` 加在 `AuthController` 的
  `login` 方法上（或整个 `AuthController`，但**不含** `@Public()` 的公开读接口）。
  - 为什么不全局：全局限制会顺带节流"公开简历页读取"和前端轮询，那是另一个产品决策
    （防 DoS），与"防爆破"不是同一件事。**本轮只收 auth 面**。
- **429 带稳定 errorCode**：throttler 默认抛 `ThrottlerException`（429），
  经现有 `ApiExceptionFilter` 会得到没有 `errorCode` 的响应体。需要覆写
  `throwThrottlingException`，抛带 `API_ERROR_CODES.AUTH_LOGIN_THROTTLED`（新增码）的
  `HttpException`，前端才能按码显示"操作太频繁，请稍后再试"。
- **保护点在守卫阶段**：throttler 作为 Guard 在 Controller 之前执行，
  因此**被限流的请求不会跑到 `verifyPassword`** —— CPU 保护成立。

### 3.4 已知限制（必须写进注释与文档）

1. **内存存储 → 只对单实例有效**。本仓 `compose.yaml` 与依赖里**都没有 Redis**（已核实），
   多实例部署时每个实例各有一份计数，实际额度被放大。要跨实例需接 Redis storage ——
   属于"上多实例"时的事，本轮不做但留明确注记。
2. **按 IP 计数**，所以：
   - 同一 NAT / 办公室出口共享额度；
   - 换 IP 即可绕过；
   - **反向代理后 `req.ip` 是代理地址**，需 `app.set('trust proxy', ...)` 才能拿到真实 IP。
     本轮不引入 `TRUST_PROXY`（属基础设施配置），但**必须在文档里写明**：
     上线到反向代理后，这条限流会退化为"全站共享一份额度"。
3. **不防"撞库式低频爆破"**（每分钟 4 次、持续数天）—— 那需要账号锁定或异常检测，
   属产品决策，本轮不做。

### 3.5 验收

- 连续 6 次错误密码 → 第 6 次 `429` + `AUTH.Login:throttled`；前 5 次仍是 `401`
- 等 TTL 过后可再次尝试（`401`）
- 正确密码在额度内 → `200`（限流不误伤正常登录）
- 被限流时**服务端没有 `verifyPassword` 的耗时**（日志 `responseTime` 明显更小）
- 单测：guard 行为（第 N+1 次抛 429 且带 errorCode）

## 4. B1 · 发布态与公开读过滤（最重）

### 4.1 现状（已核实）

- `resume.service.ts` 的 `publishedResume()` 是**两个公开读的唯一收口点**：

  ```ts
  private publishedResume(extra: Prisma.ResumeWhereInput): Prisma.ResumeWhereInput {
    return { ...extra, workspace: { user: { deletedAt: null } } }
  }
  ```

- 代码注释已自带路标：**"引入发布态时，这里就是加过滤条件的地方"**。
- `Resume.id` 是 `autoincrement()` → 顺序可猜；`schema.prisma` 里**没有**任何发布态字段。
- `assertEditable(currentUser)` 要求 `Resume.Sections:edit` —— `setDefault` 已在用这套授权。

### 4.2 决策 1：字段形态

| 方案 | 形状 | 优点 | 代价 |
| --- | --- | --- | --- |
| A | `isPublished Boolean @default(false)` | 直观，过滤写 `isPublished: true` | 没有"何时发布"；以后要补时间就再迁移一次 |
| **B（推荐）** | `publishedAt DateTime?` | 一个字段同时表达"是否发布"**与**"何时发布"；未发布 = `null` | 过滤写 `publishedAt: { not: null }` |
| C | `publicToken String? @unique` | 真正防枚举 | 新增 URL 形态，前端、分享、旧链接全变 |

**推荐 B**：一个字段干两件事，且"发布于何时"以后一定要用（分享页/首页显示）。
计划文档写的是 `isPublished`，这里建议调整为 `publishedAt` —— 语义严格更强，不是缩水。

**C 不在本轮**：它要改 URL 形态（`/resume/:token`）、前端全部取数、以及"分享"入口，
与 C5 同源，单独一轮做更划算。

### 4.3 决策 2：存量数据回填 ← **需要你拍板**

| 方案 | 迁移内容 | 后果 |
| --- | --- | --- |
| **B-i（推荐）** | 只加列，不回填 | 上线后**所有简历立刻不可见**（首页空态、分享链接 404）。因此**必须同轮交付"发布"入口**，否则等于故障 |
| B-ii | `publishedAt = createdAt` 全量回填 | 现有演示行为不变；但"半成品对外可见"在存量数据上**继续存在** |
| B-iii | 只回填 `is_default = true` 的 | 折中：首页那份继续可见，其余需显式发布 |

**AI 推荐 B-i**，理由：
1. 这是**上线前**项目，没有真实生产数据，没有"回填保平滑"的必要；
2. B-i **强制发布入口必须同轮交付**，反而保证这条链路被真的走一遍；
   B-ii 会让新功能"看起来没用过"，风险被推迟到上线那天；
3. 语义最干净：`publishedAt IS NULL` 一律不可见，没有"某些历史数据是例外"的暗规则。

> **决策记录（Owner 2026-10-17）：选 B-iii（只回填 `is_default = true` 的那份）。**
> 取舍是「演示不中断」优先于「语义最干净」。为了让这个选择**不变成暗规则**，
> 下面两条后果必须显式落地 —— 否则它们会以"奇怪的 bug"形式找上门。

**B-iii 的两条必然后果（实现时必须处理）**

| # | 后果 | 处理方式 |
| --- | --- | --- |
| 1 | 迁移后**非默认的简历一律不可见** —— 首页照常，但其他简历的分享链接变 404 | 列表页要能一眼看出「未发布」，不能让人以为简历丢了 |
| 2 | `setDefault` 若允许把**未发布**的简历设为默认，首页就会指向一份读不到的简历 | `setDefault` **校验目标必须已发布**；错误文案要指路：「请先发布该简历，再设为默认展示」 |

→ 由此产生一条**用户可见的操作顺序：先发布，再设默认**。
这条要落进列表页的交互与文案，而不只是写在代码注释里。

### 4.4 决策 3：发布 / 取消发布接口

```
PATCH /api/resume/:id/publish     body: { published: boolean }     → 返回更新后的完整列表
```

照 `PATCH /api/resume/:id/default` 的形状（同控制器、同 `resumePrimaryKeySchema`、
同 `@CurrentUser()` + `@TraceId()`），一个端点做两件事且**幂等**（重复发布不报错）。

- 授权：复用 `assertEditable`（与 `setDefault` 一致）
- 写入：`publishedAt = published ? new Date() : null`
- **未发布时公开读返回 404 而非 403** —— 不泄露"存在但未发布"这一事实
- **`isDefault` 与发布态的一致性**：设为默认时**校验目标必须已发布**，否则首页会指向一份
  读不到的简历。这条校验放在 `setDefault` 里（强一致，比"首页碰巧空态"更好排查）。
- **审计**：`setDefault` 现在会写审计。发布/取消发布**也是值得审计的动作**，但给
  `AUDIT_ACTIONS` 加枚举值会碰 `packages/common/src/api/constants.ts` 与
  `audit-labels.ts` —— **正是另一窗口刚改过的文件**。建议：**审计这一项等他们的分支合入后补**，
  本轮先只带 `requestId` 入日志（日志已能做关联）。
