关联：[核心设计](./03_简历系统_核心设计.md)、[DAO-028](../../dao/tasks/DAO-028-个人能力字段与内容结构.md)。本文先提供业务讨论模板与推荐方向；字段、表结构、API 和伪代码须逐步确认，当前不代表已实现。

## 1. 一条完整 Task 如何推进

一个 Task 对应一个用户可验收的结果，可以跨多轮讨论和多个小提交；后端与前端是同一任务的不同阶段。

| 阶段 | 本阶段产物 | 通过依据 |
| --- | --- | --- |
| 分析与范围 | 用户故事、样本、目标/非目标、依赖、验收故事、任务卡 | Owner 认可业务结果与边界 |
| 设计 | 字段语义、表关系/约束、交互状态、接口契约、程序化伪代码、测试计划和回滚方案 | 未决项不会影响当前用例；Owner 确认方案 |
| Issue 与分支 | 已确认的实现范围、文档链接、验收入口、带 Issue 的短分支 | 工作区旧改动有明确归属；实现不直接落 main |
| 数据与后端 | 审查迁移 SQL、共享校验/类型、Service/Controller、接口文档 | 数据动作已说明影响并获授权；验证权限、异常和并发 |
| 前端与联调 | 编辑器/展示组件、请求与缓存、加载/空态/失败态、保存反馈 | 数据从 UI 到接口到数据库再回 UI 闭环成立 |
| 验证与 Review | 有意义的自动测试、质量门、关键人工路径、改动自审 | 机器证据与 Owner 意图验收齐全；失败已修复或记录 |
| 交付与收口 | 文档/Issue 回填、提交、分支推送、PR 或明确集成方式 | 验证通过；需要授权的动作（发布 / 数据破坏性动作）已获授权；进入目标分支后按任务规范关闭 |

测试计划在分析时开始，不等接口全部写完。优先验证字段校验、权限、并发、保存失败等真实规则；不为可逆小改或实现细节堆模板测试。新增测试依赖需说明用途再确认。

文档随决策和实现更新；提交前才集中整理也不能遗漏中途决定。**推送 `dev` / 开发分支是自主动作，不需要逐次授权；`main` 与发版才需要 Owner 授权**（闸门设在 `main` / 发版，见 [`AGENTS.md`](../../AGENTS.md) §4）。发布需要环境/迁移顺序、兼容窗口、回退与可观测性方案，不把日常 Task 等同生产部署。

## 2. 现状与最小依赖

当前 `ResumeContent.skills[]` 为 `{ group, items: string[] }`，`profile.radar[]` 为 `{ label, value }`；后者有类型与编辑字段但未真正完整展示。已有三档是 minimal/standard/pro，内容与配置保存在本地。

服务器目前没有简历表。因此“个人能力落数据库”至少依赖简历归属、当前草稿、模块实例定位与草稿读取/保存。先设计所需最小基础，再确认并入本 Task 还是作为前置任务；无需提前创建发布、分享、历史版本六张完整业务表。

本轮仅做讨论稿，不改 Prisma、API、前端、依赖或配置。

## 3. 字段职责建议

推荐固定类型键 `capabilities`、用户标题“个人能力”；具体技术放技能条目。允许同类型多个模块实例，例如把“AI Agent 能力”单独展示；同实例也可以按前端、全栈、Agent 分组。

| 层级 | 内容字段候选 | 示例与理由 |
| --- | --- | --- |
| 模块实例 | 公共 id/type/title/description + data | 类型稳定，实例独立，标题可以定制 |
| data.groups[] | id/title/summary?/items[] | 前端工程、全栈开发、AI Agent；数组顺序是组内阅读顺序 |
| 技能条目 items[] | id/name/description，可选 evidenceLinks[] | Vue/TypeScript，或“实现工具调用与评估”；文字主导，不强制打分 |
| evidenceLinks[] | id/label/url | 作品或开源地址；列表也支持排序，先不引入跨模块项目引用 |
| data.dimensions[] | id/label/score?/description? | 系统设计/工程化/Agent 编排；score 缺失为未评分，不是 0 |
| data.ratingScale | min/max/basis? | 模块统一量尺与用户填写的自评依据；不得把缺少分数当成 0 |

量尺推荐采用模块内统一的自评规则；是否固定 0～100，或允许选择 0～5/10/100，见 §9 的新讨论。文字技能不自动转换评分，维度与技能不要求一一对应。重复名称可以存在，但 ID 必须满足文档身份规则；长度、条目数量及链接协议白名单在契约设计时逐项定稿。

旧 skills.group → groups.title，旧字符串 item → items.name；旧 radar.label/value → dimensions.label/score。旧数据无描述/证据时保留缺省；原始 localStorage 不自动删除，导入失败要能重试。

## 4. 内容与展示分开

内容保存能力、描述、证据、自评分数；模块编排保存实例显隐/顺序/栏位。模块视图配置通过实例 ID 放在 display 的覆盖区，候选为 view、dimensionIds、showScores、showEvidence；不保存 ECharts option，不另存图表分数。

Owner 已明确需要评分与图表，首个业务闭环的设计需纳入图表视图；具体首期支持 radar/bar 哪些形式以及实现依赖仍待确认。文字/标签保留为详情和降级视图。图表引用相同 dimensions，选择和顺序存 dimensionIds；服务端检查引用存在、无重复，删除维度同时处理引用。

不同风格消费同一能力内容，未使用字段继续保留；无评分按文字降级，不能补 0。移动端要能读到标签与数值，并提供图表的可访问文本。图表最低维度数、部分未评分、全未评分及超长标签的行为在交互稿中明确。

列表的内容顺序直接用数组表达，不为同一列表另存 sortIndex；模块级顺序沿用核心设计的编排权威。公开响应的过滤规则属于后续公开读取设计，本 Task 不能假称已具备发布过滤能力。

## 5. 编辑与接口设计待展开

先围绕当前简历的个人能力闭环，而非一次实现所有简历列表、版本发布接口。

- 编辑：新增/改名/删除能力组与条目、拖拽排序、评分为空与 0 的区别、描述/证据编辑；删除需考虑撤销或确认。
- 数据流：完整读取当前草稿，UI 编辑目标模块；保存粒度、校验、事务和版本条件统一确定，整份写入与模块更新择一先实现，避免双保存入口相互覆盖。
- 权限：服务端验证登录身份、简历所有权和编辑资格；不因处于 admin 就能访问任意简历。
- 并发：保存携带 expectedRevision，条件更新与 revision 增量必须原子；校验失败或冲突不覆盖本地输入，切换简历时旧请求不能写回新简历状态。
- 状态：加载、空内容、未保存、保存中、已保存、失败、冲突；2～3 秒防抖、主动保存、离开提醒、恢复策略需在接口之前确定。
- 契约：请求/响应 Schema、错误码、认证、大小上限、OpenAPI 示例和 Apifox 验收用例同步；表名或 Prisma 类型不直接成为前端依赖。

## 9. 自定义分组、条目与评分：推荐结构

### 9.1 用户自定义内容，程序固定字段职责

Owner 的“capability + 自定义二级 key + string[]”可以表达简单文字，但不能充分承接后续改名、条目评分、说明、证据、排序和差异对齐。推荐固定模块类型使用 `capabilities`（单数 `capability` 也可统一选用；现在仍是命名候选），分组用对象数组表达。

例如，不把 frontend/aiAgent/sales 写成固定业务字段，而让用户编辑 groups[].title。稳定 id 用于引用和改名；标题是显示内容，不承担主键职责。只有明确需要外部导入映射时，才增加可选 key/slug，并约定作用域与改名规则；普通用户无须理解或填写技术 key。

下面是仅用于说明字段职责的 JSON 样本；ID 是占位示例，score 为 null 表示 Owner 尚未评分。所有标签和概括文案均可编辑，摘要是待 Owner 审定的建议文案。

```json
{
  "id": "section-capabilities-1",
  "type": "capabilities",
  "title": "专业技能",
  "description": "",
  "data": {
    "groups": [
      {
        "id": "group-agent",
        "title": "AI Agent 开发",
        "summary": "多 Agent 工作流、流式交互与协同开发",
        "items": [
          {
            "id": "item-agent-workflow",
            "name": "Agent 工作流",
            "description": "从 0 到 1 搭建多 Agent 系统，理解规划、执行、验证、反馈闭环等核心机制",
            "evidenceLinks": []
          }
        ]
      }
    ],
    "ratingScale": {
      "min": 0,
      "max": 100,
      "basis": ""
    },
    "dimensions": [
      {
        "id": "dimension-agent",
        "label": "AI Agent 开发",
        "groupId": "group-agent",
        "score": null,
        "description": ""
      }
    ]
  }
}
```

能力条目的 name、description 可为空值组合中的具体规则后续定稿；纯文字条目可只填 name。旧 string[] 不要求按冒号自动拆分：原字符串先完整保留，只有结构化导入确认后再拆为名称与说明。Owner 这次提供的 Markdown 有明确名称/描述，可人工确认对应映射。

### 9.2 自评维度独立，允许关联分组

推荐把评分集中存入 dimensions，每个维度都有用户可编辑的 label/description/score；可选 groupId 关联一个能力组，点击图表维度能定位到对应详情。没有关联时也能建立“沟通”“领导力”等跨组能力维度。

你的六组可以先对应六个概览维度，详情仍是三十条文字；不为每条技术都强制评分，也不同时在 group 和 dimension 存一份相同分数。某个组以后需要详细技术评分，可以显式新增维度并关联该组，而不是自动从技能条目推算。

评分量尺推荐模块统一，先提供 0～5、0～10、0～100 的可选预设，默认 0～100；这项仍待 Owner 确认。用户可自定义维度、分值和评价依据，但同一个图表共享量尺。切换量尺须显式选择换算或清空，不能只改 max 后让旧分数失效；换算精度另定。分值是自评，不是客观成绩、百分位或岗位匹配率，也不自动算总分或排名。

score 缺省或 null 都归一化为未评分；0 是有效评分。图表选中未评分维度时不伪造 0，提示编辑者补充评分，访客视图降级到列表并标注未评分。雷达至少需要三个已评分维度，优先展示少量可读维度；维度少、标签长或手机空间不足时使用条状/文字视图。雷达与条状图只引用 dimensionIds，不保存第二套分数或 ECharts option。

### 9.3 把信息分为概览与详情

| 展示层 | 默认候选 | 数据来源 |
| --- | --- | --- |
| 概览 | 雷达或条状图，标签与自评分数 | 用户选定的 dimensions |
| 分组摘要 | 组标题、用户填写的一句话 summary、少量技能名称 | groups 与 items.name |
| 展开详情 | 原始完整说明与可选证据 | items.description/evidenceLinks |
| PDF/打印 | 全量文字为默认候选，图表可选；适配分页 | 同一份内容，独立的导出显示策略 |

图表帮助扫读，但单独的分数无法解释能力，因此保留简短标签、摘要与按需展开详情。折叠只是当前视图状态，不是权限隐藏；“展开详情”的内容已经对访客公开。真正不公开的内容需要服务端过滤，两者不能混成一个 hidden 开关。默认展开哪些组、展示几个条目及是否允许访客切图表形式放在展示配置中，不修改作者内容。

产品中的 Vue/Agent 等名称只出现在用户内容和可选模板里；运营、销售、设计等岗位同样可以填写“客户沟通”“活动策划”“视觉表达”。模板负责提供初始内容，不对组名写业务枚举。

## 10. 先确定整体简历骨架，再实现个人能力

Owner 指出整体简历字段应先大致设计，以支撑完整读取和真实接口联调；采用这个推进方向。先定“外层契约 + 现有模块承接”，随后逐模块完善，不把三十条技能孤立保存为账号属性。

### 10.1 简历身份与文档分开

| 层级 | 候选内容 | 职责 |
| --- | --- | --- |
| 简历元信息 | id、owner（经空间归属）、name、locale、targetRole?、createdAt/updatedAt | 区分多份简历及其所属用户；内部投递信息不进入公开内容 |
| 草稿状态 | resumeId、revision、updatedBy、updatedAt | revision 是保存并发令牌，不是发布版本号 |
| 完整文档 | schemaVersion、content、display | 原子保存、展示、复制和以后冻结版本 |
| content | sections[]、footer | 模块实例 + 独立页尾 |
| display | brand/layout/sections/options/theme/background/style | 保留现有显示能力，实例编排与内容分离 |

建议形状（只列骨架，省略的 display 字段按核心设计与现有配置承接）：

```text
ResumeDraftResponse
  resume: { id, name, locale }
  revision
  updatedAt
  document
    schemaVersion
    content
      sections[]: { id, type, title, description?, icon?, data }
      footer: { note? }
    display
      brand / layout / options / theme / background / style
      sections: { order, slot, hidden, overrides }
```

data 按 type 选择严格的运行时 Schema，不能用任意对象绕过服务端校验；用户改的是标题和内容，而不是执行代码或任意数据库字段。模块类型新增由程序注册支持，用户可从支持的类型中新增实例。个人能力内部新增组/条目不需要新增程序类型。

### 10.2 第一版需要承接的模块

| 固定类型候选 | data 的概要 | 旧内容映射 |
| --- | --- | --- |
| profile | name/headline/summary/avatarText/availability、hero、infoItems、links、interests、stats、gallery | profile 全部既有字段；contact 转 Info；radar 移入能力模块 |
| highlights | items[]：id/title/description | highlights[] |
| education | items[]：id/school/date/degree/major | education[]；旧 period 进入自定义日期模式 |
| experience | items[]：id/company/date/role/domain/overview/achievements/tech | experience[]；成果与技术列表可排序 |
| projects | items[]：id/name/date/role/overview/features/highlights/tech | projects[]；允许不同标题的多实例 |
| capabilities | groups/items、ratingScale、dimensions | skills[] + profile.radar[] |
| evaluations | items[]：id/text | evaluations[] |
| 独立 footer | note | footerNote，不依赖自我评价显隐 |

表中是字段范围清单，必填/可空、默认值、数组上限、URL/日期校验与转换规则尚未定稿；不得直接据此生成 Prisma 或最终 API 类型。完整保存接口实施前，所有能写入文档的模块都必须具备服务端校验与旧字段映射，不能只校验 capabilities 后静默丢弃其他内容。新增通用模块后续扩充 schemaVersion 与注册表。

### 10.3 最小存储与接口边界

与核心六表候选保持一致，推荐先设计空间、简历、当前草稿三类关系：空间归属用户，简历归属空间，草稿以 resumeId 唯一关联简历。若另选只建 resumes + drafts 的两表起步，则需明确 ownerId 与以后空间归属的迁移，不在本轮静默改变总设计。发布版本/公开入口/分享表继续保留候选，首次能力闭环无需一并实现。

没有单独的“前端能力”“AI 能力”列，也无需每个能力分组建表；个人能力与其他模块一起进入经过 Schema 校验的 document JSONB。JSONB 存储不豁免所有权、ID 引用、文档大小与并发约束。

推荐首期只使用一种保存协议：整体读草稿、按 expectedRevision 原子保存完整文档；前端编辑能力模块时在当前文档中更新对应实例，再提交完整文档。约束更新必须在一次条件更新中比较 revision 并递增，不能先查询再无条件写入。服务端合并单模块更新可以后续讨论，第一期不同时实现两套保存协议。

创建/初始化简历、读取当前草稿、保存当前草稿是最小用例；接口路径与权限在下一步设计。演示可以把已有内容导入一份草稿，用真实读取/保存链路逐模块迭代；不需要先实现其他模块的新编辑器、简历管理列表、发布、分享或所有历史版本功能。公开展示读取仍要另行设计，不能直接把作者草稿接口暴露给访客。

这部分是推荐的依赖范围，不是 schema 或迁移授权。字段审定后说明建表、初始导入、失败恢复与回滚，再确认它们纳入 DAO-028 还是形成明确前置任务；无论如何不省略持久化依赖，也不扩成全平台实现。

## 12. 实现计划与程序化流程（DAO-028）

Owner 本轮确认按完整流程开发，并补充确认：web 登录接真实后端；仅 admin/super_admin 编辑本人草稿，普通用户暂只读；admin 管理页不纳入本轮。

本次新增后端 resume 业务目录和 common/resume 契约目录，分别隔离持久化业务与框架无关校验；web 的草稿页放在已有 public-resume layer 内。回滚为撤销本分支业务代码，未应用的迁移不进入数据库；已应用后须先导出新草稿，再停用接口并按备份恢复或单独逆向迁移，禁止随手 reset 用户库。既有本地演示页保留，作者草稿通过 /resume/draft 独立访问。

### 最小三表

- ResumeWorkspace：userId 主键且关联 User，一用户一个空间；本轮不建立默认公开指针。
- Resume：id、workspaceUserId、name（1～80）、locale（1～20）、createdAt/updatedAt、deletedAt；按归属索引。未实现管理列表与删除入口。
- ResumeDraft：resumeId 主键并关联 Resume、schemaVersion、document JSONB、revision（正整数，初始 1）、updatedBy、updatedAt。updatedBy 关联 User；schemaVersion 必须与 document 内版本一致。文档大小上限 100 KiB；外键禁止悬空，revision 由服务端生成。

本轮不新增默认发布、历史版本和分享表，不更新用户角色或 seed。创建资格同时满足编辑角色和 Resume.Sections:edit，访问再检查简历归属；超管也不代编他人草稿。所有写入再次检查用户未软删除。

### 第一批接口

| 方法与路径（/api 前缀） | 输入 | 结果与失败 |
| --- | --- | --- |
| POST /resume | name、locale、document | 201 安全元信息与草稿；400 校验、401 认证、403 资格 |
| GET /resume/:id/draft | 路径 id | 200 本人完整草稿；他人/删除/不存在统一 404 |
| PUT /resume/:id/draft | expectedRevision、document | 200 已保存文档与新 revision；409 Resume.Draft:conflict，不自动重试覆盖 |

不会在 GET 中隐式创建数据。用户首次进入草稿页主动点击“创建”，前端从现有示例生成完整模块实例；可选导入本机旧 localStorage，转换失败保留原始数据。本轮输入的六组/三十条能力提供可选演示内容，评分保持未填写。

### 严格校验

第一版支持 profile/highlights/education/experience/projects/capabilities/evaluations 的区分联合，所有 data 字段白名单校验。模块最多 30，能力组最多 20、每组条目最多 50、维度最多 20、每条证据最多 5；字符串按名称/摘要/描述/URL分配上限，不接受脚本 URL 或任意 HTML/JS。

统一文档版本 1；所有模块/条目/维度 ID 在文档内唯一；order 必须恰好覆盖模块，hidden/slot/overrides 只能引用存在实例。图表只引用所属模块的维度，groupId 只能引用所属能力组；选中未评分维度按文字降级。一个 profile 单例，其余类型可多实例。

量尺预设为 5/10/100，min 为 0；score 为 null 或合法数值。修改量尺由用户明确选择按比例换算或清空；本轮不计算平均分、岗位排名或推断能力。雷达少于三个已评分维度降级；图表用现有 Vue/SVG 能力实现，条状和雷达共用同一维度，无图表库依赖。

### 创建与保存伪代码

```text
创建：接收已校验 name/locale/document + Guard 身份
  检查 admin/super_admin 与 Resume.Sections:edit
  事务：检查本人用户未删除 → upsert 本人空间
    → 创建归属于该空间的 Resume 和唯一 Draft，revision = 1
  只返回安全元信息与文档；不接收客户端 owner/updatedBy/revision

读取：接收 id + Guard 身份
  以 id、workspace.userId = currentUser.userId、未删除归属过滤查询
  缺失统一 404，不透露他人简历存在性
  验证已存文档版本/结构后返回完整草稿，不当作公开响应

保存：接收 id、expectedRevision、已校验 document + Guard 身份
  检查编辑资格；事务内检查本人归属与未删除状态
  条件更新：resumeId + expectedRevision + 归属与未删除
    → document/schemaVersion/updatedBy/updatedAt 更新，revision 原子递增
  影响行数为 0 → 回滚并返回 409，不覆盖现有内容
  同事务读取已保存草稿返回，避免把更晚一次写入误当本次结果

前端：真实登录 → 主动创建/输入本人 resumeId → 获取草稿
  只编辑本地工作副本；2.5 秒防抖且一次仅一个保存请求
  保存期间的新输入不被响应覆盖；成功更新 revision，再保存后续输入
  失败/冲突保留输入，暂停自动重试；可导出备份，再主动重新加载
  离开有未保存变更时提醒；切账号取消旧结果回写，缓存按账号/简历隔离
```

验证顺序：契约边界与旧数据转换测试 → 后端所有权/角色/条件更新测试 → 隔离本地库 HTTP 登录/创建/读取/保存/冲突链路 → 三档/桌面/移动端编辑展示 → 全仓质量门与受影响构建。数据库应用只在确认环境后执行；外部 Apifox 写入采用可审查 OpenAPI 产物后再同步。
