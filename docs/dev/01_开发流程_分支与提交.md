# 开发流程（分支、Issue、提交、发布）

> 本仓沿用 Dao 标准流程：**先立 Issue，再从 `dev` 开短分支，验证完成后合回 `dev`**；`main` 只承载发布与正式版本。

## 1. 分支模型

| 分支                   | 用途           | 说明                                                                 |
| ---------------------- | -------------- | -------------------------------------------------------------------- |
| `main`                 | 发布与正式版本 | **不直接在 `main` 上开发**；只在阶段性可展示 / 可部署时由 `dev` 并入 |
| `dev`                  | 日常开发主线   | 所有功能分支的合入目标                                               |
| `feat/<issue>-<slug>`  | 功能开发       | 例：`feat/1-infra-data-layer-and-layers`                             |
| `fix/<issue>-<slug>`   | 缺陷修复       |                                                                      |
| `docs/<issue>-<slug>`  | 文档与教程     |                                                                      |
| `chore/<issue>-<slug>` | 工程与配置     |                                                                      |

- 分支名**必须带 Issue 编号**；禁止 `dev`、`fix`、`test` 这类不可追踪名称。
- 开分支前先同步基线：`git switch dev && git pull --ff-only origin dev`。

### 一次性历史说明

建仓时 `main` 与 `dev` 是分别初始化的两条历史（无共同祖先但内容相同）。2026-10-07 已把 `dev` 变基到 `main` 之上并强制推送，两者现已同源。**此后不要对 `dev` / `main` 做历史改写**。

## 2. 标准流程

1. **先建 Issue**：背景 / 目标 / 非目标 / 改动范围 / 验收标准 / 测试计划 / 日志输出要求。模板见 `.github/ISSUE_TEMPLATE/`。
2. **从 `dev` 开分支**：`git switch -c feat/<issue>-<slug>`。
3. **先设计再实现**：目标、边界、涉及文件、风险、验收与第一步写清后再动代码；关键任务同步建 `dao/tasks/DAO-XXX-*.md` 任务卡。
4. **实现与自测**：只做当前 Issue 范围；发现旁支问题记为独立 Issue，不混入当前分支。
5. **质量门**：`pnpm typecheck && pnpm lint && pnpm test`；涉及构建或发布时补 `pnpm build`。
   说明：**格式基线以仓库的 oxfmt 配置为准**（`.oxfmtrc.json`：单引号 / 无分号 / 2 空格 /
   `printWidth: 120` / 尾逗号 `all` / 单参数箭头不带括号）。`DAO-006` 已全仓统一重排，
   `pnpm format:check` 是常规质量门；大量改动之后跑一次 `pnpm format`，避免格式噪音混进语义 diff。
   模板（`.vue`）格式同样交给 oxfmt：属性按 `printWidth` 折行（超宽则一行一个属性）——
   ESLint Vue 的 `vue/max-attributes-per-line` 那类规则本项目**不采用**（oxlint 无对应实现）；
   规则开关见 `.oxlintrc.json`（只保留 oxlint 真正支持的项）。
6. **自审**：是否越界、是否留下可抽离能力、类型 / 契约 / 文档是否同步。
7. **提交并推送**：Conventional Commits，推分支到远端。
8. **合回 `dev`**：单人阶段可本地 squash 合并后 push，但必须保留可追踪提交与 Issue 链接；多人协作优先开 PR。
9. **回填并关闭 Issue**：改动摘要、验证结果、后续 Issue。
10. **发布到 `main`**：阶段性可展示 / 可部署时，再由 `dev` 并入 `main`。

## 3. 提交规范

- 日常提交用 Conventional Commits：`feat(admin): …`、`fix(web): …`、`docs(dao): …`、`chore: …`。
- 集成边界（`feat/* → dev`、`dev → main`）的净变化使用 **Dao Commit**（`[上卦下卦][卦名] type(scope): subject`），由人定锚。
- 版本与 Changelog 走根目录 `standard-version` 脚本。

## 4. Issue、任务卡与提交的分工

| 载体                 | 管什么                                                   | 不管什么                    |
| -------------------- | -------------------------------------------------------- | --------------------------- |
| GitHub Issue         | 对外可追踪的目标、范围、验收与测试计划                   | 不承载逐步实现细节          |
| `dao/tasks/DAO-*.md` | 当前关键任务的目标、状态、验证、交接与收口（唯一事实源） | 不复制聊天记录与原始日志    |
| Commit / PR          | 具体改动与集成边界                                       | 不替代 Issue 与任务卡的状态 |

三者用链接互相串联：Issue ←→ 任务卡 ←→ commit SHA / PR。

## 5. 验证范围按风险扩大

| 改动类型               | 至少验证                                     |
| ---------------------- | -------------------------------------------- |
| 纯文档 / 注释          | `format:check` + 链接自查                    |
| 单端组件 / 页面        | 该端 `typecheck` + dev server 关键路径       |
| 请求层 / 共享契约      | 两端 `typecheck` + 真实接口调用路径          |
| 跨端 / 跨 package 能力 | 全仓 `typecheck` + `test` + 受影响端构建     |
| 里程碑收口 / 发布      | 全仓 `typecheck` / `lint` / `test` / `build` |

## 6. 展示层任务的附加检查

- `light / dark` 基础可用，语义色 token 优先，不写死颜色。
- 为后续主题 / 布局扩展保留钩子（配置 → 渲染，而不是把样式写死在页面里）。
- 桌面与移动端关键路径都要看一眼，必要时附验证记录。

## 7. UI / 交互改动的确认闸门

**机器验证不等于验收。** 前端改动跑完 `typecheck` / `oxlint` / 结构断言，只能说明"没坏"，不能说明"对"。

- 凡涉及**视觉、布局、动效、交互手感**的改动：改完**先别提交**，留在工作区；
- 同步说明**看哪里、看什么**（哪个路由、哪个断点、哪一步操作、期望什么样）；
- **Owner 实看确认后**再提交；未确认前不得用 squash / 合并把改动带进 `dev`；
- 若 Owner 发现样式或交互不对：**基于他的反馈继续改**，不要辩解"技术上已经生效"——他说的是观感与手感，
  与"类是否生效"是两个层面的事。
