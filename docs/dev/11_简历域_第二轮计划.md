### P0 的顺序理由

1. **P0-1 → P0-2 必须相邻**：先定查询参数（后端契约），再改前端查询层；反过来会写两遍。
2. **P0-3 独立，但最重**：`resumeDateSchema` 是 `discriminatedUnion`（`custom` 文本 / `structured` 起止月 + `isCurrent`），
   且带 `superRefine`（"至今"与 `end` 必须一致、`start ≤ end`）。所以不能塞一个文本框 ——
   要做一个**双模式**编辑器，并把校验规则与 schema 同源。这是本轮唯一"大"的一条。
3. **P0-4 依赖 P0-3？不依赖**，但**依赖已完成的发布态**（未发布时分享要给出"先发布"的引导）。
4. **P0-5 先做**：成本几分钟，但它决定"我们有 HTTP 验证"这句话是真是假。

## 4. 需要 Owner 拍板的两个点

### 决策 1：「背景图」属于**用户级**还是**简历级**？

`User` 表**已经有 `avatar`**，但**没有 background**。而简历的 `profile.hero` 里已经有头图字段，
展示配置里也已有背景。

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A（推荐）** | `settings/user` 只做**用户头像**；背景图仍留在**简历级**（展示配置 / hero） | 不用迁移；语义也更对 —— 背景是"这份简历的样子"，不是"这个人的样子" |
| B | `User` 加 `background` 列（迁移），`settings/user` 两个都设，作为**新建简历的默认值** | 一次迁移 + "默认值如何被简历继承"这套规则 |

### 决策 2：搜索走哪个字段、要不要全文检索？

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A（推荐）** | 只按 `name` 做 `contains`（大小写不敏感）+ 已发布/默认等**布尔筛选** + 排序（更新时间/名称） | 小；`@@index` 够用 |
| B | 搜正文（`document` 的 JSONB 全文） | 需要 GIN 索引与中文分词，属于另一个量级 |
