# P0-3 设计方案：教育 / 经历 / 项目的时间可编辑

日期：2026-10-19。状态：**设计待确认，未写代码**。
上下文：`docs/dev/11_简历域_第二轮计划.md` 的 P0-3。

## 0. 现状：为什么它当初是只读的

`resume-edit-segments.ts` 的注释已经写明：

> ⚠️ **日期不在字段表里**：契约的 `date` 是判别联合（`custom` 文本 / `structured` 起止 + 至今），
> 而现有字段类型只能表达标量、字符串数组与文字条目数组。硬塞一个文本框会把 `structured`
> 写成非法形状，所以本轮**只读展示**。

**这个判断是对的** —— 一个 `text` 字段承载不了判别联合。要做得对，缺的是**一种新的字段类型**。

## 1. 契约现状（已核实）

```ts
const text  = z.string().max(500)
const month = z.string().regex(/^\d{4}-(0[1-9]|1[0-2])$/)   // 只用年-月，没有"日"

export const resumeDateSchema = z
  .discriminatedUnion('mode', [
    z.strictObject({ mode: z.literal('custom'),     text }),
    z.strictObject({ mode: z.literal('structured'), start: month, end: month.nullable(), isCurrent: z.boolean() }),
  ])
  .superRefine((date, context) => {
    if (date.mode !== 'structured') return
    if (date.isCurrent ? date.end !== null : date.end === null || date.start > date.end) {
      context.addIssue({ code: 'custom', message: '日期顺序或至今标记不合法' })
    }
  })
```

**四条硬约束**（编辑器必须产出合法形状，不能只做"看起来能用"的输入框）：

1. `custom` 只允许 `{ mode, text }` —— **不允许**携带 start/end（`strictObject`）
2. `structured` 只允许 `{ mode, start, end, isCurrent }`
3. `isCurrent === true` ⇒ `end === null`
4. `isCurrent === false` ⇒ `end` 非空 **且** `start <= end`（字符串比较，`YYYY-MM` 可直接比）

**日期出现在 4 处**：

| 位置 | 字段 |
| --- | --- |
| `education` 模块的 `items[]` | `date` |
| `experience` 模块的 `items[]` | `date` |
| `projects` 模块的 `items[]` | `date` |
| 某模块的 section 级 | `time` |

**好消息**：新列表项的 `blank` **已经带** `date: { mode: 'custom', text: '' }` —— 不需要改新增逻辑。

## 2. 唯一的接入点（已核实）

```
FormFieldType = 'text' | 'textarea' | 'tags' | 'number' | 'textItems'    ← 缺 date
        │
        ▼
MySchemaForm（mode: fields / list）
        │  每个字段交给
        ▼
MySchemaFieldInput    ← **按 field.type 分发控件的唯一地方**
```

所以整件事的骨架是：

1. `FormFieldType` 加 `'date'`
2. 新增 `MyResumeDateInput.vue`（真正的日期编辑器）
3. `MySchemaFieldInput` 加一个 `date` 分支，委托给它
4. 在 3 张字段表里把 `date` 写成正式字段

**web 端不需要改任何代码** —— 它与 admin 共用 `@rs/common` 的字段表，`MySchemaForm` 也会自动拿到新控件。这正是当初把字段表上提到共享层的回报。

## 3. 组件设计：`MyResumeDateInput`

**模型是 `ResumeDate` 整个对象**（不是一个字符串）—— 这是与现有所有字段类型最本质的区别：
`text` / `number` 都是标量，而它是判别联合。props：`:value: ResumeDate`，emit `update:value: ResumeDate`。

### 3.1 两种模式的 UI

```
[ 结构化 | 自定义 ]          ← 二选一的分段控件（USelectButton 或 UButton 组）

结构化：  [ 2020-09 ] → [ 2023-06 ]   [✓ 至今]
自定义：  [ 2020 年 9 月 – 2023 年 6 月 ]        （自由文本，max 500）
```

- **结构化**：两个月份输入 + 「至今」勾选
- **自定义**：一个文本框（保留给"三段经历 / 兼职 / 远程"这类表达不了的时间说明）

### 3.2 约束怎么落到 UI（不让用户走到非法状态）

| 约束 | UI 层怎么做 |
| --- | --- |
| `isCurrent ⇒ end === null` | 勾选「至今」时**清空并禁用**结束月；取消勾选时给一个默认 end（= start 或当前月） |
| `end !== null && start <= end` | 结束月的可选范围**从 start 起**（年/月下拉可禁用更早的项）；若用原生 `type=month`，则提交前比对并在字段下方提示 |
| `strictObject` 不允许混字段 | 切模式时**整体替换**对象（`{ mode: 'custom', text }` / `{ mode: 'structured', … }`），不做 merge |

### 3.3 模式切换时的数据怎么办 ← **需要你拍板**

判别联合决定了切换必然丢另一模式的数据（不可能两者同时存在）。三种做法：

| 方案 | 行为 | 代价 |
| --- | --- | --- |
| **A（推荐）** | 单向预填：`structured → custom` 把摘要串填进 `text`（可改）；`custom → structured` 用当前年月作起止 | 不猜、不解析；切到自定义时不丢已有信息 |
| B | 智能解析：把 `2020.09 - 2023.06` 解析成结构化 | 解析规则一多就会**静默猜错**，比让人重填更糟 |
| C | 不预填，直接给空 | 用户切一次就丢一次输入，体验差 |

## 4. 交互细节（admin 与 web 一致）

1. **admin 的 `#list-item-extra` 只读摘要**：日期成为正式字段后，那行"时间：xxx（本页暂不可编辑）"就重复了 → **建议移除**（`hasDate` 与 `formatResumeDate` 的调用点一并清）。← 需确认
2. **保存链路不变**：整份 document 走 `PUT /resume/:id/draft`（revision 乐观锁），**后端零改动**
3. **错误提示**：非法形状由 zod 在服务端拦（400 `Common.Validation:failed`）。**验证项**：确认 `superRefine` 的 issue 带 `path`，前端才能把错误挂到具体字段而不是只弹一句"参数有误"（若没带，加 `path` 是唯一可能的契约侧小改动）
4. **新建列表项**：`blank` 已有 `date`，但 `text: ''` —— 空 `custom` 是合法形状吗？**要验证**：若 `text` 允许空串，用户新建一项不填时间也能存；若不允许，`blank` 得改成 `{ mode: 'structured', start: 当前月, end: null, isCurrent: true }`

## 6. 验证计划

**单元（common）**
- `resumeDateSchema`：`isCurrent` 与 `end` 四种组合；`start > end` 被拒；`custom` 携带 start 被拒；`YYYY-MM` 格式边界（`2020-1` / `2020-13` 被拒）

**单元（ui）**
- `MyResumeDateInput`：切模式产出的是**合法形状**（不是 merge）；勾「至今」时 `end === null`；取消勾选时 `end` 有值

**手工（Owner 实看，两端各一次）**
- 教育 / 经历 / 项目各编辑一条，保存 → 刷新 → 形状与内容不变
- `custom` ↔ `structured` 互切后仍能保存
- 「至今」勾选/取消后保存成功
- 空白新项直接保存（验证 §4.4 的结论）

**机器**：`pnpm check` + 两端 `build`（**必须 build** —— `typecheck` 抓不到 SFC 模板编译错误，这一轮已经踩过两次）

## 7. 需要 Owner 拍板的四点

1. **月份输入控件**：`UInput type="month"`（简洁，原生给 `YYYY-MM`；Safari 会降级成文本框）vs 年 / 月两个 `USelect`（跨浏览器一致，但 8 个控件更笨重）
2. **模式切换的数据策略**：A 单向预填（推荐）/ B 智能解析 / C 不预填
3. **admin 的只读日期摘要**：移除（推荐）还是保留作概览
4. **空时间的处理**：允许 `custom.text === ''`（新项可不填时间）还是强制必须有时间
