## 5. 基础功能需补齐或核验的地方

### R07 本人资料：保存契约与错误反馈

当前 [资料页](../../apps/admin/layers/13-settings/app/pages/settings/user.vue) 每次保存都组装 username、nickname、email、phone，并非只传变更字段。空邮箱转换为 `null`，但 [updateUserSchema](../../apps/server/src/user/dto/user.schema.ts) 的 email 允许不传、不允许 null。由此推断：无邮箱账号只改昵称，或试图清空邮箱，都可能在输入校验处失败；本轮未发 HTTP 复现。

前端 [ProfileUpdateInput](../../apps/admin/layers/13-settings/app/apis/user.ts) 从响应 MyProfile 推导，email 包含 null，因此类型检查未暴露这项输入差异。这适合作为一个完整学习闭环：**响应字段可空，不代表 PATCH 输入支持清空**。

页面还按错误 message 的字段名定位 409，而全局唯一冲突提示为通用文本，邮箱/手机冲突可能落到用户名栏。页面未接入手机号严格校验 schema；后端注释提到工具存在，不能视为页面已调用。页面只刷新本人资料 query，其他身份展示是否更新须另验。

头像是独立流程：选图 → 上传 → 单独 PATCH avatar → 刷新资料，不等普通资料保存按钮。上传成功、PATCH 失败的重试和残留文件处理须分别验。前端设计已据此勘误，目标行为与当前事实分开记录。

## 9. 建议如何收完基础产品再接 AI

1. **确定可验收的产品边界**：站点指定作者还是多作者；谁能读他人资料；是否接受保存即更新公开内容；分享限制作用于哪些入口。对应 R01～R06，每项先确认规则再设计。
2. **补齐会影响实际使用的闭环**：R07 资料输入契约与反馈、R08 所需展示开关/素材入口、R09 产品页说明与无效入口。每次只取一条 Task，需求 → 前后端设计 → API → 验证共同更新。
3. **用 V01～V07 做一次联合验收**：机器证据和 Owner 桌面/移动端意图验收齐全后，负责窗口回填任务卡/Issue；明确保留问题和部署条件。
4. **冻结 AI 的数据前提**：哪些是作者私有草稿、哪些可公开、AI 读取哪一份内容、哪些访客可调用和如何计费/限额，再开 AI 需求。已有权限键或配额字段不等于 AI 业务已交付。

复制简历、发布快照/历史恢复、多语言、回收站、公开注册、完整后台用户管理均可由 Owner 选择延期；它们不是 AI 接入的自动前置条件。若确定面向多用户开放，则账号管理与恢复能力需要重新评估，不能套用个人展示站的最小范围。

建议学习的第一刀是 **R07：无邮箱账号修改昵称**。先复述用户意图，再沿资料页 save → ProfileUpdateInput → updateUserSchema → UserService.update → 错误 Filter 阅读；确认空值规则后另开实现任务，用一个正例和一个失败例子验证。这能同时练习需求语言、前后端职责分离和契约审查。
