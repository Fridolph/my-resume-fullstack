## 第 1 组 · 内容建模

**Q1.1** 用户在编辑器里删掉一个能力分组。`display.sections.overrides` 里存着引用该分组的维度选择，谁负责清理——契约层、编辑器、还是后端？为什么？

<details><summary>提示与参考答案</summary>

**提示**：先分清 `view.dimensionIds` 引用的到底是 `groupId` 还是 `dimensionId`。

**参考答案**：**编辑器负责清理，契约负责拒绝不一致，后端只校验和存储。**

- 删分组时真正要清理的是 `dimensions[].groupId`（`delete item.groupId`，**只解除关联、不删维度**——那条自评可能仍有意义）。
- `view.dimensionIds` 引用的是 **dimension 的 id**，与 group 无关；删**维度**时才 `filter` 掉它。
- 后端拿到的必须是完整合法的文档，若引用悬空，`superRefine` 会报"能力组引用不存在"→ 400 拒收。
- 为什么不让后端清理：后端不知道用户意图（那条维度该删还是留成独立维度），替用户猜就是隐式改写内容。

**易错点**：以为 `dimensionIds` 引用的是 groupId；把"删引用"和"删实体"混为一谈。

</details>

**Q1.2** 现在要给"每条能力"加一个熟练度标签（初级/中级/高级）。该加在 `items[]` 还是 `dimensions[]`？加了之后会不会和 `dimensions[].score` 打架？

<details><summary>提示与参考答案</summary>

**提示**：只问一句——这个字段描述的对象是谁？

**参考答案**：加在 **`items[]`**（它描述"这一条能力本身"）。判据：描述 item → 放 item；描述"用户在一个抽象轴上的自评" → 放 dimensions；描述"整套评估规则" → 放 `ratingScale`。

**但要点出真实张力**：如果标签是"初/中/高"，它和 `dimensions[].score` 在表达**同一件事**（自评强度），用户会困惑"我该打标签还是打分"。所以要么把标签定义为**不可排序的分类**（语言/框架/工具/软技能），要么就别单独加字段。

**实现代价**：`items[]` 是 `strictObject`，加字段 = 改共享契约 = 三端同步升级；新前端提交带 `level` 的文档、老后端会 400。

</details>

**Q1.3** 复制一份简历（Duplicate）时，新文档里的模块 ID / 分组 ID / 条目 ID / 证据 ID，哪些**必须**重新生成，哪些**可以**保留？

<details><summary>提示与参考答案</summary>

**提示**：唯一性约束的作用域是"整张表"还是"一份文档"？

**参考答案**：**ID 唯一性的作用域是"一份文档"。**

- **跨文档复制**（Duplicate 简历）→ 内部 ID **全部可以保留**；数据库层只有 `resumes.id` 必须新（它是新的一行）。
- 保留还有**正面价值**：将来做"简历 A vs B 差异对齐"时，相同 ID 就代表"同一条能力"。
- **同一文档内**复制模块 → **所有内部 ID 必须重建**，还要同步改 `display.sections.order` 和 `overrides` 的键，否则 `collectIds` 立刻报"文档 ID 重复"。

**易错点**：用"外层 id 变了所以里面就独立了"来解释——机制不是嵌套作用域隔离，而是"约束只要求文档内唯一"。

</details>

## 第 2 组 · 表结构与约束

**Q2.1** 用户改了三条能力描述并成功保存。`resumeId`、`schemaVersion`、`revision` 三个字段各自怎么变？为什么？

<details><summary>提示与参考答案</summary>

**参考答案**：`resumeId` **不变**（指向的简历没变）；`schemaVersion` **不变**（只改内容，不动文档结构）；`revision` **递增**（每次成功保存 +1）。

判据：`schemaVersion` 表达"这份文档按第几版契约书写"，是**跨文档共享的离散常量**；`revision` 是"这份草稿的并发版本号"，每个文档各有自己的计数。

</details>

**Q2.2** 把 `ResumeDraft` 改成用独立的自增 `id` 作主键、`resumeId` 只保留普通外键，还能保证"一份简历最多一条当前草稿"吗？

<details><summary>提示与参考答案</summary>

**参考答案**：**不能**，需要补 `resumeId @unique`。

- 独立主键保证"每条草稿身份不同"；外键保证"简历存在"；**唯一约束**才保证"同一 resumeId 不重复"。
- 只加 `@@unique([resumeId, id])` 不够：`draft-1/resume-A` 与 `draft-2/resume-A` 是不同的组合，两条都能写入。

（项目后来真的改成了这个形态：`resume_drafts.id` 自增主键 + `resume_id` UNIQUE —— 见 §11.2。）

</details>

**Q2.3** 只保留 `id` 主键与 `resumeId` 外键、**不加** UNIQUE 约束，连续写入两条 `resume_id = resume-A`（id 不同），数据库会接受几条？为什么？

<details><summary>提示与参考答案</summary>

**参考答案**：**两条都会接受**。主键不重复、外键都指向存在的简历，没有任何约束被违反。

所以"一份简历一条草稿"必须由 `resume_id` 的 UNIQUE 显式表达——**它从"主键的副作用"变成了"显式的业务约束"**。附带收益：将来做历史快照时，去掉这条 UNIQUE 就能容纳多条记录。

</details>

**Q2.4** `ResumeDraft.resumeId` 是主键时，删除一份 `Resume` 会怎样？（若 `onDelete` 是 `Restrict`）

<details><summary>提示与参考答案</summary>

**参考答案**：**被阻止**（有草稿引用时无法物理删除该简历）。

要点区分：外键的 `onDelete` 决定**父记录被物理删除时**的行为——`Restrict` 阻止、`Cascade` 连带删除、`SetNull` 置空。而项目当前**没有**简历物理删除接口；`Resume.deletedAt` 是**软删除**（只标记字段，不触发外键动作）。

**易错点**：把"外键指向"理解成"级联删除"；把软删除当成 SQL DELETE。

</details>

## 第 3 组 · 共享契约与校验

**Q3.1** 下面五份能力数据，哪几份不合法？各自属于哪类错误（字段形状 / 跨字段规则 / 引用关系）？

```ts
1. { ..., extraField: 'x' }
2. { dimensions: [{ ..., groupId: 'backend' }] }        // groups 里只有 'frontend'
3. { dimensions: [{ ..., score: 8 }] }                  // ratingScale.max = 5
4. { groups: [{ ..., items: [] }] }
5. { dimensions: [] }
```

<details><summary>提示与参考答案</summary>

**参考答案**：

| 数据 | 结论 | 原因 |
| --- | --- | --- |
| 1 | ❌ | `strictObject` 拒绝未声明字段——**字段形状**错误 |
| 2 | ❌ | 字符串格式合法，但 `superRefine` 要求它引用 `groups` 中真实存在的 ID——**引用关系**错误 |
| 3 | ❌ | 超出 `ratingScale.max`——**跨字段业务规则**错误 |
| 4 | ✅ | 只设了上限制（最多 20），没有 `min(1)`；用户可以先建空分组 |
| 5 | ✅ | 同上，可以暂不配置评分维度 |

**易错点**：把"数组字段存在"误读成"数组必须非空"。这个项目的风格是：**数组可以为空，字段不可以省略**。

</details>

## 第 4 组 · 并发与版本

**Q4.1** A、B 两个窗口都读到 `revision = 3`。A 改标题并保存。A 应提交哪个 `expectedRevision`？成功后数据库 `revision` 是多少？

<details><summary>提示与参考答案</summary>

**参考答案**：提交 **3**；成功后变为 **4**。

补充：返回给前端的 `revision` 不是应用层用 `expectedRevision + 1` 算的，而是**同一事务内重新读出来的最终值**——少一处能算错的地方。

</details>

**Q4.2** 紧接着 B 用 `expectedRevision = 3` 提交（改的是评分）。后端会怎样处理？**这是加锁吗？**

<details><summary>提示与参考答案</summary>

**参考答案**：返回 **409**。**不是加锁**，是**乐观并发控制**。

- 没有悲观锁、没有 `SELECT ... FOR UPDATE`、没有任何等待——B 的请求立即执行。
- 409 的原因不是"revision 3 被占用"，而是 **"revision 3 已经不存在了"**（A 已把它变成 4），B 的版本前提过期。
- "判断与更新不可分割"由**单条原子 SQL** 保证：`UPDATE ... WHERE resume_id = ? AND revision = ?`。数据库在该语句期间确实持有行级锁来保证原子性，但那是**引擎实现细节**，范围仅这条语句；"悲观加锁"的语义是持有到**整个事务结束**。二者不是一回事。

</details>

**Q4.3** B 能否只把 `expectedRevision` 改成 4 就自动重试？为什么？

<details><summary>提示与参考答案</summary>

**参考答案**：**不能——会静默覆盖他人修改。**

- 保存提交的是**整份 document**，不是局部补丁；B 手上的是它在 revision 3 时读到的**旧副本**。
- 改成 4 提交成功后，revision 变 5，而 **A 改的标题被 B 的旧副本覆盖**——表面"保存成功"，实际丢数据（last-write-wins 陷阱）。
- 409 的价值在于它是个**信号**：告诉用户"别人动过这份数据"；自动改写版本号重试就是把信号抹掉。
- 正确路径：保留本地输入 → 主动重新读取 → 用户对比后决定如何合并 → 再保存。冲突判断交给人。
- 将来要做自动合并，前提是能**按稳定 ID 做差异对齐**（每个模块/分组/条目都有稳定 ID）。

</details>

## 第 5 组 · 模块与边界

**Q5.1** `create` 和 `saveDraft` 都调了 `assertEditable()`，`findDraft()` 没调。为什么？加上会怎样？

<details><summary>提示与参考答案</summary>

**参考答案**：因为**读不需要编辑资格**。

- `findDraft` 的保护机制是**所有权过滤**（`ownedResume()` 进 `where`），不是资格检查；写操作才叠加 `assertEditable()`。
- 加上会直接打掉"普通用户只读本人草稿"这个已实现能力（`useResumeDraft` 的 `canEdit` 只管写入，`load()` 不检查资格）。
- 措辞提醒：这是**服务端检查点**，不是"按钮"。前端思维问"按钮谁能点"，后端思维问"接口谁能调"——按钮可以被 curl / Apifox 绕过。

</details>

**Q5.2** 要加 `GET /resume`（列出本人的所有简历）：属于哪个模块？要新表吗？要 `assertEditable()` 吗？

<details><summary>提示与参考答案</summary>

**参考答案**：

| 问题 | 答案 | 理由 |
| --- | --- | --- |
| 模块归属 | **属于 `resume` 模块** | 查的是同一个聚合根 `Resume`，只是另一种视图；模块归属看"数据和规则归谁" |
| 新表 | **不需要** | `Resume` 已有 `workspaceUserId` 与 `deletedAt`，一次 `findMany` 即可 |
| `assertEditable` | **不需要** | 但**必须**带所有权过滤（`where.workspaceUserId`） |

⚠️ 列表接口的所有权过滤比详情接口更关键：漏掉过滤 = 全库越权读取（IDOR）。

**易错点**：想在 `users` 表加字段关联 resumes——**方向反了**，一对多时外键必须在"多"的一侧。

</details>

**Q5.3** 将来的 `ResumeSnapshot`（发布快照）该放 `resume` 模块还是新开模块？判据是什么？

<details><summary>提示与参考答案</summary>

**参考答案**：倾向**新开模块**，判据是**事务边界与规则归属**。

- 快照确实有 `resumeId` 外键，但**"有外键"推不出"同一模块"**——反例就在同一张表里：`ResumeDraft` 同时有 `resume_id → resumes` 与 `updated_by → users`，却没人认为 draft 属于 user 模块。
- 真正判据：创建简历**必须同时**创建草稿（同一事务）→ 同模块；发布是**独立动作**（"把当前草稿冻结成不可变副本"），不与草稿编辑同事务，且有不可变性、版本号、分享 token、公开读取等自己的规则。
- 另需区分：**"一个发布对应一份简历"不是数据模型必然，而是产品选择**（也可设计成"一个发布 = 多份简历合集"的作品集形态）。

</details>

## 第 6 组 · 路由与错误语义

**Q6.1** 要加"列出本人简历的发布快照"，路径怎么写？为什么？

<details><summary>提示与参考答案</summary>

**参考答案**：

```text
GET  /resume/:id/snapshots          列表（某一份简历的所有快照）
GET  /resume/:id/snapshots/:sid     详情
POST /resume/:id/snapshots          发布
```

- `:id` 指的是"**哪一份简历**"（父资源/归属），不是"哪一份快照"；带 `:id` 不等于查单个——列表与详情的区分在**最后一段**有没有 id。
- `/resume/snapshots` 会读成"系统级全部用户的快照集合"，是完全不同且危险的东西。
- "本人的"来自认证身份，不写进路径。
- 进阶：**URL 空间 ≠ 模块边界**——快照可能是独立模块，但 URL 仍可挂 `/resume/:id/snapshots`。

</details>

**Q6.2** `@Param` 校验失败返回 400、"id 合法但不存在"返回 404——这个划分合理吗？统一成 404 有什么问题？

<details><summary>提示与参考答案</summary>

**参考答案**：合理。

- **400** = 请求**本身**有问题（格式、类型、长度、未知字段）；**404** = 请求没问题但目标**不存在**。
- 404 其实有**两个来源**，靠 `errorCode` 区分：路由不匹配（`Common.Route:notFound`）与资源不存在（`Resume.Draft:notFound`）。
- 若把格式非法也统一成 404，会把"**客户端 bug**"伪装成"数据问题"——最浪费时间的调试陷阱。

</details>

**Q6.3** 把保存接口从 `PUT` 改成 `PATCH`，但请求体仍传整份 `document`，会有什么误导？

<details><summary>提示与参考答案</summary>

**参考答案**：核心是一句话——**HTTP 方法是对"服务端要做什么"的承诺，不是对"请求体长什么样"的描述。**

| | `PUT` | `PATCH` |
| --- | --- | --- |
| 语义 | 用请求体**替换**目标完整状态 | 把请求体**应用**到现有状态 |
| 请求体 | 必须能独立表达目标新状态 | 只需表达变化 |
| 幂等性 | 幂等 | 不保证 |

用 `PATCH` 传整份的三个后果：对**基础设施**撒谎（幂等性影响代理/重试）；对**下一个开发者**撒谎（会以为可传局部补丁）；**契约与语义脱钩**。

**连锁因果链**（值得背）：JSONB 整存整取 → 保存 = 整份替换 → 用 `PUT` 才诚实 → 整份替换会覆盖并发修改 → 必须带 `expectedRevision` → 冲突返回 409 → 不能自动重试。

</details>

## 第 7 组 · Service 与事务

**Q7.1** `saveDraft` 的 `updateMany` 里已经有 `resume: this.ownedResume(...)`，前面 `findFirst` 也校验过了。能删掉 `updateMany` 里那个条件吗？

<details><summary>提示与参考答案</summary>

**参考答案**：**不能。**两个条件的**职责不同**：

| 位置 | 回答的问题 | 去掉的后果 |
| --- | --- | --- |
| `findFirst` + throw | 这是 404 还是别的问题？（**错误语义**） | 失败全部退化为 409 |
| `updateMany` 的 `resume` 条件 | 写入本身受不受所有权约束？（**正确性**） | 校验与写入之间出现时间窗，可能写到已删除/已易主的行上 |

原则：**写操作的所有权条件，不依赖"前面已经查过"。**

另注意同处一个 `where` 的第三类条件：`resume` 管**所有权**，`revision` 管**并发**——一个防越权、一个防覆盖。

</details>

**Q7.2** 把 `create` 里的 `buildResumeDocument` 挪进事务内，功能与性能会怎样？

<details><summary>提示与参考答案</summary>

**参考答案**：

- **功能**：成功路径无变化；但**错误路径**会变——它在缺 profile 时会抛错，放事务外则"根本没开事务"，放事务内则白付一次 BEGIN + ROLLBACK。
- **性能**：更准确的视角是**连接占用**（事务一旦开启就持有连接池中的连接），而非 CPU。原则：**事务里只放必须原子的数据库操作，纯计算移到外面。**

</details>

**Q7.3** `updated.count !== 1` 能否改成 `updated.count === 0`？什么情况下两者不等价？

<details><summary>提示与参考答案</summary>

**参考答案**：**当前完全等价**——`where` 含唯一字段（`resume_id` UNIQUE），`count` 只可能是 0 或 1。

不等价出现在 **`where` 可能匹配多行**时：

| 场景 | `count === 0` | `count !== 1` |
| --- | --- | --- |
| 匹配 0 行 | ✅ 报错 | ✅ 报错 |
| 匹配 1 行 | ✅ 通过 | ✅ 通过 |
| **匹配 2 行** | ❌ **静默放过，还更新了 2 行** | ✅ 报错 |

所以 `count !== 1` 是**断言式写法**：把"成功"定义为"恰好影响一行"，从而把"依赖 UNIQUE 约束"这件事显式表达出来——将来谁去掉了 UNIQUE，这行会立刻报警。

</details>

## 第 8 组 · 鉴权与权限

**Q8.1** 有人在数据库里给 `user` 角色加上了 `Resume.Sections:edit` 权限键。他能编辑简历吗？为什么？

<details><summary>提示与参考答案</summary>

**参考答案**：**不能。**

`assertEditable` 通过的条件是 **`isEditorRole && hasEditPermission`**（两者都要满足）；权限键满足了第二个，但角色条件不满足。

⚠️ **德摩根陷阱**：原文写的是 `if (!是管理员 || !有权限) throw`，等价于 `NOT (是管理员 && 有权限)`。若把那个 `||` 读成"满足其一即可"，行为正好相反。嵌套让误读更容易——内层 `role === 'admin' || role === 'super_admin'` **真的是"或"**。

（该处已按建议改成命名变量正向表达，见 `resume.service.ts` 的 `assertEditable`。）

</details>

**Q8.2** 用户改了密码，`sessionVersion++`。他另一台设备上未过期的 token 会在**哪一步**、以**什么 errorCode** 被拒？

<details><summary>提示与参考答案</summary>

**参考答案**：在 **`AuthService.restoreUser()`** 的 sessionVersion 比对处被拒，`errorCode = AUTH.Session:revoked`。

执行路径：token 验签与 exp 检查**通过**（token 本身有效）→ `JwtStrategy.validate()` → `restoreUser()` 里 `findFirst` 查到用户（`if (!user)` 不触发）→ `user.sessionVersion !== tokenSessionVersion` 命中 → 抛 401。该异常由 `handleRequest` 的 `if (error) throw error` **原样穿透**，不会进入 `expired ? ... : ...` 分支。

| 拒绝原因 | 在哪一步 | errorCode |
| --- | --- | --- |
| 没带 token | `handleRequest` | `AUTH.Token:missing` |
| token 过期 | `handleRequest` | `AUTH.Token:expired` |
| token 伪造/格式错 | `handleRequest` | `AUTH.Token:invalid` |
| **会话已被撤销** | **`restoreUser` 抛出** | **`AUTH.Session:revoked`** |
| 用户不存在/已删除 | `restoreUser` 抛出 | `AUTH.User:unavailable` |
| 账号或密码错 | `login` 抛出 | `AUTH.Credentials:invalid` |

意义：`Token:expired` 未来可静默刷新；`Session:revoked` 说明密码被改/被强制下线，**必须重新登录**。

</details>

**Q8.3** `restoreUser` 里去掉了 `deletedAt: null`，一个被**软删除**的用户会怎样？（他的 token 还没过期）

<details><summary>提示与参考答案</summary>

**参考答案**：他的**会话继续有效**——`restoreUser` 能查到该用户，不抛 `AUTH.User:unavailable`，请求被放行，权限照旧是删除前的角色权限。

两处措辞要收紧：不是"能重新登录"（`login` 接口自身也有 `deletedAt: null`），而是"**已登录的会话继续有效**"；不是"错误的权限"，而是"**删除前的权限照旧**"。

结论沉淀：**软删除只是标记，能否"立即生效"完全取决于每个查询有没有过滤它。** 所以 `deletedAt: null` 必须出现在 `login`、`restoreUser`、`ownedResume`（简历本人 + `workspace.user`）等处。

延伸：`ownedResume` 里检查 `workspace: { user: { deletedAt: null } }` 表面冗余（主人自己被删时 `restoreUser` 已拦住），实为**纵深防御**——若将来出现"管理员代操作"入口，或 Service 被内部脚本直接调用（不经过 HTTP 鉴权链），这层仍能兜住。

</details>

## 第 9 组 · 元问题与判据

**Q9.1** 两个"防御性写法"：`nextId` 的 `while` 查重被删掉了，而 `count !== 1` 被保留。判据是什么？

<details><summary>提示与参考答案</summary>

**参考答案**：

| 写法 | 防御的对象 | 判定 |
| --- | --- | --- |
| `nextId` 的 while 重试 | **理论上不可能**（uuid 碰撞） | 删掉，用注释交代为什么不查重 |
| `count !== 1` | **当前约束下不可能**（UNIQUE 保证），约束一变就会发生 | 保留，作为显式断言 |

> **"不可能"要分两种**：数学上不可能（删）、以及"靠某个约束才不可能"（留，并让它显式）。
> 第二种防御的价值不在今天，而在**别人改掉那个约束的那天**。

另外：真正的兜底网是 `buildResumeDocument` 末尾的 `resumeDocumentSchema.parse`（会报"文档 ID 重复"），生成侧的查重是**在网之前又织一张网**。

</details>

**Q9.2** 把 `schemaVersion` 从 1 升到 2，需要改哪几处？已发布/已分享的内容怎么办？

<details><summary>提示与参考答案</summary>

**参考答案**：

**要改三处**：① 契约的 `z.literal(1)` → 联合（`z.discriminatedUnion('schemaVersion', [v1, v2])`，不能直接替换，否则旧数据全部读不出来）＋ 新增升级函数；② 迁移里的 CHECK 约束（`"schema_version" = 1` 及与 `document->'schemaVersion'` 的一致性）；③ `buildResumeDocument` 的输出。

**已发布内容**：区分两类——

| 类型 | 策略 |
| --- | --- |
| 草稿（仍在编辑的"活"文档） | **读取时升级**：库里存 V1，读出时转成 V2 |
| 发布 / 分享（对外的"承诺"） | **冻结快照**：发布时冻结为不可变副本，自带 `schemaVersion`，不随代码升级而变 |

这正是 `docs/dev/03` §4「发布快照」要解决的问题之一。

</details>

**Q9.3** `create` 里为什么写 `schemaVersion: createResumeDto.document.schemaVersion`，而不直接硬编码 `1`？

<details><summary>提示与参考答案</summary>

**参考答案**：**单一事实源 + 派生优于复制。**

文档已经过 `z.literal(1)` 校验，值必然合法，从它派生就不用维护第二处真相。硬编码 `1` 会形成第二个"真源"，将来升 V2 要同时改契约和 Service——而迁移里那条 CHECK 约束（要求列值与文档内值一致）存在的意义，正是**防止这两处漂移**。

（另注意区分：`schemaVersion` 是结构版本常量，**不会自增**；每次保存 +1 的是 `revision`。）

</details>
