## 1. 要解决的问题（C 方案）

现在的创建入口要求调用方**自己拼出一份完整合法文档**：

```ts
// packages/common/src/resume/document.ts（现状）
export const createResumeSchema = z.strictObject({
  name: resumeNameSchema,
  locale: z.string().min(1).max(20).regex(/^[A-Za-z0-9-]+$/),
  document: resumeDocumentSchema,   // ← 必须是完整 V1 文档
})
```

而 `resumeDocumentSchema` 的门槛相当高，调用方必须同时满足：

| 约束 | 出处 | 对"最小输入"的阻碍 |
| --- | --- | --- |
| `content.sections` 1～30 项 | `document.ts` | 至少要造 1 个模块 |
| **恰好一个** `type: 'profile'` | `superRefine` | 必须造对类型 |
| `display` 七块（brand/layout/sections/options/theme/background/style）**全必填** | `document.ts` | 必须补全套展示配置 |
| `display.sections.order` **必须完整覆盖所有模块** | `superRefine` | order 漏一个模块就失败 |
| 文档内所有 `id` **唯一** | `superRefine` | 手工拼容易撞 ID |
| `profile` 的 `headline` / `summary` / `hero` / `infoItems` / `links` / `interests` / `stats` / `gallery` 全必填 | `profileData` | 只填姓名根本过不去 |

**C 方案**：允许调用方只给**最小、稀疏**的内容（例如"姓名 + 工作年限 + 一段经历"），
由**服务端**把它补全成一份合法的完整文档再入库。

**收益**：创建门槛从"必须理解整个文档契约"降到"填几个字段"；
将来 admin 的上传 → AI 生成、以及从 0 创建，都落在同一个入口上。

## 2. 四点结论

### 2.1 `document` 仍必传；`schemaVersion` 不出现在创建输入里，由服务端注入

- **`document` 仍然是必传字段**（不是可选），变的只是它的**形状要求**：从"完整文档"放宽到"稀疏输入"。
- **`schemaVersion` 从创建输入中移除**，由服务端固定写入 `1`。
  - 理由：`schemaVersion` 是**服务端契约的版本标识**，不是用户的输入内容。调用方不该知道、也不该决定入库文档是哪个版本 —— 否则客户端可以塞一个服务端不认识的版本。
  - **类比 token**：登录后的接口都自动带 `Authorization`，不需要每个调用点各自拼一遍；`schemaVersion` 同理 —— 它是**由服务端按当前契约决定的**，客户端不必（也不应）手写。
  - **入库的文档仍然是自描述的**：写库时补上 `schemaVersion: 1`，所以 `resumeDocumentSchema`（读路径的校验）**一行不改**，`saveDraft` 仍按完整文档校验。

### 2.2 最小输入的 `sections` 最少 1 项，且必须**恰含一个** `type: 'profile'`

- 现有 `resumeDocumentSchema` 的 `content.sections` **已经是 `min(1)`** —— 这条不是新增约束，是**继承**下来的。
- `profile` 用 `z.literal('profile')` 锁定：**其它模块类型可以没有，`profile` 不能没有，也不能有两个**。
  - 理由：`profile` 承载姓名/头衔/联系方式等"简历的锚点"，没有它页面无法成立（`superRefine` 本来就要求"恰好一个基本信息模块"）。
- 其余六类模块（`highlights` / `education` / `experience` / `projects` / `capabilities` / `evaluations`）**可选、可多实例**（同类型允许多个，例如公司项目与开源项目各一个 `projects`）。

### 2.3 条目数组允许空数组；`profile.name` 必填，其余可空/可默认

- **所有"条目数组"只设 `max`、不设 `min`** —— 没有内容自然为空数组，这与现有契约一致
  （`capabilityGroupSchema` 的注释已写明"空数组合法，但省略这些必填数组不合法"）。
- 因此稀疏输入的语义是：**结构可以空，但字段不能缺** —— 调用方给 `interests: []` 是合法的，
  直接省略 `interests` 由补全函数补上。
- **`profile.name` 是唯一真正的必填内容**（`text` = `z.string().max(500)`，但空串无意义，补全时要求非空）。
- `profile` 其余字段（`headline` / `summary` / `avatarText` / `availability` / `hero` / 各数组）可省略，补全为
  空串 / 空数组 / 空 hero。

**「工作年限」这类基础信息落在 `profile.infoItems`**（P2 已拍板）：用 `kind` 作自由文本分类键
（如 `kind: 'years'`），`label` / `value` 存展示文案 —— **不新增 `profile` 一等字段**，因此不动
`resumeDocumentSchema`，已有文档不受影响。`display.options.showYears` 这个既定开关继续控制它是否展示。

### 2.4 稀疏 schema 与补全函数放 `packages/common/src/resume`，三端共用一份契约

- 位置：`packages/common/src/resume/`（与 `document.ts` / `capabilities.ts` 同目录），并从 `src/index.ts` 导出。
- **消费者至少有两个，且必须一致**：
  1. `apps/server` 的 `resume.service.create`（服务端补全，权威实现）；
  2. `apps/admin` 的创建页（客户端即时预览/校验输入是否可提交）。
- 判据沿用 `packages/common` 的既有约定：**能脱离 Vue 运行 → 放这里**。补全是纯函数（无模板、无 Nuxt UI），符合。
- 命名建议：`resumeDraftInputSchema`（稀疏输入）+ `buildResumeDocument(input)`（补全函数）。

## 3. 默认补全规则（`buildResumeDocument`）

输入：稀疏输入；输出：**已通过 `resumeDocumentSchema.parse` 的完整文档**。

### 3.1 模块补全

- `profile` 模块：保留用户给的部分，缺的字段补默认（`headline: ''`、`summary: ''`、`hero` 补四个空项、各数组补 `[]`）。
- `profile` 模块的 `id` / `title`：`id` 若未给则生成；`title` 若未给则用默认标题（沿用 web 侧 `resume-document.ts` 的 `titles` 表，如「基本信息」）。
- 其余模块（若调用方给了）：**原样保留**，只补该模块内部缺的可选数组（如 `experience.items[].achievements` 补 `[]`）。

**六类空模块一律补齐**（P3 已拍板）：

最小输入（只有 `profile`）会被补成 **7 个模块**的完整文档，让用户一进编辑页就能看到全部模块位：

| 模块 | 补的空数据（必须满足各自 schema） |
| --- | --- |
| `highlights` | `{ items: [] }` |
| `education` | `{ items: [] }` |
| `experience` | `{ items: [] }` |
| `projects` | `{ items: [] }` |
| `capabilities` | `{ groups: [], ratingScale: { min: 0, max: 5, basis: '' }, dimensions: [] }` ⚠️ `ratingScale` 是必填对象，不能省 |
| `evaluations` | `{ items: [] }` |

每个补齐模块都需要自己的 `id`（生成，见 §3.3）、`title`（默认标题）、`type`（固定）。

> ⚠️ **补齐方案下最容易踩的坑**：新造的 6 个模块 id **必须同时进入 `display.sections.order`** ——
> `superRefine` 要求 `order` 完整覆盖所有模块，漏一个就直接 `parse` 失败（详见 §3.4 第 2 条）。
> 7 个模块远低于 `sections` 的 30 项上限，不会触发上限。

### 3.2 `display` 默认值

`display` 七块全部必填，补全时按以下默认：

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `brand` | `{}` | 四个字段皆可选，空对象合法 |
| `layout` | `{ mode: 'single', splitSide: 'left', stickySide: false, sideWidth: 'compact' }` | 单栏最安全 |
| `sections.order` | **按 content.sections 的实际顺序逐项列出** | ⚠️ 必须完整覆盖，见 §3.4 |
| `sections.slot` / `hidden` / `overrides` | `{}` / `[]` / `{}` | 允许只配部分模块 |
| `options` | 六个开关 **全 `true`** | 默认展示全部信息 |
| `theme` | 取 web `resumeThemePresets` 的首个预设（当前为 `blue` / 蓝色简约），`mode: 'light'` | 需 9 色 × light/dark 两套 |
| `background` | `{ type: 'plain', textureId: 'none', image: { url: '', fit: 'cover', overlay: 0, blur: 0 } }` | 纯色底 |
| `style` | `{ id: 'minimal' }` | `minimal` / `standard` / `pro` 三选一 |

### 3.3 ID 生成与**文档内唯一**

- `resumeIdSchema` 只校验格式（`/^[A-Za-z0-9_-]+$/`，1～100 字符），**不负责生成** —— 生成策略由补全函数承担。
- 生成用 `globalThis.crypto.randomUUID()`：**浏览器与 Node ≥ 20 都可用**（本机 Node v22.18.0 已实测 `typeof globalThis.crypto.randomUUID === 'function'`），且 uuid 的 `-` 符合 `resumeIdSchema`。
- ⚠️ **`superRefine` 要求文档内所有 `id` 唯一** —— 所以补全时必须：
  1. 先收集**用户已给的全部 id**；
  2. 生成新 id 时**跳过已用集合**（uuid 实际不会撞，但契约要求保证，故仍显式校验）；
  3. 生成后再跑一次 `resumeDocumentSchema.parse` 兜底。
- ⚠️ **注意**：**不要**按"每次调用都生成新 id"来实现幂等归一 —— 若输入已是完整文档，
  补全应**保留原有 id**（否则 `order` / `overrides` 与 id 的引用会跟着变，等于重写文档）。

### 3.4 必须同时满足的跨字段规则（照抄自 `superRefine`）

补全函数**必须**让产物满足这些 `superRefine` 规则，否则 `parse` 当场失败：

1. `content` 内所有 `id` 唯一（§3.3）。
2. `display.sections.order` **完整包含所有模块、无重复** —— 长度 = 模块数、内容 = 模块 id 集合。
3. `display.sections.hidden` 无重复；`hidden` / `slot` / `overrides` 的键**必须引用真实模块**。
4. `content.sections` 中 `type === 'profile'` 的模块**恰好一个**。
5. `overrides[id].capabilities` **只能挂在 `capabilities` 模块上**，且 `dimensionIds` 必须来自该模块的 `dimensions`（补全默认不产出 `overrides`，此条仅供将来参考）。
6. 文档 `JSON.stringify` 的 UTF-8 字节数 ≤ **100 KiB**（稀疏输入不会触发，但补全后应例行检查）。

## 4. 兼容边界：新输入是完整文档的**超集**

⚠️ **这是本设计最需要守住的一条**，写错会直接打崩现有 web 创建链路。

- **稀疏 schema 必须是「完整文档」的超集**：完整文档能过、稀疏输入也能过。
  - 实现要点：稀疏 schema 里 `schemaVersion` **可选**（或干脆不接受、由补全忽略），
    其余字段逐字段用 `optional()` / 默认值放宽 —— **不能**用 `strictObject` 把完整文档的字段拒之门外。
- **`buildResumeDocument` 是幂等归一**：
  - 输入**完整文档** → 原样返回（保留 id、display、schemaVersion 归一为 1）；
  - 输入**稀疏输入** → 补全为完整文档。
  - 两种输入都得到合法 `resumeDocumentSchema` 产物。
- **现有 web 客户端（仍发 `schemaVersion: 1` 的完整 `document`）不被打破**：
  `createResumeSchema` 换成稀疏输入后，老的完整文档仍能通过（因为超集）。
- ⚠️ **反例（必须避免）**：如果稀疏 schema 写成"严格替换"（用 `strictObject` 拒绝 `schemaVersion`
  或完整文档里的字段），那么现有 web 的创建请求会直接 **400**。

## 5. 已拍板结论（原待确认项）

以下三项已由 Owner 确认，作为实现的既定前提：

| # | 问题 | **结论** | 理由 |
| --- | --- | --- | --- |
| **P1** | 创建时 `name` / `locale` 是否仍必填？ | **保持必填** | 它们是简历列表里的标识，由用户显式给出更可控；本轮只放宽 `document` 的形状，顶层元信息不动 |
| **P2** | 「工作年限」落哪个字段？ | **`profile.infoItems`** | `kind` 作自由文本分类键（如 `years`）；不新增一等字段，因而不动完整文档契约、已有文档零影响。`display.options.showYears` 继续控制显隐 |
| **P3** | 补全时是否补齐六类空模块？ | **补齐**（见 §3.1） | 让用户一进编辑页就看到全部模块位，符合"从 0 创建"的直观感受；代价是最小输入产出 7 个模块（含 6 个空模块） |

## 8. 验证方式

| 验证 | 期望 |
| --- | --- |
| 最小输入（仅 `name` + 空 `profile`） | 补全成功，产物通过 `resumeDocumentSchema.parse` |
| 缺 `profile` / 缺 `profile.name` / 空 `sections` | 分别报错（由 §2.2 的 `z.literal` 与 `min(1)` 保证） |
| 空数组 | 合法（§2.3） |
| **完整文档输入** | 走补全后**幂等归一**，与原文档等价（§4） |
| 现有 web 创建链路 | 不回归（仍发完整文档，仍 200/201） |
| `saveDraft` 并发契约 | 不受影响（读路径 schema 未变） |
