## 3. 第一轮：从需求推导内容模型

### 3.1 原始目标

让求职者自行组织能力内容，以简洁概览和可选评分展示，支持编辑、排序，并在刷新后恢复。

从全栈开发视角，先推导数据和规则，再写页面：

| 用户需求 | 模型要求 |
| --- | --- |
| 前端、全栈、AI 或其他职业能力可自定义 | 分组标题属于用户内容，不写死 |
| 一组包含多项能力 | 分组内使用条目数组 |
| 改名、排序、删除、添加实践说明 | 分组/条目有稳定 ID 和明确字段 |
| 图表降低文字负担 | 独立自评维度，不强迫每条技能评分 |
| 自行评分 | 可留空，有统一量尺和自评依据 |
| 同样内容切换展示方式 | 内容与展示配置职责分开 |
| 多份简历面向不同岗位 | 能力内容归属具体简历的草稿 |

### 3.2 用户自定义内容，程序固定字段职责

Owner 原先设想类似 `capability.frontend: string[]`，动态键承载分组。这个结构能够承载文字，但改名、非技术职业扩展、条目说明和身份追踪会更困难。

当前模型采用对象数组。以下为教学简化示例，省略完整文档和必填的评分字段，不能直接当作创建接口请求体：

```ts
{
  id: 'capability-module-1',
  type: 'capabilities',
  title: '个人能力',
  data: {
    groups: [
      {
        id: 'group-1',
        title: '前端核心能力',
        summary: '能够独立交付复杂前端应用',
        items: [
          {
            id: 'item-1',
            name: 'Vue 生态',
            description: '具备 Vue2 → Vue3 迁移经验',
            evidenceLinks: []
          }
        ]
      }
    ]
  }
}
```

- `type`：程序据此选择编辑器与渲染组件；当前固定为 `capabilities`。
- `id`：对象身份，改名和排序后保持稳定。
- `title` / `name`：给读者看的名称，由用户编辑。
- `description` / `summary` / `evidenceLinks`：详细说明、概述和佐证。

源码入口：[能力契约](../../packages/common/src/resume/capabilities.ts)。

### 3.3 条目、自评与展示的职责

`groups` 说明有哪些能力、做过什么；`dimensions` 选择少量维度表达自评；`ratingScale` 说明量尺和依据。维度可通过 `groupId` 关联一个分组，也可以独立存在。

`score: null` 表示没有填写；`score: 0` 表示用户明确给零分。二者不能混用。当前不根据文字推断评分，也不自动求平均分或做岗位排名。

`content` 与 `display` 在模型中分开，但当前作为同一草稿文档共同保存。职责分开不必等于拆成不同表。

### 3.4 练习与真实纠正

练习：分组改名、移到最后、隐藏个人能力模块分别改哪里？

Owner 复述：

1. 改名仅改 `data.groups[index].title`，模块外层不变。
2. 分组移动不改数据，修改配置里的 `order`。
3. 隐藏只改 visibility 相关配置，内容不变。

校准：第 1、3 项成立，第 2 项需要区分层级。AI 上一轮对排序的讲解没有明确区分这两层，容易让人理解为所有顺序都单独配置。

| 操作 | 实际修改位置 |
| --- | --- |
| 分组改名 | `section.data.groups[index].title` |
| 分组排序 | `section.data.groups` 数组排列 |
| 条目排序 | `group.items` 数组排列 |
| 整个模块排序 | `display.sections.order` 中的模块 ID 顺序 |
| 整个模块隐藏 | `display.sections.hidden` 中加入模块 ID |

数组重排时，元素内容和身份可不变，但数组顺序确实改变。未来若同一份内容需要多套内部排列，可以另行设计独立顺序配置；本轮未实现。

## 4. 第二轮：表里的记录与文档里的数组

### 4.1 Owner 的复述与疑问

Owner 理解为「单用户多份简历，所以 resume_drafts 是数组或者 Map；表层有版本、display，再有 content/sections」，并追问：既然前端按对象取字段，为什么结构变化还需要解析或迁移？

校准：数据库表里的多条记录，与一条记录里面的嵌套数组是两个层次。`resume_drafts` 是表；读取单份草稿返回对象，列表接口可返回数组，不必把整张表建成一个数组或 Map 字段。

### 4.2 三表职责

| 表 | 职责 | 示例 |
| --- | --- | --- |
| `resume_workspaces` | 用户的逻辑简历空间 | user-1 的空间 |
| `resumes` | 某份简历的稳定身份与元信息 | 前端岗位版 / AI Agent 岗位版 |
| `resume_drafts` | 某份简历唯一的当前草稿 | 对应文档与 revision |

一名用户拥有两份简历时，当前模型是一个空间、两条 Resume、两条 ResumeDraft。这里「两份简历」与将来的「同一简历多个发布版本」要区分。

空间是逻辑容器，不是数据库磁盘容量。内部名称存 `resumes.name`，语言存 `resumes.locale`；正文姓名与能力等存草稿文档。将来加入 AI 或其他字段时，需要先明确职责并更新契约，当前严格 Schema 不接受未声明字段。

```text
resume_drafts 中的一条记录
  ├─ resumeId / schemaVersion / revision / updatedBy / updatedAt
  └─ document（JSONB）
       ├─ schemaVersion
       ├─ content（对象）
       │    ├─ sections（模块对象数组）
       │    └─ footer
       └─ display（对象）
```

关系表承担所有权、身份、外键和唯一约束；JSONB 承载嵌套、自定义内容与整体读取。代价是单个条目修改仍提交完整文档，未来跨简历检索/统计能力会比独立能力表复杂。

### 4.3 schemaVersion 为什么必要

合法 JSON 不代表符合组件期待的结构。例如旧条目是 `['Vue', 'React']`，新条目是 `[{ id, name, description }]`；两者都能解析，但新组件读取 `item.name` 时，旧字符串没有这个字段。

`schemaVersion` 是结构识别入口，不会自动迁移。支持旧结构时，仍需编写识别、转换、补默认值和校验逻辑。当前 V1 Schema 仅接受版本 1，迁移 SQL 也约束版本为 1；未来升级需同步修改这些约束，当前没有任意版本自动迁移能力。

更通用的设计指字段职责清晰、变更有转换路径，不是把所有东西都改为无约束 Map。

### 4.4 三种版本概念

| 概念 | 变化条件 | 当前能力 |
| --- | --- | --- |
| `schemaVersion` | 需要区分的文档结构升级 | 当前固定为 1 |
| `revision` | 每次成功保存 | 并发条件更新，成功后递增 |
| 发布版本 | 将来执行发布形成固定结果 | 未实现 |

练习：修改三条能力描述并成功保存，三个字段怎样变化？

Owner 回答：`resumeId` 不变，说明简历指向未变；`schemaVersion` 不变，因为只是改内容；`revision` 要变。

结论：正确。revision 更准确称为「草稿并发版本号」，并不代表旧内容已经被保存为历史版本。

### 4.5 新建与复制简历

Owner 提出 Duplicate：复制草稿再修改，本质是新增而不是覆盖。

校准：复用本人 workspace，新增 Resume（新 resumeId）与 ResumeDraft（关联新 resumeId），新草稿 revision 从 1 开始；两个创建在事务内完成。当前 Duplicate 尚未实装。

内部模块/分组/条目 ID 不一定全部重建：当前只要求在各自文档内唯一，独立文档可保留相同内部 ID；未来差异对齐可能利用这种对应关系。若复制到同一文档内，则需重新生成 ID 并更新关联引用。

## 5. 第三轮：并发版本与编辑追踪

Owner 提出借鉴 Pinia/Redux，追踪用户修改，便于编辑与溯源。

两窗口同时读到 revision 3 时：A 以 expectedRevision 3 保存成功，数据库递增到 4；B 再以 3 保存，条件不匹配，返回 409。当前更新同一条草稿，无法仅凭 revision 还原旧正文。

| 能力 | 目的 | 可能的实现位置 |
| --- | --- | --- |
| 撤销/重做 | 撤回刚才的错误操作 | 前端工作副本和操作历史 |
| 草稿历史 | 查看昨天修改、恢复旧内容 | 后端历史快照或差异记录 |
| 发布版本 | 固定发给某公司的内容 | 后端不可变发布快照 |

状态管理库可承载状态，但不会自动提供刷新后仍可访问的用户编辑历史；开发者工具的追踪也不等于产品历史功能。

候选取舍：完整快照恢复简单、存储较多；差异记录可能更小，但重放、结构升级与恢复更复杂。结合当前简历体积，可优先讨论有数量/期限限制的快照，再用稳定 ID 对齐新增/删除/修改/移动。保存节点需定义，不能默认每次按键写库。

这是后续候选，未批准新表或接口，当前未实现历史、撤销/重做或发布。

## 6. 第四轮：主键、外键与唯一草稿

源码入口：[Prisma Schema](../../apps/server/prisma/schema.prisma)、[三表迁移](../../apps/server/prisma/migrations/20261011090000_resume_drafts/migration.sql)。

当前 `ResumeDraft.resumeId` 同时是主键和指向 `Resume.id` 的外键：

- 主键：不能为空且不能重复，一份简历最多一条当前草稿。
- 外键：必须指向存在的简历，不允许悬空草稿。
- 事务创建：外键不保证每份简历一定有草稿，创建接口把简历和草稿一起创建，避免只完成其中一步。
- `updatedBy` / `updatedAt`：最近操作者与时间，不能替代完整历史。

### 6.1 删除是否会影响复制出来的简历

Owner 顾虑：外键指向已存在 Resume，删除那份记录后，复制出来的是否也会丢失？随后想到该表是草稿，删除简历及对应草稿似乎合理。

校准：外键引用的是「本草稿所属的新简历」，并非复制来源。复制后的 B 拥有自己的 Resume 和 ResumeDraft，当前模型没有 B 依赖 A 的来源外键；删除 A 不会因为这个归属外键而删除 B。

删除动作取决于引用动作，不能只看到外键就推断级联：

| 动作 | 父记录被物理删除时 |
| --- | --- |
| 当前 `onDelete: Restrict` | 有草稿引用时阻止删除简历 |
| `onDelete: Cascade` | 自动删除引用它的草稿；当前未采用 |
| `onDelete: SetNull` | 将外键置空，要求字段可空；当前未采用 |

本轮没有简历删除 API。`Resume.deletedAt` 表达软删除，标记字段而非执行 SQL DELETE，不触发外键删除动作；本人草稿接口会过滤已软删除简历。未来物理清理需另行设计删除顺序、历史/分享关联和事务，不能直接认为「删简历会自动删草稿」。

### 6.2 改为独立草稿主键的练习

练习：ResumeDraft 新增自动生成的 id 作为主键，resumeId 只保留普通外键，还能保证一份简历最多一条当前草稿吗？

Owner 回答：不能；是否要把 resumeId 与新增 resume_draft_id 关联？

校准：归属关联已经由 resumeId 外键承担，需要补的是 `resumeId @unique`。独立主键保证每条草稿身份不同；外键保证简历存在；唯一约束保证同一 resumeId 不重复。

教学候选示例，不是本轮实际表结构变更：

```prisma
model ResumeDraft {
  id       String @id @default(cuid())
  resumeId String @unique
  resume   Resume @relation(fields: [resumeId], references: [id], onDelete: Restrict)
}
```

上面只展示关键约束，省略 document 等字段；配套 Resume 反向关系也需存在。当前复用 resumeId 作为主键已经满足需要，无须额外增加 id。

仅建 `@@unique([resumeId, id])` 不够：`draft-1/resume-A` 与 `draft-2/resume-A` 是不同组合，两条都可以写入。要限制的是 resumeId 本身唯一。

待 Owner 巩固：如果只保留 id 主键与 resumeId 外键，没有 resumeId 唯一约束，连续写入 `id=draft-1, resumeId=resume-A` 与 `id=draft-2, resumeId=resume-A`，数据库会接受几条？为什么？

### 6.3 Owner 复述：关系字段与草稿变化

Owner 进一步复述：`id` 可以理解为一条文档记录的身份，`resumeId` 表示它属于哪份简历，`@unique` 表示同一份简历只能对应一条草稿；如果两个草稿 ID 不同但 `resumeId` 都是 `resume-A`，可能是在操作同一份简历内容。

校准：前半段正确，但需要区分数据库记录与记录里的正文。`ResumeDraft.id` 标识草稿表中的一行；`resumeId` 是真正的外键列；`resume` 是 Prisma 关系字段，方便读取所属的 `Resume`，不是简历正文列；正文存放在 `document` JSONB 中。`onDelete: Restrict` 也不是“删除时把简历内容删除”，而是父级 `Resume` 仍被草稿引用时阻止物理删除。

没有 `resumeId @unique` 时，`draft-1/resume-A` 与 `draft-2/resume-A` 会被数据库接受为两行，因为主键不重复且外键都指向存在的 `resume-A`。第二个 ID 只是另一条记录的身份，不自动表示“内容变了”，也不是自动发布；只有应用明确写入不同的 `document`、历史快照或 revision 语义，才能说明它代表了什么业务变化。

当前产品选择的是“一份简历一条当前草稿”，所以继续使用 `resumeId` 同时作为主键和外键；将来做历史快照时，再把模型扩展为独立草稿 ID、多条记录和明确的历史版本字段。

## 7. 博客取材与后续追加

### 7.1 共享契约练习：字段形状与跨字段规则

进入共享契约学习时，Owner 对下面的能力数据进行了判断：未声明的 `extraField` 是多余字段，`score: 8` 超过 0～5 量尺，`items` 可能需要至少一项，并将前两类问题都归为字段错误。

校准结果如下：

| 数据 | 结论 | 原因 |
| --- | --- | --- |
| `extraField` | 错误 | `z.strictObject` 不允许 schema 未声明字段 |
| `groupId: 'backend'` | 错误 | 字符串格式本身合法，但 `superRefine` 要求它引用当前 `groups` 中真实存在的 ID；这里只有 `frontend` |
| `score: 8` | 错误 | `ratingScale.max` 为 5，评分超出统一量尺；这是跨字段业务规则 |
| `items: []` | 合法 | 当前只设置最多 20 项，没有 `min(1)`；用户可以先建空分组 |
| `dimensions: []` | 合法 | 当前只设置最多 20 项，没有 `min(1)`；可以暂不配置评分维度 |

因此，`extraField` 属于字段形状/未知字段错误；`groupId` 的格式检查通过但引用关系失败；`score` 属于跨字段规则错误。`items` 和 `dimensions` 的空数组不是错误，不能把“数组字段存在”误读成“数组必须非空”。

这轮还为 `packages/common/src/resume/capabilities.ts` 与 `document.ts` 补充了 TSDoc，明确记录运行时 Zod 校验、编译期 TypeScript 类型、模块联合类型、跨字段规则、并发版本和未评分 `null` 的职责边界。后来发现数据库使用 Prisma cuid、编辑器使用 UUID，而旧 ID 上限为 20，于是将共享 ID 上限统一为 100，并补充回归测试与 OpenAPI 同步；`@rs/common` 类型检查、16 项测试和目标文件格式检查均通过。

## 8. 保存请求契约：客户端期望与数据库事实

记录日期：2026-10-13（Asia/Shanghai）。本轮只阅读已有实现并追加学习记录，没有修改业务代码或数据库。

源码入口：[保存请求 schema](../../packages/common/src/resume/document.ts)、[Web 请求封装](../../apps/web/layers/11-public-resume/app/apis/resume-draft.ts)、[草稿 Service](../../apps/server/src/resume/resume.service.ts)。

前面的练习回答了「文档是否合法」，本轮继续回答「能否用这份文档替换当前草稿」。真实请求是 `PUT /api/resume/:id/draft`，请求体由 `saveResumeDraftSchema` 约束：

```ts
export const saveResumeDraftSchema = z.strictObject({
  expectedRevision: z.number().int().min(1).max(2147483646),
  document: resumeDocumentSchema,
})
```

简历 ID 放在 URL；document 提交完整正文和展示配置；expectedRevision 是前端最后读取或成功保存后收到的版本。用户归属从认证身份获取，不能由请求体自行指定。schemaVersion 在 document 中，只改正文无需递增结构版本。

| 字段 | 职责 | 谁维护 |
| --- | --- | --- |
| expectedRevision | 声明本次修改基于哪个草稿版本 | 前端使用上次响应中的 revision |
| revision | 数据库当前草稿的并发版本 | 后端成功保存时递增并返回 |
| schemaVersion | 文档结构采用哪个版本 | 文档契约与结构迁移逻辑 |

Zod 可以确认 expectedRevision 是合法整数，却无法确认它与数据库当前版本一致。Service 在事务内检查本人归属，再执行带 revision 条件的原子更新：匹配 resumeId、归属和 expectedRevision 才替换 document，并将 revision 加一；更新数量不等于 1 时返回 409 冲突，不覆盖当前草稿。

不能先单独读取版本、在应用中比较后再无条件更新：比较与更新之间可能有另一个请求写入。版本条件必须与实际更新一起交给数据库执行。

失败处理也属于契约：版本冲突时保留本地输入，重新读取并对比后再决定如何保存。直接把 expectedRevision 改成最新数字重试，会失去对其他窗口修改的审看，不能作为自动解决冲突的办法。当前没有实现自动合并或历史快照。

本轮练习（已由 Owner 回答并校准，记录日期 2026-10-13）：A、B 两个窗口都读取 revision=3。A 改标题并保存；B 改评分，仍基于原先读取的内容保存。

**问题 1**：A 应提交哪个 expectedRevision？成功后数据库 revision 是多少？

Owner 回答（原文）：*"A 应提交 revision = 3，成功后数据库 revision 为 4。"*

结论：正确。Service 的条件更新同时匹配 `resumeId` 与 `expectedRevision`，命中后 `revision` 递增 1。补充一点：返回的 `revision` 不是应用层用 `expectedRevision + 1` 算出来的，而是同一事务内重新读取的最终值，避免把更晚一次写入误当本次结果。

**问题 2**：B 提交 expectedRevision=3 时，后端应怎样处理？

Owner 回答（原文）：*"先拒绝，应该 3 已被 A 正在操作（所谓的加锁对吧？）。"*

结论：拒绝正确，机制理解需纠正——这里是**乐观并发控制**（optimistic concurrency control），**不是加锁**：

- 没有悲观锁、没有 `SELECT ... FOR UPDATE`、没有任何等待；B 的请求立即执行。
- B 拿到 409 不是因为"revision 3 正被 A 占用"，而是因为 **revision 3 已经不存在**——A 的更新已经把它变成 4，B 的版本前提过期。
- "判断与更新不可分割"由**单条原子 SQL** 保证：`UPDATE ... WHERE resume_id = ? AND revision = ?`。数据库在该语句执行期间确实持有行级锁以保证原子性，但那是引擎实现细节，作用范围仅限这条语句；"悲观加锁"的语义则是把锁持有到整个业务事务结束。二者不是一回事。

**问题 3**：B 能否只把 expectedRevision 改为 4 就自动重试？为什么？

Owner 回答（原文）：*"不能，因为同一时间如果有多条，那根本加不完，数据也会异常，增加不确定性。"*

结论：结论正确，理由需替换。真正的危害是**静默覆盖他人修改**：

- 保存提交的是**整份 document**，不是局部补丁。B 手上的 document 是它在 revision 3 时读到的旧副本。
- 若把 expectedRevision 改成 4 并提交成功，revision 变成 5，而 **A 改的标题会被 B 的旧副本覆盖**——表面"保存成功"，实际丢数据（last-write-wins 陷阱）。
- 409 的价值正在于它是个**信号**：告诉用户"别人动过这份数据了"。自动改写版本号重试就是把这个信号抹掉。
- 正确路径：保留本地输入 → 重新读取（拿到别人的新版本）→ 用户对比后决定如何合并 → 再保存。冲突判断交给人，不让程序自作主张。
- 关联：将来若要做自动合并，前提是能**按稳定 ID 做差异对齐**（文档内模块/分组/条目都有稳定 ID），否则整份替换无法安全合并。

本轮依据已有代码讲解，没有重新执行接口测试；接口与并发验证证据仍以 DAO-028 任务卡为准。

### 9.2 用例先行

按模块开发模板 §1，先写清"谁在什么条件下做什么"，再写文件。三个用例的实际边界：

| 用例 | 操作者 | 输入 | 成功 | 拒绝条件 |
| --- | --- | --- | --- | --- |
| 创建本人简历 + 唯一草稿 | `admin`/`super_admin` 且有 `Resume.Sections:edit` | `name`、`locale`、`document` | 201，元信息与草稿 rev=1 | 400 / 401 / 403 |
| 读取本人完整草稿 | 任意已登录用户，限本人 | 路径 `id` | 200 完整草稿 | 401 / 404（他人、已删除、不存在统一） |
| 按 revision 保存 | 同创建的写权限 | `id`、`expectedRevision`、`document` | 200 新 revision | 400 / 401 / 403 / 404 / 409 |

两个刻意决策：读不要求编辑权限；"他人的"与"不存在的"返回同一个 404，不泄露资源存在性。

### 9.3 模块边界 = 聚合边界 = 事务边界

`ResumeDraft.resumeId` 既是主键又是指向 `Resume.id` 的外键，数据层直接强制"一份简历最多一条草稿"。创建时两张表必须同时写入（`create` 的 nested write 在 `$transaction` 内），所以它们必须同属一个模块——若拆成 `resume` + `draft` 两个模块，创建用例的事务会横跨模块。

判据沉淀：**一个用例里必须原子完成的数据，属于同一个模块。** 模块按业务域或聚合切分，不按表或接口数量切分：`user` 管身份与会话，是另一个聚合，所以是另一个模块。

### 9.4 目录落地与模板的偏离

模板（模块开发模板 §2）要求 `dto/`、`repository.ts`、`errors.ts`、`README.md` 与模块 Guard；实际 `apps/server/src/resume/` 只有 `controller / service / module` 三个文件。每处偏离的理由：

| 模板要求 | 实际 | 理由 |
| --- | --- | --- |
| `dto/*.schema.ts` | 无 | 请求契约在 `@rs/common`（三端共享），在 server 重写会成为第二个真源 |
| `*.repository.ts` | 无 | 模板限定"仅查询复杂或需要复用时添加"；本模块查询简单，直接用 `PrismaService` |
| `*.errors.ts` | 无 | 错误码统一在 `common/error-codes.ts` |
| `README.md` | 无 | 说明落在 `docs/server/` 专题文档与 DAO-028 任务卡 |
| 模块 Guard | 无 | 权限检查写在 `ResumeService.assertEditable()`（代价见 §9.7） |

模板是默认形状而非必须全填；判断标准是"各层只负责什么"的职责表——只要职责不越界，文件少几个不是问题。

### 9.5 `@Global()` 的判据

`ResumeModule` 不写 `imports: [PrismaModule]`，因为 `PrismaModule` 标了 `@Global()`。其注释给出的判据是：**全应用唯一、且不承载业务语义**才用 `@Global()`（数据库连接满足）；`AuthModule` 这类业务模块不适用。

### 9.6 一次 `POST /api/resume` 的完整链路

```text
HTTP POST /api/resume
 ├─ TraceIdMiddleware            common/trace-id.middleware.ts      写 req.traceId
 ├─ JwtAuthGuard (APP_GUARD)     auth/jwt-auth.guard.ts             非 @Public() 交 Passport
 │   └─ JwtStrategy              auth/jwt.strategy.ts               验签 → restoreUser() 回查数据库恢复角色权限
 ├─ StandardSchemaValidationPipe main.ts                             createResumeSchema 校验 Body
 ├─ ResumeController.create      resume/resume.controller.ts        @Body + @CurrentUser
 ├─ ResumeService.create         resume/resume.service.ts           assertEditable → $transaction
 │   └─ PrismaService            prisma/prisma.service.ts           upsert workspace → create resume + draft
 │       └─ PostgreSQL                                              resumes / resume_drafts
 └─ ApiResponseInterceptor       common/api-response.interceptor.ts 包成 {code,data,message,timestamp,traceId}
                                    ↳ 抛异常 → ApiExceptionFilter（旁路接管）
```

顺序的含义：`traceId` 最先，失败请求也带追踪 ID；鉴权在管道之前，未登录的请求不消耗校验算力；校验在控制器之前，进入 Service 的 DTO 一定合法。Controller 只取参并调用 Service，响应形状由拦截器与过滤器统一，模块不自造第二套响应格式。

### 9.7 练习与校准

**练习 1**：`findDraft()` 为什么没调 `assertEditable()`？加上会怎样？

Owner 理解（原文）：*"反过来想……若不是管理员和超管就会报错，也就是说普通用户不能查看自己的草稿；查看应该是可以的，只限制修改和删除这一层。"*

结论：**正确**。补充两点精度。其一，`findDraft` 的保护机制是**所有权过滤**（`ownedResume()` 进入 `where`），不是资格检查；读操作靠"只能查到自己的"，写操作才叠加 `assertEditable()`。其二，加上会直接打掉"普通用户只读本人草稿"这个已实现能力（`useResumeDraft` 的 `canEdit` 只管写入，`load()` 不检查资格）。

措辞纠正：Owner 说的"没调按钮"应表述为"服务端检查点"——**后端没有按钮**。前端思维问"按钮谁能点"，后端思维问"接口谁能调"；按钮可被 curl / Apifox 绕过，所以权限必须落在服务端，UI 隐藏只是体验。

**练习 2**：`GET /resume`（本人简历列表）属于哪个模块？要新表吗？要 `assertEditable()` 吗？

Owner 理解（原文）：*"直觉上认为不属于 resume 模块，应该是一个新表？或者就在用户 user 表中多一个字段关联的 resumes，只是查看的话不需要 assertEditable。"*

校准：

| 问题 | Owner 判断 | 校准 |
| --- | --- | --- |
| 模块归属 | 不属于 resume 模块 | **属于** `resume` 模块：查的是同一个聚合根 `Resume`，只是另一种视图。模块归属看"数据和规则归谁"，不看有没有新接口 |
| 是否新表 | 应该是新表 | **不需要**：`Resume` 已有 `workspaceUserId` 与 `deletedAt`，一次 `findMany` 即可 |
| 表的关联方向 | user 表加字段关联 resolves | **方向反了**：一对多时外键必须在"多"的那一侧（`resumes.workspace_user_id`）。往 user 表塞数组会违反第一范式、无法建索引/外键/唯一约束，且 `restoreUser()` 每个请求都读 user 表，等于让鉴权热路径背负业务数据 |
| 是否要 `assertEditable` | 不需要 | 对。但**列表接口的所有权过滤比详情接口更关键**：漏掉 `workspaceUserId` 过滤就是全库越权读取（IDOR） |

**练习 3**：`ResumeSnapshot`（发布快照）该放 `resume` 模块还是新开模块？判据是什么？

Owner 理解（原文）：*"应该是一个模块；发布一定对应某个 resumeId，类似一个简历一份唯一草稿……一个发布对应一份简历这点我确定。"*

校准：第一环成立（快照确实会有 `resumeId` 外键），但**"有外键"推不出"同一模块"**。反例就在同一张表里：`ResumeDraft` 同时有 `resume_id → resumes` 与 `updated_by → users` 两个外键，却没人认为 draft 属于 user 模块。

判据是**事务边界与规则归属**：创建简历必须同时创建草稿（同一事务）→ 同模块；发布是独立动作（"把当前草稿冻结成不可变副本"），不与草稿编辑同事务，且有不可变性、版本号、分享 token、公开读取等自己的规则 → 倾向独立子域/新模块。

另一个纠正：**"一个发布对应一份简历"不是数据模型必然，而是产品选择**（也可以设计成"一个发布 = 多份简历合集"的作品集形态）。区分这两类，是后端思维的分水岭：

| 类型 | 例子 | 谁说了算 |
| --- | --- | --- |
| 结构必然 | 一对多时外键在"多"侧；`resumeId` 做主键→不可能两份草稿 | 关系代数 / 数据库引擎 |
| 业务约定 | "一份简历只有一份当前草稿"、"发布对应一份简历" | 产品决策，用约束或代码落实 |

### 9.8 本轮暴露的两个思维缺口

| 缺口 | 表现 | 修正口诀 |
| --- | --- | --- |
| A. 把"关联"当"归属" | "user 表加字段关联 resumes"、"有外键就同模块" | 外键管引用，事务管边界；一对多时外键在"多"方 |
| B. 把"产品约定"当"结构必然" | "一个发布对应一份简历这点我确定" | 先问"这是谁定的？换个产品还能成立吗？" |

接口写完后的四问（用例模板的实战版）：

```text
① 谁在调？        → 认证：有没有 token
② 对谁的资源？     → 授权：自己 / 别人 → 过滤条件 or 统一 404
③ 读还是写？       → 用 view / edit / delete 哪个权限
④ 拒绝返回什么？   → 400/401/403/404/409，且不泄露存在性
```

### 9.9 阅读中发现的两处待留心

- **权限检查是"约定"而非"强制"**：`resume.service.ts` 里 `create`（第 48 行）与 `saveDraft`（第 101 行）调用 `assertEditable()`，`findDraft` 第 83 行不调用（读操作，合理）。今天没问题，但将来新增第 4 个写方法时忘了调用就是越权。对比 `public.decorator.ts` 的注释："漏标一个接口的后果是需要登录（安全的那一侧）"——Guard + 元数据是**默认拒绝**，Service 内联检查是**默认放行**；`user` 模块已用 Guard 方案（`user-creation.guard.ts`）。是否统一为 `@RequirePermission(...)` + 通用 Guard，留待 §④ 讨论。
- **`permission-keys.ts` 的一条注释已过期**：其中"那边是 ESM 而 API 编译为 CJS"（指无法放进 `packages/common` 共享）在当前已不构成阻碍——`packages/common` 是 `"type": "module"`（ESM），`apps/server/tsconfig.json` 是 `module: commonjs`（产物为 `require("@rs/common")`），而 `resume.service.ts` 正是 `import { resumeDocumentSchema } from '@rs/common'` 跑通的。注释与文档会过期，读到"由于 X 所以不能 Y"时应先验证 X 是否仍成立。

## 10. HTTP 接入层：路由语义与参数校验

记录日期：2026-10-13（Asia/Shanghai）。本轮只阅读 [resume.controller.ts](../../apps/server/src/resume/resume.controller.ts)、[main.ts](../../apps/server/src/main.ts) 与 [API 约定](../server/01_API_约定.md)，未修改代码。对应第 9.1 节路线中的第 ② 段。

### 10.1 Controller 的职责边界

三个方法体都只有一行 `return this.resumeService.xxx(...)`，这是最重要的信号：

| Controller 负责 | Controller 不负责 |
| --- | --- |
| 声明路径与 HTTP 方法 | 业务判断（"这份简历归谁"） |
| 参数绑定与校验声明（`@Body({ schema })`、`@Param`） | 查数据库 |
| 调用 Service 并返回结果 | 组装响应格式（由拦截器统一） |

判据：Controller 里出现 `if`、`prisma.`、`try/catch` 都属于越界。

### 10.2 路由设计的三个决策

- `POST /resume` 而不是 `POST /resume/create`：REST 把动作放在 HTTP 方法里，不在路径里；混入 RPC 风格会让接口越写越乱。
- `GET/PUT /resume/:id/draft` 而不是 `/resume/:id`：草稿是简历的**子资源**，多写一段给未来的兄弟资源留位置（`/snapshots`、`/share`）。若写成 `/resume/:id`，将来加兄弟资源时"这个 id 下面是简历还是草稿"会失去区分。
- 保存用 `PUT` 而不是 `PATCH`：`saveResumeDraftSchema` 提交的是**完整 document**，`PUT` 的语义正是"用请求体替换目标的完整状态"。方法与契约必须匹配。

### 10.3 三个接入层动作

- `@Param('id', { schema: resumePrimaryKeySchema })`：路径参数也要过 schema。`resumes.id` 已改为 integer 自增，但 URL 参数天然是字符串，所以该 schema 先按 `/^\d+$/` 校验字符串、再 `transform` 成 number、最后 `pipe` 到整数范围校验；非法格式在进入 Service 前直接 400，不会让 `NaN` 直达数据库。**格式校验（400）与资源不存在（404）是两层。**（2026-10-13 更新：此前为 `resumeIdSchema` + `id: string`，详见 §11.2）
- `@Body({ schema: createResumeSchema })`：Nest 12 的 Standard Schema 管道，Zod schema 直接挂在装饰器上，由 `main.ts` 的全局管道执行。`exceptionFactory` 只返回 `messages[0]`，因此错误信息只显示第一条（避免一屏错误，代价是调试时易被第一条误导，可用 `safeParse` 看全集）。
- `@CurrentUser()`：`createParamDecorator` 从 `req.user` 取值，由 `JwtAuthGuard` 验签后写入。价值是类型安全（`currentUser: AuthUser`），避免 `req.user as any`。类型来自 `common/http-context.ts` 的 declaration merging。

### 10.4 练习与校准

**问题 1**：列出本人简历的发布快照，路径怎么写？

Owner 回答（原文）：*"路径写 GET /resume/snapshots，不关心草稿，只关心已发布的 / resume 模块是 resume，而快照应该可以发布多份去分享，所以不查具体 id，直接用 snapshots 复数，表示查所有。"*

校准：用复数表达集合**正确**，但**层级错了**，且对 `:id` 的理解有偏差。

```text
GET  /resume/:id/snapshots          列表（某一份简历的所有快照）
GET  /resume/:id/snapshots/:sid     详情
POST /resume/:id/snapshots          发布
```

- `:id` 指的是"**哪一份简历**"（父资源/归属），不是"哪一份快照"；带 `:id` 不等于查单个。列表与详情的区分在**最后一段**有没有 id。
- `/resume/snapshots` 会读成"系统级全部用户的快照集合"，是完全不同且危险的东西。
- "本人的"来自认证身份，不写进路径（Owner 默认理解正确）。
- 路径的父资源表达**归属**，不表达"你要查的数据"——快照列表不查 `resume_drafts`，但归属仍是某份简历。
- 进阶：**URL 空间 ≠ 模块边界**。按事务边界判据，快照可能独立成模块，但 URL 仍可挂 `/resume/:id/snapshots`（NestJS 里另一个模块的 controller 可写 `@Controller('resume/:id/snapshots')`）。

**问题 2**：`@Param` 校验失败 400、资源不存在 404，这个划分合理吗？统一成 404 有什么问题？

Owner 回答（原文）：*"不合理，我理解的，对于后端业务来说，Param 校验失败是坏请求这一类 400，而 404 属于路径请求错了，是另一层。"*（"不合理"指"不应该统一成 404"）

校准：方向正确，措辞需修正。400 是"请求本身有问题"，404 是"请求没问题但目标不存在"。而 404 其实有**两个来源**：

| 来源 | 例子 | errorCode |
| --- | --- | --- |
| 路由不匹配 | `/api/resumex/1/draft` | `Common.Route:notFound` |
| 路由匹配但资源不存在 | `/api/resume/xyz/draft` | `Resume.Draft:notFound` |

这正是 `errorCode` 存在的理由：同一状态码可由不同原因产生，所以前端按 `errorCode` 分支，不解析 message。若把格式非法也统一成 404，会把"客户端 bug"伪装成"数据问题"，是最浪费时间的调试陷阱。

**问题 3**：`PUT` 改 `PATCH` 但请求体不变，会有什么误导？

Owner 回答（原文）：*"PUT 理解上是全量替换。若是 PATCH 则是局部资源替换，若传整份 document 感觉有点越权……虽没有强行规定，但不合约定（感觉无法从概念上根上回答上来，现在都还没对后端理解成体系）。"*

校准：感觉正确，缺一条可推导的链条。框架是一句话：**HTTP 方法是对"服务端要做什么"的承诺，不是对"请求体长什么样"的描述。**

| | `PUT` | `PATCH` |
| --- | --- | --- |
| 服务端语义 | 用请求体替换目标的完整状态 | 把请求体应用到现有状态上 |
| 请求体要求 | 必须能独立表达目标的新状态 | 只需表达变化 |
| 幂等性 | 幂等 | 不保证幂等 |
| 重试 / 中间件 | 可安全重试 | 需谨慎 |

用 `PATCH` 传整份文档的三个具体后果：对基础设施撒谎（方法声明影响代理与重试行为）；对下一个开发者撒谎（看到 PATCH 会以为可传局部补丁）；契约与语义脱钩。

**完整因果链（本轮最有价值的沉淀）**：

```text
草稿用 JSONB 整存整取
  → "保存" = 整份替换
  → 用 PUT 才是诚实声明
  → 整份替换天然会覆盖他人的并发修改
  → 请求体必须带 expectedRevision
  → 冲突返回 409，交给用户决策
  → 不能自动改写 expectedRevision 重试（会静默覆盖，见 §8 问题 3）
```

从"存储决策"一路推到"错误处理策略"，每一环都是上一环的必然结果。

### 10.5 后端体系的三根支柱（对应本轮三题）

| 支柱 | 对应问题 | Owner 表现 |
| --- | --- | --- |
| 资源建模（REST、集合与成员） | 问题 1 | 复数表达正确，层级偏差 |
| 分层错误语义（谁错、错在哪层） | 问题 2 | 方向与措辞均正确 |
| 一致性（事务、并发、约束） | 问题 3 | 感觉正确，缺推导链条 |

### 11.1 C 方案：稀疏创建输入 + 服务端补全

源码入口：[document.ts](../../packages/common/src/resume/document.ts) 的 `resumeDraftInputSchema`（第 402 行）、`buildResumeDocument`（第 515 行）、`createResumeSchema`（第 614 行）；设计文档 `docs/dev/07_简历系统_最小创建输入与默认补全.md`。

**三条必须守住的设计边界**（源码注释原文归纳）：

1. **超集兼容**：稀疏 schema 必须接受「完整文档」（含 `schemaVersion` 与完整 `display`），否则现有 web 客户端仍发完整 document 会直接 400。实现手法：`schemaVersion: z.literal(1).optional()`、`display: displaySchema.partial().optional()`。
2. **跨字段规则仍然由完整契约兜底**：补全产物必须过 `resumeDocumentSchema.parse`，所以 `order` 在补全时按最终模块顺序重建。
3. **渐进放宽，不一次全放**：

```ts
const sparseSectionSchema = z.union([sparseProfileSection, resumeSectionSchema])
```

  只有 profile 走稀疏版（可省略 id/title/内部字段），其余六类沿用完整契约——「半截模块」属边缘用法，需要时再放宽。

**派生而非重写**（值得学的 Zod 手法）：

```ts
const sparseProfileData = profileData.partial().extend({ name: text, hero: profileHeroSchema.partial().optional() })
```

从完整 schema 派生（`.partial()`）再覆盖局部（`.extend()`），保证稀疏版与完整版不会各自漂移。

**补全函数的三个行为**：

- **幂等**：输入已是完整文档时保留其 id 与 display，只归一 `schemaVersion`。注释给出的理由——"按『每次调用都重新生成 id』实现会把 order / overrides 的引用一起改掉，等于重写文档"——正是 §9 所讲三层引用一致性的直接应用。
- **补齐**：六类可选模块缺失即补空模块（`emptySection`）；capabilities 即使无条目也必须给 `ratingScale`（量尺下限固定 0，上限取最小 5）。
- **兜底校验**：产物仍走 `resumeDocumentSchema.parse`，任何规则漏掉都会当场失败而不是写进库。

**Owner 的练习推演成为实现**：

| 本轮之前的练习 | 当时的校准 | 现在的实现 |
| --- | --- | --- |
| 练习 1：document 不能可选吧？schemaVersion 也得传吧？ | 需明确"能否省略 document"与"版本号谁提供" | `schemaVersion` 改为可选且被忽略，真实版本号由补全函数固定写 1；源码注释用的类比正是"登录后接口自动带 token" |
| 练习 2：sections 至少 1 项，且要恰有一个 profile | 正确 | `resumeDraftInputSchema` 的 superRefine 校验 `profileCount !== 1` |
| 练习 3：可以给空数组 | 正确 | `emptySection` 造空模块；`items: []` 合法但字段不可缺 |
| 练习 4：消费者是 admin 创建页与 server 的 resume service | 方向正确 | 补全函数放在 `packages/common`，server 的 `create` 直接调用（且刻意放在事务外：补全是纯计算） |

**一处可讨论的取舍**：`buildResumeDocument` 里的 ID 生成带显式查重循环——

```ts
const nextId = (): string => {
  let id = globalThis.crypto.randomUUID()
  while (usedIds.has(id)) id = globalThis.crypto.randomUUID()
  usedIds.add(id)
  return id
}
```

注释自认"uuid 实际不会撞，但仍显式查重"。收集输入已有 ID 是有效的（避免新生成 ID 与输入冲突）；但针对 uuid 碰撞的 `while` 循环属于防御性略过头——真正需要防的"输入内部自己重复"已由 `resumeDocumentSchema` 的文档 ID 唯一性规则兜住。这类"能分辨有效防御与无效防御"的阅读能力，是读别人代码时的实用技能。

### 11.2 内部实体主键从 cuid 改为 integer 自增

源码入口：[migration.sql](../../apps/server/prisma/migrations/20261013120000_internal_int_ids/migration.sql)（115 行）。

**划分原则**（迁移注释原文）：面向人的实体（`users`）保留 cuid——它出现在 URL 与外部引用里，不可枚举、不泄露数量；纯内部字典/关联实体（`roles` / `permissions` / `resumes` / `resume_drafts`）改用 integer 自增，便于人工查找与维护。

判据的价值：这正是 §9 所讲"**结构必然 vs 业务约定**"的应用——"哪些标识需要不可枚举"是产品与安全约定，不是数据库能力的必然。注意 `resumes.id` 虽然出现在 URL（`/resume/:id/draft`），但因该路径需要鉴权、且不是公开分享标识，所以被归入"内部"。将来做公开分享链接时，仍需一个不可枚举的对外标识（share token / slug），这是 §8 讨论中已记下的伏笔。

**技术手法**：Postgres 无法直接把 cuid 文本转成整数，因此用「**临时列 + `row_number()` 映射**」而不是 DROP/ADD，全程单事务：

```text
拆掉受影响的主键与外键
  → 三张主表加 new_id 并填充行号（按 created_at + 原 id 排序，保证映射确定）
  → 关联表按映射填充 new_roleId / new_permissionId / new_resumeId
  → 主表换列、建序列（SERIAL 语义）
  → 关联表换列、重建复合主键与外键
```

**三个必须记住的细节**：

1. **`setval(MAX(id))`**——最关键的一步。建完序列必须把游标推到当前最大值：

```sql
CREATE SEQUENCE "resumes_id_seq" OWNED BY "resumes"."id";
SELECT setval('resumes_id_seq', (SELECT COALESCE(MAX("id"), 0) FROM "resumes"));
ALTER TABLE "resumes" ALTER COLUMN "id" SET DEFAULT nextval('resumes_id_seq');
```

   漏掉 `setval` 会让序列从 1 开始，下一次插入直接撞主键冲突——数据迁移最经典的坑之一。

2. **`resume_drafts` 的模型语义变化**：从"`resumeId` 既是主键又是外键"变为"**新增代理主键 `id` + `resume_id` 加 UNIQUE 约束**"。迁移注释写得很清楚：1:1 关系由 `resume_id` 的 UNIQUE 保证，`id` 只是代理主键。

   这与 §6.2～§6.3 的练习推演完全对应：当时 Owner 判断"独立主键无法保证一份简历最多一条草稿，需要 `resumeId @unique`"，校准确认了这个结论；现在它成了真实表结构。§6.3 留下的"待巩固"问题（只保留 id 主键与 resumeId 外键时，连续写入两条 `resume_id = resume-A` 会被数据库接受）正是必须加 UNIQUE 的原因。

   附带收益：改为代理主键后，"一份简历一条草稿"从"主键隐含的副作用"变成"**显式的唯一约束**"；将来做历史快照时，去掉该 UNIQUE 即可容纳多条记录。

3. **单事务 + 顺序**：改列类型前必须先拆外键与主键；迁移整体在事务内，失败会整体回滚。

### 11.3 两处待留心

- **`DEFAULT_THEME` 与 `SECTION_TITLES` 镜像了 web 的 UI 语义**：源码注释分别写着"与 web 的 `resumeThemePresets` 首项一致""与 web 侧 `resume-document.ts` 的 titles 表保持一致"。这是一处**隐式跨端耦合**：common 不该知道 UI 语义，但为了让"最小输入创建的文档一进页面就正常"，不得不镜像 web 的默认值。将来 web 换首选项或改标题文案时，common 需要同步——值得在专题 07 或后续 Issue 里记明。

## 12. 版本演进、防御性代码与破坏性列变更

记录日期：2026-10-13（Asia/Shanghai）。本节由 §11 的导读引出三轮追问。**其中 §12.2 产生了本次学习中的第一次代码改动**（Owner 采纳选项 A），其余为阅读与讨论。

### 12.1 `schemaVersion` 升到 2 会不会出问题

Owner 的疑问（原文）：*"万一我改了 schemaVersion 版本，是 2 了，但之前已发布的项目（分享出去的）还是 schemaVersion 1，不能影响之前的浏览，那么后续的 schemaVersion 为 2，`z.literal(1).optional()` 这里不是会报错吗？上面说服务端固定写 1，但这个值不应该灵活来定吗？"*

**先分清两个 schema**：

| schema | 定义 | 用途 | `.optional()` |
| --- | --- | --- | --- |
| `resumeDocumentSchema` | `schemaVersion: z.literal(1)` | 入库与读取时校验完整文档 | 否 |
| `resumeDraftInputSchema` | `schemaVersion: z.literal(1).optional()` | 创建接口的接收口（兼容完整文档请求） | 是 |

**结论一：`z.literal(1)` 不是缺陷，而是"当前代码只认一版"的显式声明。** 它的价值是让结构不明的文档当场暴露，而不是等到渲染时拿到 `undefined` 崩溃（见 §4.3）。

**结论二：升 V2 的正确形态不是"把 1 改成 2"，而是变成联合 + 升级函数。** 升级那一刻库里同时存在两版文档（旧草稿 V1、新草稿 V2）：

```ts
// ❌ 直接替换会让旧数据全部读不出来
schemaVersion: z.literal(2)
// ✅ 同时接受两版，再按版本分派
z.discriminatedUnion('schemaVersion', [v1DocumentSchema, v2DocumentSchema])
```

**结论三：草稿与已发布内容用完全不同的升级策略。**

| 类型 | 是什么 | 策略 |
| --- | --- | --- |
| 草稿 | 用户仍在编辑的"活"文档 | **读取时升级**：库里存 V1，读出时转成 V2，用户总看到最新格式 |
| 发布 / 分享 | 对外的"承诺"，外部链接指向它 | **冻结快照**：发布时冻结为不可变副本，自带 `schemaVersion`，不随代码升级而变 |

这正是 `docs/dev/03` §4「简历、草稿、版本、发布与分享」中"发布快照"要解决的问题之一——Owner 的担忧不是待解难题，而是该设计存在的理由。

**结论四：「服务端固定写 1」表达的是"服务端是唯一的版本决定者"，不是"版本号永远等于 1"。** 区分两件事：谁说了算（服务端，架构原则，不变）；值是多少（当前 1，升 V2 后写 2，随代码演进）。输入 schema 里那句"可选且被忽略"防的是"客户端乱传版本号"，不是禁止版本演进。

**结论五：升 V2 要改三处，不是一处。** 契约的 literal；迁移里的 CHECK 约束（`"schema_version" = 1` 与 `document->'schemaVersion'` 一致性检查）；`buildResumeDocument` 的输出与新增的升级函数。第 2 条恰好证明 `schemaVersion` 值得存在：没有它就无法知道库里某条 JSON 属于哪一版结构，也就无法安全编写升级逻辑。

### 12.2 防御性代码的收敛：`nextId` 的查重循环

§11.1 末尾指出 `buildResumeDocument` 的 `nextId` 带一个几乎不可能触发的 `while` 查重循环。Owner 采纳**选项 A**：用注释替代永不执行的代码。已实施：

```ts
// 改动前：usedIds + collectIds + while 重试
// 改动后：
// ID 生成：crypto.randomUUID() 是 v4 UUID，文档内 ID 量级（最多几百个）下碰撞概率可忽略，
// 所以这里不做查重。「文档 ID 重复」的兜底由本函数末尾的 resumeDocumentSchema.parse 负责；
// 而「输入自带重复 ID」属于输入校验的职责（见 resumeDraftInputSchema 的文档内 ID 规则）。
const nextId = (): string => globalThis.crypto.randomUUID()
```

判据：**安全网已经存在（末尾的 `parse`），查重循环是在安全网之前又织一张网。** 删除后安全性不变、代码更短，且把"防御意图"写成注释（知识）而不是写成永不执行的代码。

结论沉淀：读别人代码时要能分辨**有效防御**与**仪式性防御**；若将来真出现"输入自带重复 ID"（例如 AI 从 md/pdf 生成文档），该检查属于**输入校验层**（`resumeDraftInputSchema` 的 superRefine），而不是生成侧——分工原则是"输入的问题在输入校验层解决，生成侧只负责生成"。

验证：`pnpm --filter @rs/common test` → 22 项全通过（0 失败）。

### 12.3 破坏性列变更的标准套路

Owner 追问"关系型数据库做破坏性列变更的标准套路"的具体含义，以下为解释记录。

**为什么绕**：列的类型牵连索引、约束、外键、序列，以及其他表里的副本。把 `roles.id` 从 `text` 改成 `integer`，实际牵动 4 张表与 6 个约束：

```text
roles.id                      ← 有数据（cuid 字符串）
├─ roles_pkey                 ← 主键约束建在它上面
├─ role_permissions.roleId    ← 另一张表里也有这个值（外键）
│   └─ role_permissions_pkey  ← 复合主键建在 (roleId, permissionId) 上
├─ user_roles.roleId          ← 第三张表也有这个值
│   └─ user_roles_pkey
└─ ...
```

**为什么不能直接改类型**：Postgres 没有 `text → integer` 的隐式转换（`'clx1a2b...'::integer` 会报错），`USING` 分支也救不了，所以必须造一套"新旧值映射"。

**五步套路**：

```text
① 拆约束   删掉所有依赖这些列的主键/外键（改列类型前必须拆：外键两侧类型必须一致，
           且有外键指向的列不能直接删改）
② 造临时列 三张主表加 new_id，用 row_number() 填新值
③ 建映射   关联表按 JOIN 旧值 → 新值 回填（new_roleId / new_resumeId）
④ 换列     主表：删旧列 → 临时列改名 → 建序列 → setval(MAX) → 设默认值
           关联表：删旧列 → 临时列改名 → 重建复合主键与外键
⑤ 重建约束 把 ① 拆掉的约束按新列重建
```

两个设计要点：**用 `row_number()` 而非随机数**（整数自增要求映射确定、可复现；按 `created_at, id` 排序保证顺序稳定）；**必须单事务**（若中途崩溃会留下"主表已换、关联表没换"的不一致状态，既无法继续也无法回滚）。

**类比**：给正在营业的商场换门牌号体系——不能只换大门门牌，因为内部所有店铺的导览牌、地图、会员卡都印着旧地址（= 其他表的外键列）。要么全部同时换（= 五步套路），要么先并行挂两套门牌再逐步替换（= 临时列手法的本质）。

**判断框架：改列前先问"谁引用了它"。**

| 变更 | 能否直接改 | 原因 |
| --- | --- | --- |
| 加可空列 | 能 | 不牵动既有数据 |
| 加索引 | 能 | 只读列、不改变量 |
| `varchar(50)` → `varchar(100)` | 能 | 类型兼容且无外键引用 |
| `text` → `integer`（被外键引用） | 不能 | 值要换算 + 关联表需同步 |
| 删列（被外键引用） | 不能 | 先拆引用 |

**数据库差异（值得单独记住）**：Postgres 的 DDL **支持事务**，所以这份 115 行迁移能整体回滚；MySQL 的 DDL 绝大多数**隐式提交**（不可回滚），同样的迁移必须设计成**分批 + 可重入**。这条差异直接决定迁移策略的写法。

## 13. Service 与事务：三个用例的实现细节

记录日期：2026-10-13（Asia/Shanghai）。本轮只阅读 [resume.service.ts](../../apps/server/src/resume/resume.service.ts)（135 行），未修改业务代码。对应第 9.1 节路线中的第 ③ 段。

### 13.1 两个私有辅助方法，两种形态

| 方法 | 形态 | 为什么 |
| --- | --- | --- |
| `assertEditable(currentUser)` | 断言式（不满足即 throw） | 资格检查与数据无关，只看 `currentUser` 的角色与权限，可提前中断 |
| `ownedResume(id, currentUser)` | 构造式（返回 `Prisma.ResumeWhereInput`） | 所有权检查必须与查询一起，不能"先查出来再判断" |

第二条即"把安全条件写进 SQL"：与其"查出来再比对 owner"，不如"只查你能看到的"，避免多一次往返与检查-使用之间的时间窗。

### 13.2 所有权条件为什么在两处重复

`saveDraft` 里同一条件出现两次（`findFirst` 的 `where` 与 `updateMany` 的 `where`）。两者职责不同：

| 位置 | 回答的问题 | 去掉的后果 |
| --- | --- | --- |
| `findFirst` + throw | 这是 404 还是别的问题？（错误语义） | 失败全部退化为 409，用户无法区分"版本旧了"与"不是我的简历" |
| `updateMany` 的 `resume` 条件 | 写入本身是否受所有权约束？（正确性） | 前置检查与写入之间出现时间窗，可能写到"已删除/已易主"的行上 |

原则沉淀：**写操作的所有权条件，不依赖"前面已经查过"。** 第 ① 段讲过 Service 内联检查属"默认放行"，所以每一处都要自己兜住，冗余在这里是美德。

同时要区分同处一个 `where` 的第三类条件：`resume: ownedResume` 管**所有权**（是不是我的、有没有被删），`revision: expectedRevision` 管**并发**（改的是不是我读到的那一版）。一个防越权、一个防覆盖。

### 13.3 `updateMany` 而非 `update`：乐观并发的落点

| | Prisma `update` | Prisma `updateMany` |
| --- | --- | --- |
| `where` 可用字段 | 只能唯一字段（PK 或 `@unique`） | 任意条件 |
| 返回值 | 记录本身 | `{ count }` |
| 能做条件更新 | 否（传不了 `revision`） | 是 |

`revision` 不是唯一字段，因此条件更新只能用 `updateMany`。其真正价值是**原子性**：`UPDATE ... WHERE resume_id = ? AND revision = ?` 把"判断 + 更新"交给数据库在一条语句内完成；若拆成"先读比对再无条件更新"，两步之间会有窗口期，另一请求可能插入——这就是文档 §8 所讲"不能先读后比较再更新"。

`updated.count !== 1` 的含义是"成功必须**恰好**影响一行"（断言式写法）。当前 `where` 含唯一字段（`resume_id` 有 UNIQUE），`count` 只可能是 0 或 1，因此该判断与 `count === 0` 暂时等价；一旦约束放开、`where` 可能匹配多行，`count !== 1` 会拦住，而 `count === 0` 会静默放过。

### 13.4 事务客户端的坑

```ts
return this.prismaService.$transaction(async transaction => {
  await transaction.resumeWorkspace.upsert(...)   // ✅ 绑定该事务
  // await this.prismaService.xxx → ❌ 编译通过、运行不报错，但走另一个连接，原子性静默失效
})
```

规律：**事务回调里一律用参数 `transaction`，不碰 `this.prismaService`**。这是最隐蔽的一类错误——写错了没有任何报错。

### 13.5 `create` 的三个细节

- **补全放在事务外**：`buildResumeDocument` 是纯计算，注释写明"避免占用事务时间"。事务会占用数据库连接（连接池是有限资源），"事务最小化"的核心收益是缩短连接占用时间，而非省 CPU。另外这也影响错误路径：抛错时事务根本不会开启。
- **nested write 同时创建两张表**：`draft: { create: {...} }` 使得 `resumes` 与 `resume_drafts` 一次写入、天然同事务——这正是第 ① 段"两者必须同模块"的数据层依据。
- **create 后再 `findUniqueOrThrow` 一次**：因为 `toResponse` 需要 `Draft & { resume }`，而 `create({ include: { draft } })` 给的是 `Resume & { draft }`，形状方向相反。当前写法让 `toResponse` 成为唯一的响应构造入口，用一次事务内查询换形状统一。这里 `where: { resumeId }` 能用于 `findUnique`，是因为迁移给 `resume_id` 加了 UNIQUE。

### 13.6 `saveDraft` 的最后两步

`transaction.resume.update({ data: { updatedAt: new Date() } })` 是**手工维护的跨表一致性**：Prisma 的 `@updatedAt` 只在该行被更新时刷新，改草稿不会触碰 `resumes` 行；而"列表按更新时间排序"依赖它。属于隐式契约，将来新增"更新草稿"的入口时需一并维护。

随后同事务 `findUniqueOrThrow` 读回最终值，而不是在应用层推算 `expectedRevision + 1`——让"revision 是多少"只有一个来源。

### 13.7 练习与校准

**问题 1**：能否删掉 `updateMany` 里的 `resume: this.ownedResume(...)`？

Owner 回答（原文）：*"感觉不能。在事物开始前我们判断了具有编辑权限，但这里是保存，保存的话可能遇到另外的窗口同时已经先一步提交过更新了，那就会遇到上面提到的数据上 revision 已经更新了，但这里拿到的还是旧的，不过不做一次 findFirst 我们拿到的可能是一份旧的或是错误的简历，导致这次更新（后续的操作都白费）既然如此，那就应该提前把这层错误识别并抛出来，避免浪费。"*

校准：结论（不能删）正确，但**把问题读成了"能不能删掉前面的 `findFirst`"**；并且把 `revision` 冲突（并发）与所有权条件混在一起。正确的区分见 §13.2：`findFirst` 管错误语义（404），`updateMany` 的 `resume` 条件管写入正确性；`revision` 是第三类条件。删掉 `updateMany` 的条件会导致"校验与写入之间的时间窗"，可能写到已删除或已易主的行上。

**问题 2**：把 `buildResumeDocument` 挪进事务内，功能与性能会怎样？

Owner 回答（原文）：*"功能上没有变化；但在性能上，由于这是构造数据，会让数据库在操作时造成不必要的损耗和开销，这会增加事务时间，从而造成更多隐患和并发问题；既如此，就不应该把这种非必要计算挪进事务里。"*

校准：正确。补充两点：(a) 错误路径也会变——`buildResumeDocument` 在缺 profile 时会抛错，放事务外则"根本没开事务"，放事务内则白付一次 BEGIN + ROLLBACK；(b) 更准确的性能视角是**连接占用**而非 CPU，事务一旦开启就持有连接池中的连接，"事务最小化"直接关系并发吞吐。

**问题 3**：`updated.count !== 1` 能否改成 `updated.count === 0`？什么情况下不等价？

Owner 回答（原文）：*"根据上面的，我们知道了 updated.count !== 1 大概率是 updated.count 为 0，和记录不存在这两种情况；只有在 updated.count === 0 两者会等价；但是可能出现记录不存在的情况，所以我们定制一下报错。"*

校准：未答到关键点。**当前两者完全等价**——`where` 含唯一字段（`resume_id` UNIQUE），`count` 只可能是 0 或 1。不等价出现在 **`where` 可能匹配多行**时：`count === 0` 会**静默放过**一次批量误更新（例如匹配 2 行时既不报错又更新了 2 行），`count !== 1` 则会拦住。

由此引出两条判据：

| 写法 | 防御的对象 | 判定 |
| --- | --- | --- |
| `nextId` 的 while 重试（§12.2） | **理论上不可能**（uuid 碰撞） | 剪掉，用注释交代 |
| `count !== 1` | **当前约束下不可能**（UNIQUE 保证），约束一变就会发生 | 保留，作为显式断言 |

> **"不可能"要分两种**：数学上不可能（删）、以及"靠某个约束才不可能"（留，并让它显式）。
> 第二种防御的价值不在今天，而在别人改掉那个约束的那天。

## 14. 鉴权与权限链路

记录日期：2026-10-13（Asia/Shanghai）。本轮只阅读 `apps/server/src/auth/*` 与 `user-creation.guard.ts`，未修改业务代码。对应第 9.1 节路线中的第 ④ 段。

### 14.1 定位：JWT Bearer + RBAC + ownership 三层

| 维度 | 本项目实现 | 依据 |
| --- | --- | --- |
| 提取方式 | `Authorization: Bearer <token>` | `ExtractJwt.fromAuthHeaderAsBearerToken()` |
| 签名算法 | HS256（对称；签发与验证用同一密钥） | `auth.module.ts` |
| 服务端会话 | 无状态（`PassportModule.register({ session: false })`） | 同上 |
| 载荷 | 仅 `sub` + `sessionVersion` | `auth.service.ts` 的 `sign()` |
| 有效期 | `JWT_EXPIRES_IN`，默认 `2h` | `auth.module.ts` |

授权模型是三件事叠加，不是"纯 RBAC"：

| 层 | 管什么 | 在代码里 |
| --- | --- | --- |
| RBAC（角色 → 权限） | 功能授权："你有没有这个能力" | `user_roles` → `role_permissions` → `permissions`，由 `toAuthUser()` 聚合 |
| 权限键直判 | 执行时看权限键，不看角色名 | `permissionKeys.includes('Resume.Sections:edit')` |
| 资源级授权（ownership） | 数据授权："这条数据是不是你的" | `ownedResume()` 的 where 条件 |

第三层无法用 RBAC 表达（"只能改自己的"是资源属性判断，属 ABAC 范畴）。完整表述：**RBAC 负责"能做什么"，ownership 负责"能对哪条数据做"**。

### 14.2 一次带 token 请求的鉴权链

```text
Authorization: Bearer eyJ...
 ├─ JwtAuthGuard（APP_GUARD，全局默认保护所有路由）
 │    ├─ Reflector 读 IS_PUBLIC_KEY → @Public() 直接放行
 │    └─ 否则 super.canActivate() → Passport
 ├─ JwtStrategy
 │    ├─ 提取 token → 验签（HS256）→ 检查 exp（由库负责）
 │    └─ validate(payload)：校验载荷结构（sub 为字符串、sessionVersion 为非负安全整数）
 │         └─ AuthService.restoreUser(sub, tokenSessionVersion)
 │              ├─ findFirst({ id: sub, deletedAt: null }) → 无 → 401 AUTH.User:unavailable
 │              ├─ sessionVersion 比对不一致 → 401 AUTH.Session:revoked
 │              └─ toAuthUser()：多角色权限取并集 + 去重 + 排序
 ├─ handleRequest：失败时区分 缺失 / 过期 / 无效
 └─ AuthUser 写入 req.user → Controller 用 @CurrentUser() 取用
```

### 14.3 四个设计点

- **token 里不放角色权限**（`sign()` 注释）：角色与权限不写入 JWT，每次验签后按 `sub` 回查数据库，因此"角色变化与软删除在下一次请求生效"。这是**性能 vs 一致性**的取舍：自包含 token 省一次查询，但权限变更要等 token 过期（最长 2h）才生效；对管理类系统，"立即生效"更重要。代价是每次受保护请求一次三层嵌套身份查询。
- **`sessionVersion` 实现"可撤销"**：用户表存整数版本号，签发时写入 payload，恢复身份时比对；改密码或强制下线时 `++`，该用户全部旧 token 立即失效。结论沉淀：**纯无状态的 JWT 做不到可撤销**，真实系统里无状态 token 往往都要配一个"状态"（version / blacklist / jti 表）——代价就是每次请求要查库，与上一条是同一枚硬币的两面。
- **失败分成三种语义**（`handleRequest`）：缺失（`AUTH.Token:missing`）/ 过期（`AUTH.Token:expired`）/ 无效（`AUTH.Token:invalid`），前端处理不同（跳登录 / 引导重新登录 / 清本地凭证）。注释另有一条重要设计："策略抛出的用户状态或数据库异常原样向上传播，避免把服务故障误报为 401"——即"数据库连不上"不能报成"你没登录"，否则监控里全是 401，看不到真实故障。这属于**可诊断性**设计。
- **密钥不设默认值**（`auth.module.ts`）：对比参考项目的 `config.get('JWT_SECRET') || 'wwzhidao-secret-key'`——有默认值则"忘了配环境变量就用人人可见的密钥签发 token"，静默不安全。这里改成"拿不到就让服务启动失败"。原则：**敏感配置不设公开默认值，缺失即启动失败**。

### 14.4 `toAuthUser` 的并集计算

```ts
const permissionKeys = user.roles.flatMap(a => a.role.permissions.map(i => i.permission.key))
return {
  roleKeys: user.roles.map(a => a.role.key).sort(),
  permissionKeys: [...new Set(permissionKeys)].sort(),
}
```

三点：多角色的权限取**并集**；**去重**（两角色可能有同一权限键）；**`sort()` 让输出确定**——与迁移用 `row_number()` 保证映射确定是同一习惯：结果稳定才可比较、可 diff、可断言。

### 14.5 Guard 还是 Service 内联（讨论题）

项目里已有 Guard 版本的可对照实现：`user-creation.guard.ts` 与 `ResumeService.assertEditable()` 是**完全相同的判断模式**（角色 ∈ 白名单 且 权限键存在），只是位置不同。

| | Service 内联（resume 现状） | Guard（user 的做法） |
| --- | --- | --- |
| 漏写的后果 | 越权（默认放行） | 访问不了（默认拒绝，安全侧） |
| 规则可见性 | 需翻 Service | 看 Controller 装饰器即可 |
| 复用 | 每个方法手写 | 一处定义 + 装饰器声明 |
| 表达能力 | 高（可混合业务条件） | 低（只能表达静态规则） |

结论倾向：**两者配合而非二选一**。

```ts
@RequirePermission('Resume.Sections:edit')   // Guard 管功能授权（静态、声明式）
saveDraft(...) {
  const resume = await ...ownedResume(...)     // Service 管资源授权（动态、必须与查询一起）
}
```

判据：**Guard 管"你能不能做这件事"，Service 管"你能不能对这条数据做这件事"**——所有权判断必须与查询一起（§13.2），无法上提到 Guard。

### 14.6 练习与校准

**问题 1**：给 `user` 角色加上 `Resume.Sections:edit` 权限键后，他能编辑简历吗？

Owner 回答（原文）：*"当前数据库加 Resume.Sections:edit 乍看是 permissions 表里已有这个权限了，看外键 ~ user 对应一个 roleId，而 roleId 对应多个 permissionId，链路看着似乎可以了。但结合提示来看，并不是这样，assertEditable 是一个私有方法，判断用的或，他在 role 这一层直接拒掉了，让普通用户哪怕拥有权限也无法编辑。"*

校准：结论正确（不能编辑），但**把 `||` 的方向读反了**。`assertEditable` 里的 `||` 位于**否定条件**中：

```ts
if (!是管理员 || !有权限) throw          // 抛错 = A || B
// 等价于 NOT (是管理员 && 有权限)  →  通过 = 是管理员 && 有权限
```

这是**德摩根定律**（`¬(A ∧ B) = ¬A ∨ ¬B`）的经典陷阱："两件坏事发生任意一件就拒绝"等价于"两件好事都满足才通过"。若按"或"理解通过条件（是管理员 **或** 有权限），普通用户被加权限后即可编辑，行为完全相反。

嵌套进一步增加了误读概率：内层 `role === 'admin' || role === 'super_admin'` **真的是"或"**（角色白名单），外层又是否定，两层 `||` 含义不同。

改进建议（易读性）：提出命名变量后正向表达——

```ts
const isEditorRole = currentUser.roleKeys.some(role => role === 'admin' || role === 'super_admin')
const hasEditPermission = currentUser.permissionKeys.includes(PERMISSION_KEYS.RESUME_SECTIONS_EDIT)
if (!isEditorRole || !hasEditPermission) throw new ForbiddenException(...)
```

这也印证了"双保险"是有意的：角色表达身份层级，权限键表达功能授权，权限键误配不会造成越权。

**问题 2**：用户改密码后 `sessionVersion++`，另一台设备未过期的 token 会在哪一步被拒？errorCode 是什么？

Owner 回答（原文）：*"handleRequest 那看来是 Provider AppGuard 这层，errorCode: expired ? API_ERROR_CODES.AUTH_TOKEN_EXPIRED : API_ERROR_CODES.AUTH_TOKEN_INVALID。"*

校准：归属错误。该请求会**通过** Passport 的验签与过期检查（token 本身有效），在 `JwtStrategy.validate()` → `restoreUser()` 的 sessionVersion 比对处被拒，抛出 `AUTH.Session:revoked`；`handleRequest` 的 `if (error) throw error` 使其**原样穿透**，不会进入 `expired ? ... : ...` 分支。

完整对照表：

| 拒绝原因 | 在哪一步 | errorCode |
| --- | --- | --- |
| 没带 token | `handleRequest`（提取不到 Bearer） | `AUTH.Token:missing` |
| token 过期 | `handleRequest`（`TokenExpiredError`） | `AUTH.Token:expired` |
| token 伪造或格式错 | `handleRequest`（其他 info） | `AUTH.Token:invalid` |
| 会话已被撤销 | **`restoreUser` 抛出** | **`AUTH.Session:revoked`** |
| 用户不存在或已删除 | `restoreUser` 抛出 | `AUTH.User:unavailable` |
| 账号或密码错 | `login` 抛出 | `AUTH.Credentials:invalid` |

判据：`handleRequest` 只管"token 本身的问题"；`restoreUser` 抛的是"token 有效但身份/会话已不该用"。分层的意义在于前端处理不同——`Token:expired` 未来可尝试静默刷新，`Session:revoked` 说明密码被改或强制下线，必须重新登录，绝不能自动刷新。

**问题 3**：`restoreUser` 去掉 `deletedAt: null` 后，被软删除的用户会怎样？

Owner 回答（原文）：*"不加这个 deletedAt: null，由于我们用的是软删除便于审计，那数据库里记录还在的，也就是会被查出来，逻辑会忽略错误直接 return toAuthUser(user) 结果变成可以正常登录（有可能超管改了权限或者密码了，但在这种状态下，可能以错误的权限进行访问和操作，带来后续问题）。"*

校准：方向正确，两处表述需收紧。其一，不是"正常登录"，而是"**已登录的会话继续有效**"（`login` 接口自身也有 `deletedAt: null`，那层未改动）；现象是被软删除的用户拿着未过期的旧 token 仍能访问受保护接口。其二，不是"错误的权限"，而是"**删除前的角色权限照旧**"（`restoreUser` 照常从数据库恢复）。

结论沉淀：**软删除只是标记，能否"立即生效"完全取决于每个查询有没有过滤它。** 因此 `deletedAt: null` 必须出现在 `login`、`restoreUser`、`ownedResume`（简历本人 + `workspace.user`）等处。

延伸一处细节：`ownedResume` 除简历自身的 `deletedAt: null` 外，还检查 `workspace: { user: { deletedAt: null } }`（简历主人是否被删）。表面冗余（主人自己被删时 `restoreUser` 已拦住），实为**纵深防御**：若将来出现"管理员代操作"入口，或该 Service 被内部脚本/定时任务直接调用（不经过 HTTP 鉴权链），这层仍能兜住。与 §13.2 的 `updateMany` 条件同类——冗余，但有意。

### 15.1 三张表逐字段

```prisma
model ResumeWorkspace {
  userId  String @id @map("user_id")                                    // 主键 + 外键（1:1 共享主键）
  user    User   @relation(fields: [userId], references: [id], onDelete: Restrict)
  resumes Resume[]
  @@map("resume_workspaces")
}

model Resume {
  id              Int       @id @default(autoincrement())
  workspaceUserId String    @map("workspace_user_id")
  name            String    @db.VarChar(80)
  locale          String    @db.VarChar(20)
  deletedAt       DateTime? @map("deleted_at")
  createdAt       DateTime  @default(now()) @map("created_at")
  updatedAt       DateTime  @updatedAt @map("updated_at")
  workspace       ResumeWorkspace @relation(fields: [workspaceUserId], references: [userId], onDelete: Restrict)
  draft           ResumeDraft?
  @@index([workspaceUserId, deletedAt])
  @@map("resumes")
}

model ResumeDraft {
  id            Int      @id @default(autoincrement())      // 代理主键（当前代码从不使用它）
  resumeId      Int      @unique @map("resume_id")          // 1:1 的真正保证
  schemaVersion Int      @map("schema_version")
  document      Json     @db.JsonB
  revision      Int      @default(1)
  updatedBy     String   @map("updated_by")
  updatedAt     DateTime @updatedAt @map("updated_at")
  resume        Resume   @relation(fields: [resumeId], references: [id], onDelete: Restrict)
  editor        User     @relation(fields: [updatedBy], references: [id], onDelete: Restrict)
  @@map("resume_drafts")
}
```

阅读要点：

- `@map` / `@@map` **不是关联**，只是"代码命名 ↔ 数据库命名"的翻译（camelCase ↔ snake_case）；代价是写原生 SQL 要用数据库真名。
- `@id` 与 `@relation` 是**两件独立的事**，可挂在同一字段（`ResumeWorkspace.userId` 既是本表主键，又是指向 `users.id` 的外键 = 1:1 共享主键写法）。
- `@relation(fields, references, onDelete)`：`fields` 是本表的外键列，`references` 是对方表的被引用列（须为 PK/UNIQUE），`onDelete` 决定父记录被删时的行为（`Restrict` 阻止 / `Cascade` 连带 / `SetNull` 置空 / `NoAction`）。另有 `onUpdate`（本项目未写 → 用默认 `Cascade`，见 §15.4 的漂移）。
- `ResumeDraft.id` 是代理主键但当前代码从不使用（全部按 `resumeId` 查），它是**为将来的历史快照预留**的：届时一份简历会有多条记录，需要代理主键区分。
- `Resume` 有 `createdAt`，`ResumeDraft` 没有：草稿的创建时间等于其所属简历的创建时间（1:1、同事务创建）。审计靠 `updatedAt` + `updatedBy`。

### 15.2 数据库里真实存在的约束（实测）

```text
resume_drafts | resume_drafts_pkey                 | PRIMARY KEY (id)
resume_drafts | resume_drafts_resume_id_key        | UNIQUE (resume_id)
resume_drafts | resume_drafts_resume_id_fkey       | FOREIGN KEY (resume_id) → resumes(id) ON DELETE RESTRICT
resume_drafts | resume_drafts_updated_by_fkey      | FOREIGN KEY (updated_by) → users(id)  ON DELETE RESTRICT
resume_drafts | resume_drafts_revision_positive    | CHECK (revision > 0)
resume_drafts | resume_drafts_schema_version_valid | CHECK (schema_version = 1 AND jsonb_typeof(document)='object'
                                                    |        AND document->'schemaVersion' = to_jsonb(schema_version))
```

实测手段（只读）：

```bash
psql "$DATABASE_URL" -c "select conrelid::regclass, conname, pg_get_constraintdef(oid) from pg_constraint where ..."
psql "$DATABASE_URL" -c "select tablename, indexname, indexdef from pg_indexes where tablename like 'resume%';"
```

⚠️ **关键认知：Prisma 的 schema DSL 表达不了 CHECK。** 所以那两条 CHECK 只存在于手写的迁移 SQL 里，`schema.prisma` 看不到，`prisma db pull` 也拉不出来（已实测：反推的 `ResumeDraft` 模型里两条 CHECK 完全消失）。

由此得到"真源"的概念：**一条规则写在哪，那里就是它的真源**。

| 规则 | 真源在哪 |
| --- | --- |
| 一份简历最多一条草稿（UNIQUE） | `schema.prisma`（`@unique`） |
| `revision > 0`、`schema_version` 与文档一致（CHECK） | **只在 `prisma/migrations/*/migration.sql`** |
| 文档结构、文档大小、ID 唯一（Zod） | `packages/common/src/resume/document.ts` |

推论（真实风险）：既然 CHECK 只活在迁移里，"重建数据库 / 重写迁移"很容易把它弄丢，而 `migrate status` 与 `db pull` **都不会提醒**。

### 15.3 两条 CHECK 在防谁

- `revision > 0`：防"绕过 API 直接改库"、脚本 bug、迁移失误把版本写成 0 或负数。Zod 已要求 `expectedRevision ≥ 1`，但 Zod 管不到绕过 API 的写入。
- `schema_version_valid`：同时管三件事——只认 V1；`jsonb_typeof(document) = 'object'` 防止把数组/字符串塞进文档列；**`document->'schemaVersion'` 必须等于列值**，防止"列说是 1、文档里写着别的"这类两处漂移。

第 3 条正是 §4.3 讲过"同一事实存了两处"的保险：`resume_drafts.schema_version` 与 `document.schemaVersion` 冗余，CHECK 让它们**不可能不一致**。

### 15.4 一处真实漂移（本轮发现，待处理）

```bash
pnpm exec prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script
```

输出非空：**4 个外键缺 `ON UPDATE CASCADE`**（`role_permissions.roleId`、`role_permissions.permissionId`、`user_roles.roleId`、`resume_drafts.resume_id`）。成因是 `20261013120000_internal_int_ids` 重建外键时只写了 `ON DELETE`；而 Prisma 的 `onUpdate` 默认为 `Cascade`，故 schema 期望它存在。

**为什么 `db:migrate:status` 说 "up to date"**：它只比对 `prisma/migrations/*` 与 `_migrations` 记录表（迁移是否应用过），**不比对真实结构与 schema**。所以"迁移都应用了"与"数据库与模型一致"是两件事，检测漂移必须用 `migrate diff`（`db pull --print` 也可独立复现：反推结果里写着 `onUpdate: NoAction`）。

后果与风险：

| 层面 | 影响 |
| --- | --- |
| 运行时 | 几乎为零（主键是自增 int，实践中不会 UPDATE 主键） |
| 下次 `migrate dev` | 检测到 drift，可能生成修复迁移，或要求 `migrate reset`（删库重放 + 重跑 seed） |
| 最坏 | 有人在共享/生产库上跑 `migrate dev` → `reset` → 数据全丢 |

结论沉淀：**`migrate dev` 只用于本地，生产只用 `migrate deploy`** —— 这不是洁癖，而是 `migrate dev` 手里握着"删库"这个选项。

修复方式：`migrate diff` 的输出本身就是修复脚本（4 条 `DROP + ADD FOREIGN KEY ... ON UPDATE CASCADE`），做成一条新迁移即可。**是否修复与时机由 Owner 决定**（属数据库变更）。

### 15.5 JSONB 与索引顺序

**`Json @db.JsonB`**：选 JSONB 的具体理由是"数据库能查询文档内部"——那条 CHECK 就用了 `jsonb_typeof()` 与 `document->'schemaVersion'`；用 `json` 写不出这种约束。代价：JSONB 会重排键、去重、丢格式，不能当"字节级一致"的原文存储。另外实测 `db pull` 反推得到 `document Json`（无 `@db.JsonB`），说明 **PostgreSQL 上 Prisma 的 `Json` 默认就映射 `jsonb`**，`@db.JsonB` 属于"把默认显式写出"。

**`@@index([workspaceUserId, deletedAt])`**：复合索引遵循**最左前缀**——`(a, b)` 能服务 `WHERE a` 与 `WHERE a AND b`，但**服务不了单独的 `WHERE b`**。物理结构是"先按 a 排序、a 相同再按 b 排序"（如电话簿先姓后名）。

| 顺序 | 对 `WHERE workspaceUserId = ? AND deletedAt IS NULL` |
| --- | --- |
| `(workspaceUserId, deletedAt)` ✅ | 先按用户定位，再在小区间内过滤删除态 |
| `(deletedAt, workspaceUserId)` ❌ | 最左列虽然是 `IS NULL`，但**选择性极差**（几乎全部行都满足）→ 定位≈没定位；优化器可能干脆放弃索引走全表扫描 |

判据：**多列索引的顺序按等值条件的选择性排，区分度高的在前。**

### 15.6 哪些规则写数据库、哪些写应用

纲领（`docs/server/03` §7）：数据库约束与输入校验**不是替代关系**——校验改善请求体验，数据库约束保证并发下的数据不变量。

| 维度 | 应用层（Zod / Service） | 数据库约束 |
| --- | --- | --- |
| 目的 | 好的错误信息与体验 | 保证数据不变式（并发下也成立） |
| 可绕过吗 | 可以（脚本、直连、AI 生成） | 不可绕过 |
| 表达能力 | 任意逻辑 | CHECK / UNIQUE / FK；**CHECK 不能跨表、看不到请求上下文** |
| 变更成本 | 改代码 | 需要迁移 |

本项目分工：

| 不变式 | 谁保证 |
| --- | --- |
| 一份简历最多一条草稿 | 数据库（UNIQUE） |
| 草稿必属于存在的简历 | 数据库（FK） |
| `revision > 0` | 数据库（CHECK）+ 应用 |
| `schema_version` 列与文档一致 | 数据库（CHECK） |
| 文档 ≤ 100 KiB、ID 文档内唯一 | 应用（Zod superRefine） |
| 只能改自己的简历 | 应用（`ownedResume`） |

最后一行是重点：**"只能改自己的"属于授权，不属于数据完整性。** CHECK 只看得见"这一行"，看不到"当前登录用户是谁"，所以这类规则天生只能由应用层保证。（进阶：PostgreSQL 的 RLS 可把授权下沉到数据库，但需应用显式设置会话变量，本项目未采用。）

### 15.7 数据库约束的完整清单（自测用）

| 约束 | 保证什么 | 本项目例子 |
| --- | --- | --- |
| `PRIMARY KEY` | 唯一 + 非空（行的身份） | `resumes.id` |
| `UNIQUE` | 值不重复 | `resume_drafts.resume_id` |
| `FOREIGN KEY` | 被引用的记录必须存在 | `resume_id → resumes.id` |
| `NOT NULL` | 不能为空 | `resume_drafts.schema_version` |
| **`CHECK`** | **自定义的任意条件（只能引用同一行）** | `revision > 0` |
| （索引，不是约束） | 查询加速 | `(workspace_user_id, deleted_at)` |

CHECK 与 Zod `superRefine` 的类比与差异：

| | `superRefine`（Zod） | `CHECK`（数据库） |
| --- | --- | --- |
| 在哪执行 | 应用进程 | 数据库引擎 |
| 能绕过吗 | 能（绕过 API 即可） | **不能** |
| 能跨表吗 | 能 | **不能（只能引用同一行）** |
| 错误信息 | 可写得很友好 | 比较生硬 |

### 15.8 Prisma 的四层结构与迁移最小知识（自测用）

```text
schema.prisma ──migrate dev──→ migrations/*.sql ──migrate deploy──→ 真实数据库
     │                                                                   │
     └──generate──→ Prisma Client（类型安全的查询 API）        db pull ───┘（反向）
```

- **迁移（migrate）**：改结构，产物是 `migrations/*.sql`。
- **Client（generate）**：读写数据，产物是 `src/generated/prisma/`。`prisma.resume.findFirst(...)` 就是它；它与迁移无关。

**五个命令的语义边界**：

| 命令 | 做什么 | 何时用 | 陷阱 |
| --- | --- | --- | --- |
| `migrate dev` | 改 schema → 生成 SQL → 应用 | 只在本地开发 | 碰生产会出事；遇漂移可能要求 `reset`（删库） |
| `migrate deploy` | 应用已有迁移 | 部署 / 生产 | 不生成新迁移 |
| `migrate status` | 只看"迁移是否都应用过" | 排查 | **不检查结构一致性** |
| `migrate diff` | 比对任意两个来源 | **检测漂移** | Prisma 7 参数与旧版不同（`--from-config-datasource` / `--to-schema`） |
| `migrate resolve` | 修"卡住的迁移记录" | 迁移失败后 | 会改迁移元数据，先看懂再动 |

**先不用学**（用到再说）：`baseline`（老库接入）、shadow database 原理、多环境迁移编排。

**SQL 要学到什么程度**：不必会写复杂查询；需要能**读懂 DDL**（`CREATE TABLE` / `ALTER TABLE` / `ADD CONSTRAINT` / `DROP`）并理解"约束"。判断标准：看到一条 `ALTER TABLE` 能说出"它在改什么、有什么风险"。仓库里的 9 条迁移自带中文注释，是最好的教材。

### 15.9 方法论：三条"自己发现"的动作

Owner 明确指出：需要的是"如何知道这些方法与方式"，而不只是结论。可复用的三条动作：

```text
① 它的输入和输出分别是什么？      migrate dev: schema → SQL → 库
② 它保证什么、不保证什么？        status 保证"迁移记录"，不保证"结构一致"
③ 我怎么验证它的边界？            用一个反向操作试探（db pull --print / migrate diff）
```

本轮的两个实例：`pnpm exec prisma migrate --help` 一眼列出 `diff`（"Compare the database schema from two arbitrary sources"），并顺带说明了 `dev`/`deploy` 的使用边界；`db pull --print` 让 Prisma 反推模型，CHECK 集体消失——**"它说不出什么"比"它说出什么"信息量更大**。

### 15.10 练习与校准

**问题 1**：索引反成 `@@index([deletedAt, workspaceUserId])` 有什么影响？

Owner 回答（要点）：*"索引顺序对查询有影响……先 deletedAt 基本先查一遍，deletedAt 项基本很少，没起过滤效果，再查 workspaceUserId；先 workspaceUserId 就第一次把数量过滤掉，让第二次负担轻。"*

校准：直觉正确（"先过滤掉最多的才有效"），两处精确化。(a) 不是"查两遍"，而是**B-tree 无法从第二列定位**：复合索引先按第一列排序，查询必须在**最左列**有条件才能跳着定位；这里最左列虽有 `IS NULL` 条件，但选择性极差 → 定位≈没定位。(b) 更严重的后果是**优化器可能放弃该索引直接全表扫描**——不是"慢"，而是"以为有索引其实没用上"。判据：多列索引顺序按等值条件的选择性排，区分度高的在前。

**问题 2**：为什么"简历必须属于当前用户"不能写成 CHECK？

Owner 回答（原文）：*"从功能上理解，有超管这样的，虽然不能改，但查询不是限制死的，自己的简历能开放给别人看，那这条规则就没写死到数据库里，不然行为和预期会不一致，CHECK 在数据库里比较严格？"*

校准：**偏离考点**——回答的是"业务规则会变"（规则的稳定性），而问的是"CHECK 的能力边界"。正确答案：**CHECK 只能引用同一行的列，看不到"当前登录用户是谁"**。数据库执行 CHECK 时没有请求上下文。

由此区分两个概念：**数据完整性**（这一行自己是否合法 → 数据库）与**授权**（谁能对这一行做什么 → 应用层，因为没有"用户"这个上下文）。"简历必须属于当前用户"属于后者。（进阶：PostgreSQL RLS 可把授权下沉，但需显式设置会话变量，本项目未采用。）

**问题 3**：漂移一直不修，下次跑 `db:migrate:dev` 会怎样？

Owner 回答（要点）：*"id 从 cuid 改成自增，若不改漂移，schema 定义类型没变，接口 DTO 也按之前定义，类型检查不生效……可能与预期不一致；好点能正常访问，坏的情况数据完全丢失或覆写。"*

校准：**把"漂移"与"ID 类型变更"混为一谈**——两者无关。id 类型早已在迁移中改完，schema 与数据库在这一点上一致；当前漂移只是 4 个外键缺 `ON UPDATE CASCADE`，与 id 类型、DTO、类型检查均无关。

真实后果：`migrate dev` 会打印 `Drift detected`，给出两个选项——生成修复迁移，或要求 `migrate reset`（删库 → 重放全部迁移 → 重跑 seed）。最坏情况是有人在**共享/生产库**上跑 `migrate dev` → `reset` → 数据全丢。这正是"`migrate dev` 只用于本地"这条纪律的分量：**它手里握着删库的选项**。

## 16. 接口落地与代码审查：练习 vs 真实实现

记录日期：2026-10-14（Asia/Shanghai）。本节对照两个真实提交（`e701540` 列表接口、`ae732a8` 重命名/软删除）审读代码，**验证此前练习的判断**，并学"一个新接口的完整落地流程"。只读，未修改代码。

### 16.1 练习答案 vs 真实实现（Q5.2 对照）

`GET /api/resume` 的实现（`resume.service.ts` 的 `list()`）与 §9 练习 2 的判断逐项一致：

| Owner 当时的判断 | 真实实现 | 结果 |
| --- | --- | --- |
| 属于 `resume` 模块 | 同一个 `ResumeController` / `ResumeService` | ✅ |
| 不需要新表 | 一次 `findMany` | ✅ |
| 不需要 `assertEditable()` | `list()` 未调用 | ✅ |
| 必须所有权过滤 | `where.workspaceUserId = currentUser.userId`；提交信息称"所有权即查询条件" | ✅ |
| 索引会给 `workspaceUserId` + `deletedAt` 用 | 正好走 `@@index([workspaceUserId, deletedAt])` | ✅ |

三个此前未提到的实现决策：

- **列表项不返回 `document`**（`resumeSummarySchema` 只含 `id` / `name` / `locale` / `revision` / `updatedAt`）：列表不必逐条解析正文，也不让概览页耦合正文契约。
- **要求草稿存在**（`draft: { isNot: null }`）：列表项要返回 `revision`，而它来自 draft；脏数据宁可不出现。
- **不为超管开只读他人列表的口子**：与 §14 的最小权限一致。

**一处可质疑（非 bug，属产品决策）**：`orderBy: { createdAt: 'desc' }` 但列表展示的是 `draft.updatedAt`——**排序字段 ≠ 展示字段**。后果是"很早创建、刚被编辑过"的简历仍排在后面。改为按 `draft.updatedAt` 排序更贴合"最近动过的在前"的工作台心智；需一并考虑关联字段排序对索引的影响。

### 16.2 重命名为什么**不用** `revision`

`PATCH /resume/:id` 的源码注释：

> **这里不需要 revision**：名字是单字段整体覆盖，最后写入者生效即可 —— 它不会像整份文档那样把别人的改动整段抹掉，为它加版本号只会让调用方多背一个并发概念。

| | `PUT /resume/:id/draft` | `PATCH /resume/:id` |
| --- | --- | --- |
| 改什么 | 整份 `document`（几十个字段） | 单个 `name` |
| 覆盖风险 | 会把别人改的整段抹掉 | 只影响 `name`，其余不动 |
| 需要 `revision` | 必须 | 不需要 |
| 冲突表现 | 409，交用户决策 | 最后写入者生效 |

判据沉淀：**并发控制的需求来自"覆盖范围是否会造成信息丢失"，不来自"是不是写操作"。**（补全 §13 的结论。）

### 16.3 PUT vs PATCH 的闭环（回收 §10 练习 3）

§10 练过"PUT 传整份才是诚实的声明"；真实代码给出另一半——`PATCH` 用于**局部修改**，且 `renameResumeSchema` 用 `strictObject` 拒绝顺手带上 `id` / `locale` / `document`：

> 那些各有各的接口，混进同一个 PATCH 会让"改个名字"变成一次**隐式的整体覆盖**。

路由表的资源层级至此清晰：

```text
POST   /resume              在集合里创建
GET    /resume              列出集合
PATCH  /resume/:id          改简历本身（局部：name）
DELETE /resume/:id          删简历本身
GET    /resume/:id/draft    读子资源：草稿
PUT    /resume/:id/draft    整份替换子资源
```

`PATCH`/`DELETE` 作用于**简历**，`PUT` 作用于**草稿**——正是 §10.2 所讲"多写一段 `/draft` 给兄弟资源留位置"的价值。

### 16.4 软删除：重复删除返回 404

`remove()` 用 `ownedResume`（含 `deletedAt: null`）作条件，因此第二次删除匹配 0 行 → 404：

> 语义是"已经没有这份可删的简历了"，而不是悄悄返回成功。

取舍：REST 惯例下 `DELETE` 应幂等（重复删返回 204 亦可接受）；这里选 404，理由是**重复删除说明客户端状态过期，应当暴露**。

⚠️ 这与 §8 的 409（冲突不静默覆盖）是**同一种价值观**：宁可让客户端知道"你的假设过期了"，也不要静默成功。**审代码时，"它和项目一贯做法是否一致"往往比"是否符合教科书"更重要。**

### 16.5 "最小响应"原则

| 方法 | 返回 | 回查 | 理由 |
| --- | --- | --- | --- |
| `rename` | `{ id, name }` | 否 | `name` 就是客户端传入值，服务端能确定 |
| `remove` | `{ id }` | 否 | 同理 |
| `saveDraft` | 完整 `ResumeDraftResponse` | 是 | `revision` 是数据库递增后的值，只能读回 |

判据：**服务端能确定结果就直接返回；只有"数据库才算得出来的值"才需要回查。**

另：`rename` / `remove` 均用 `updateMany`（而非 `update`），因为 `ownedResume` 返回的是复合条件，而 Prisma 的 `update` 只接受唯一字段作为 `where`。**条件与载体不匹配时，只能用 `updateMany`。**

### 16.6 一个新接口的落地流程（从提交信息还原）

```text
## 契约（packages/common）   ← 先定形状：resumeSummarySchema / renameResumeSchema
## 后端（apps/server）        ← 再写实现，并说明"为什么"（不加 revision / 所有权即查询条件）
## 任务卡                    ← 记范围调整与验证证据
验证：接口脚本 9/9（……）；quality gate 全绿
```

与 `docs/server/03` §5 的顺序一致：**契约 → 实现 → 验证 → 回填**。提交信息另记"admin 侧页面留在工作区，等 Owner 观感验收后再提交"，保留了"UI 未经实看不得提交"的纪律。

### 16.7 练习与校准

**问题 1**：`rename` 的失败为什么返回 404 而不是 409 / 403？

Owner 回答（原文）：*"先看更新方法用的是 updateMany 而不是 update，也就是不是通过主键和唯一键来改的，若修改这条不存在，修完后不会有 null，而是报错，这里就适合 404。"*

校准：抓到了 `updateMany` 返回 `count`，但未答到关键。`ownedResume` 把**四种情况**（不存在 / 属于别人 / 已软删除 / 主人已删除）统一压成"0 行"，SQL 层面无法区分。因此：不能 403（等于承认资源存在 → 泄露存在性）；不能 409（不是状态冲突）；**只能 404**。404 在此的含义是"**不可访问**"，而非"不存在"——它故意合并两种情况以防泄露。

补充分层：`rename` 先调 `assertEditable()`，所以"身份不够"抛 403、"身份够但这条不是你的"落 404，两种拒绝各归其位。

**问题 2**：给 `rename` 也加 `expectedRevision` 能防什么？代价？什么场景值得？

Owner 回答（原文）：*"仅仅是改 resume 名，若也加了 expectedRevision，我理解是相当于把名称也当作内容的一部分了，代价是修改开销变得更多了。防什么和场景想不到……加了这个字段后，能识别到同一份简历内容改前和改后是不同的一份了。"*

校准：**"想不到要防什么"本身很接近正解**——此场景确实几乎没有值得防的丢失。完整答案：能防的是"两个窗口同时改名，先改的人不知道自己被覆盖"。三层代价：(1) 调用方需先 GET 再 PATCH（多一次往返）；(2) 列表接口要维护并发概念；(3) ⚠️ **语义错位**——`revision` 属于 `resume_drafts`，而 `name` 属于 `resumes`，用它保护名称是**跨资源借用版本号**，改名是否递增 revision 两难。

判据：**"想不到要防什么"就是"不加"的正当证据。加不加不取决于"更严格是否更好"，而取决于"有没有真实的丢失场景"。** 值得加的场景：改名有副作用（触发通知、影响已分享链接）、或进入多人协作（届时正确做法是给 `resumes` 自己加 version 列）。

**问题 3**：`list()` 里 `if (!resume.draft) continue` 是运行时防御吗？

Owner 回答（原文）：*"不懂……不加这行似乎也没什么影响，因为我在开发时根本想不到……但既然这问了，肯定有其作用的，我就不乱猜了。"*

校准：**它是给 TypeScript 看的"类型收窄"，运行时永远不会触发。** `draft ResumeDraft?` 让 Prisma 生成的类型为 `Draft | null`；`where` 里的 `draft: { isNot: null }` 只作用于运行时，**TypeScript 不推断 where 条件与 select 结果类型的关系**，所以没有这行 `resume.draft.revision` 会报 "Object is possibly null"、typecheck 失败。建议加注释说明"这是类型收窄"，否则下一位读者会以为它是多余的判空。

**由此补全"三类不可能"判据**（原判据见 §13.7）：

| 类别 | 例子 | 处理方式 |
| --- | --- | --- |
| ① 数学上不可能 | `nextId` 的 `while` 查重（uuid 碰撞） | 删掉，用注释交代 |
| ② 靠约束才不可能 | `count !== 1`（UNIQUE 保证最多一行） | 保留，作为显式断言 |
| ③ **类型系统需要，运行时不可能** | `if (!resume.draft) continue` | **保留 + 注释说明是类型收窄** |

第 ③ 类最容易被误读为"多余的判空"——它既不防御也能删，但删了编译不过。

## 17. 数据库约束的三轮追问：概念边界与补基础路径

记录日期：2026-10-14（Asia/Shanghai）。承接 §15 的三道作业（`db pull` 的 `onUpdate`、CHECK 能否用 schema 表达、授权为何不能 CHECK）。只读，未修改代码。

### 17.1 `onUpdate: NoAction` 与 schema 默认 `Cascade` 共同说明什么

Owner 理解（原文）：*"NoAction 是说更新后没有其他额外动作，prisma 默认 Cascade 也就是级联，修改后有关联修改，合在一起说明本次没有对数据进行改动。"*

校准：**术语理解反了，且结论方向错**。

- **`NoAction` 不是"什么都不做"，而是"不级联、直接报错阻止"**。在 PostgreSQL 里它与 `Restrict` 几乎等价（差别只在检查时机：`Restrict` 立即、`NoAction` 可延迟到语句末），与 `Cascade` 是**对立**关系。
- 两处信息合起来说明的是**漂移**：`db pull` 读真实数据库得到 `onUpdate: NoAction`（库缺 `ON UPDATE CASCADE`），而 `schema.prisma` 未写该字段 → 用 Prisma 默认 `Cascade`。两者不一致。
- 它还能**定位漂移方向**：schema 不写 `onUpdate` 属正常写法（默认即 Cascade），所以是**迁移 SQL 漏写**那一侧。只有当"确实不想要级联"时，schema 才应显式写 `onUpdate: NoAction`。

### 17.2 "真源只有一份"时，靠什么保护它

Owner 思路（原文）：*"真源只有一份，那就在迁移前先备份啊？……但好像没解决的问题，迁移还会重复发生该问题，怎么解决呢？"*

校准：**"不能"猜对了；而且自我质疑正中要害**——问题不是"丢了"，而是"**丢了没人知道**"，所以备份不解决问题。正确做法是两件事：

| 风险 | 对冲手段 |
| --- | --- |
| 漂移（外键、索引类） | CI 跑 `prisma migrate diff --exit-code`，非空即失败 |
| **CHECK 丢失** | `migrate diff` **检测不到**（Prisma 看不见 CHECK）→ 需自写断言查 `pg_constraint` |

断言示意：

```js
const rows = await prisma.$queryRaw`
  select conname from pg_constraint where conrelid = 'resume_drafts'::regclass and contype = 'c'`
assert(rows.map(r => r.conname).includes('resume_drafts_revision_positive'))
```

另一条更根本的机制是**迁移 append-only 纪律**：新变更写新迁移、不改已应用的。因此"重建数据库"其实**不会**弄丢 CHECK（它是重放全部迁移）；真正会弄丢的场景只有"有人手工改库"或"写新迁移时误删"。

> 结论：**真源只有一份时，保护它靠"纪律 + 可检测"，不靠"备份 + 小心"。**

### 17.3 三个概念的边界（本轮最重要的沉淀）

Owner 反馈"回答不上来、缺基础认知"，并给出直觉：*"简历属当前用户算是一种关联（外键），保证用户能拥有自己的简历，这些简历不会飘……数据库不需要 check 具体内容（额外性能开销）。"*

校准：**直觉一半对一半错**。

- 对：表结构确实保证了"简历归属于某个存在的空间"（`resumes.workspace_user_id → resume_workspaces.user_id` 外键）。
- 错：**外键保证的是"归属给某个存在的空间"，不是"属于当前登录用户"**。差别就在"**当前是谁在请求**"这个信息——它根本不在数据库的视野里。
- 另一处需纠正："数据库不做是因为性能开销"**不成立**（CHECK 开销极小）。原因是**看不到请求上下文**：数据库只知道"这一行有什么"，不知道"谁在敲门"。

判据表：

| 规则 | 需要什么信息 | 谁保证 |
| --- | --- | --- |
| `revision > 0` | 只要这一行 | 数据库 CHECK |
| 简历归属某个存在的空间 | 这一行 + 被引用的表 | 数据库 FK |
| **只能改自己的** | 这一行 + **请求上下文** | **应用层**（`ownedResume`） |

**分开三个抽屉（困惑的根源是把它们混在一起）**：

| 概念 | 归属 | 关心什么 |
| --- | --- | --- |
| **数据完整性**（Integrity） | 数据库 | 这一行是否合法、引用是否成立、并发下是否仍成立 |
| **授权**（Authorization） | 应用 | **谁**能对**哪条数据**做**什么** |
| 交界判据 | — | **这条规则需要"请求上下文"吗？** 需要 → 应用；不需要 → 可下沉数据库 |

### 17.4 补基础的学习路径（给 Owner 的处方）

**第 1 步：用实验建立直觉（20 分钟）**——在事务里故意违反约束，看数据库的回应：

```sql
begin; update resume_drafts set revision = 0; rollback;                  -- CHECK: revision_positive
begin; insert into resume_drafts (resume_id, schema_version, document, revision, updated_by, updated_at)
       select resume_id, 1, '{}', 1, updated_by, now() from resume_drafts limit 1; rollback;   -- UNIQUE
begin; update resume_drafts set resume_id = 999999; rollback;            -- FOREIGN KEY
```

这三种报错就是"数据完整性"的日常。亲手看过一次，认知会从"读过"变成"见过"。

**第 2 步：读 PostgreSQL 官方文档的 Constraints 章节**（`CREATE TABLE` 下），重点看 `CHECK` 那节——它明确写着"CHECK 表达式不能引用其他行"。

**第 3 步：补授权模型**——本项目是 RBAC + ownership（见 `docs/dev/02_身份与权限_设计.md`）；想看更体系化的说明，搜 `OWASP Authorization Cheat Sheet`（讲清"资源级授权必须在应用层做，因为需要用户上下文"）。

**第 4 步：把"看不见的东西"变成可检测**——写断言确认两条 CHECK 还在（见 §17.2），这一步把概念变成工程能力。
