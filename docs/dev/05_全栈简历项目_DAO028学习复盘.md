## 3. 第一轮：从需求推导内容模型

### 3.1 原始目标

让求职者自行组织能力内容，以简洁概览和可选评分展示，支持编辑、排序，并在刷新后恢复。

从全栈开发视角，先推导数据和规则，再写页面：

| 用户需求 | 模型要求 |
| --- | --- |
| 前端、全栈、AI 或其他职业能力可自定义 | 分组标题属于用户内容，不写死 |
| 一组包含多项能力 | 分组内使用条目数组 |
| 改名、排序、删除、添加实践说明 | 分组/条目有稳定 ID 和明确字段 |
| 图表降低文字负担 | 独立自评维度，不强迫每条技能评分 |
| 自行评分 | 可留空，有统一量尺和自评依据 |
| 同样内容切换展示方式 | 内容与展示配置职责分开 |
| 多份简历面向不同岗位 | 能力内容归属具体简历的草稿 |

### 3.2 用户自定义内容，程序固定字段职责

Owner 原先设想类似 `capability.frontend: string[]`，动态键承载分组。这个结构能够承载文字，但改名、非技术职业扩展、条目说明和身份追踪会更困难。

当前模型采用对象数组。以下为教学简化示例，省略完整文档和必填的评分字段，不能直接当作创建接口请求体：

```ts
{
  id: 'capability-module-1',
  type: 'capabilities',
  title: '个人能力',
  data: {
    groups: [
      {
        id: 'group-1',
        title: '前端核心能力',
        summary: '能够独立交付复杂前端应用',
        items: [
          {
            id: 'item-1',
            name: 'Vue 生态',
            description: '具备 Vue2 → Vue3 迁移经验',
            evidenceLinks: []
          }
        ]
      }
    ]
  }
}
```

- `type`：程序据此选择编辑器与渲染组件；当前固定为 `capabilities`。
- `id`：对象身份，改名和排序后保持稳定。
- `title` / `name`：给读者看的名称，由用户编辑。
- `description` / `summary` / `evidenceLinks`：详细说明、概述和佐证。

源码入口：[能力契约](../../packages/common/src/resume/capabilities.ts)。

### 3.3 条目、自评与展示的职责

`groups` 说明有哪些能力、做过什么；`dimensions` 选择少量维度表达自评；`ratingScale` 说明量尺和依据。维度可通过 `groupId` 关联一个分组，也可以独立存在。

`score: null` 表示没有填写；`score: 0` 表示用户明确给零分。二者不能混用。当前不根据文字推断评分，也不自动求平均分或做岗位排名。

`content` 与 `display` 在模型中分开，但当前作为同一草稿文档共同保存。职责分开不必等于拆成不同表。

### 3.4 练习与真实纠正

练习：分组改名、移到最后、隐藏个人能力模块分别改哪里？

Owner 复述：

1. 改名仅改 `data.groups[index].title`，模块外层不变。
2. 分组移动不改数据，修改配置里的 `order`。
3. 隐藏只改 visibility 相关配置，内容不变。

校准：第 1、3 项成立，第 2 项需要区分层级。AI 上一轮对排序的讲解没有明确区分这两层，容易让人理解为所有顺序都单独配置。

| 操作 | 实际修改位置 |
| --- | --- |
| 分组改名 | `section.data.groups[index].title` |
| 分组排序 | `section.data.groups` 数组排列 |
| 条目排序 | `group.items` 数组排列 |
| 整个模块排序 | `display.sections.order` 中的模块 ID 顺序 |
| 整个模块隐藏 | `display.sections.hidden` 中加入模块 ID |

数组重排时，元素内容和身份可不变，但数组顺序确实改变。未来若同一份内容需要多套内部排列，可以另行设计独立顺序配置；本轮未实现。

## 4. 第二轮：表里的记录与文档里的数组

### 4.1 Owner 的复述与疑问

Owner 理解为「单用户多份简历，所以 resume_drafts 是数组或者 Map；表层有版本、display，再有 content/sections」，并追问：既然前端按对象取字段，为什么结构变化还需要解析或迁移？

校准：数据库表里的多条记录，与一条记录里面的嵌套数组是两个层次。`resume_drafts` 是表；读取单份草稿返回对象，列表接口可返回数组，不必把整张表建成一个数组或 Map 字段。

### 4.2 三表职责

| 表 | 职责 | 示例 |
| --- | --- | --- |
| `resume_workspaces` | 用户的逻辑简历空间 | user-1 的空间 |
| `resumes` | 某份简历的稳定身份与元信息 | 前端岗位版 / AI Agent 岗位版 |
| `resume_drafts` | 某份简历唯一的当前草稿 | 对应文档与 revision |

一名用户拥有两份简历时，当前模型是一个空间、两条 Resume、两条 ResumeDraft。这里「两份简历」与将来的「同一简历多个发布版本」要区分。

空间是逻辑容器，不是数据库磁盘容量。内部名称存 `resumes.name`，语言存 `resumes.locale`；正文姓名与能力等存草稿文档。将来加入 AI 或其他字段时，需要先明确职责并更新契约，当前严格 Schema 不接受未声明字段。

```text
resume_drafts 中的一条记录
  ├─ resumeId / schemaVersion / revision / updatedBy / updatedAt
  └─ document（JSONB）
       ├─ schemaVersion
       ├─ content（对象）
       │    ├─ sections（模块对象数组）
       │    └─ footer
       └─ display（对象）
```

关系表承担所有权、身份、外键和唯一约束；JSONB 承载嵌套、自定义内容与整体读取。代价是单个条目修改仍提交完整文档，未来跨简历检索/统计能力会比独立能力表复杂。

### 4.3 schemaVersion 为什么必要

合法 JSON 不代表符合组件期待的结构。例如旧条目是 `['Vue', 'React']`，新条目是 `[{ id, name, description }]`；两者都能解析，但新组件读取 `item.name` 时，旧字符串没有这个字段。

`schemaVersion` 是结构识别入口，不会自动迁移。支持旧结构时，仍需编写识别、转换、补默认值和校验逻辑。当前 V1 Schema 仅接受版本 1，迁移 SQL 也约束版本为 1；未来升级需同步修改这些约束，当前没有任意版本自动迁移能力。

更通用的设计指字段职责清晰、变更有转换路径，不是把所有东西都改为无约束 Map。

### 4.4 三种版本概念

| 概念 | 变化条件 | 当前能力 |
| --- | --- | --- |
| `schemaVersion` | 需要区分的文档结构升级 | 当前固定为 1 |
| `revision` | 每次成功保存 | 并发条件更新，成功后递增 |
| 发布版本 | 将来执行发布形成固定结果 | 未实现 |

练习：修改三条能力描述并成功保存，三个字段怎样变化？

Owner 回答：`resumeId` 不变，说明简历指向未变；`schemaVersion` 不变，因为只是改内容；`revision` 要变。

结论：正确。revision 更准确称为「草稿并发版本号」，并不代表旧内容已经被保存为历史版本。

### 4.5 新建与复制简历

Owner 提出 Duplicate：复制草稿再修改，本质是新增而不是覆盖。

校准：复用本人 workspace，新增 Resume（新 resumeId）与 ResumeDraft（关联新 resumeId），新草稿 revision 从 1 开始；两个创建在事务内完成。当前 Duplicate 尚未实装。

内部模块/分组/条目 ID 不一定全部重建：当前只要求在各自文档内唯一，独立文档可保留相同内部 ID；未来差异对齐可能利用这种对应关系。若复制到同一文档内，则需重新生成 ID 并更新关联引用。

## 5. 第三轮：并发版本与编辑追踪

Owner 提出借鉴 Pinia/Redux，追踪用户修改，便于编辑与溯源。

两窗口同时读到 revision 3 时：A 以 expectedRevision 3 保存成功，数据库递增到 4；B 再以 3 保存，条件不匹配，返回 409。当前更新同一条草稿，无法仅凭 revision 还原旧正文。

| 能力 | 目的 | 可能的实现位置 |
| --- | --- | --- |
| 撤销/重做 | 撤回刚才的错误操作 | 前端工作副本和操作历史 |
| 草稿历史 | 查看昨天修改、恢复旧内容 | 后端历史快照或差异记录 |
| 发布版本 | 固定发给某公司的内容 | 后端不可变发布快照 |

状态管理库可承载状态，但不会自动提供刷新后仍可访问的用户编辑历史；开发者工具的追踪也不等于产品历史功能。

候选取舍：完整快照恢复简单、存储较多；差异记录可能更小，但重放、结构升级与恢复更复杂。结合当前简历体积，可优先讨论有数量/期限限制的快照，再用稳定 ID 对齐新增/删除/修改/移动。保存节点需定义，不能默认每次按键写库。

这是后续候选，未批准新表或接口，当前未实现历史、撤销/重做或发布。

## 6. 第四轮：主键、外键与唯一草稿

源码入口：[Prisma Schema](../../apps/server/prisma/schema.prisma)、[三表迁移](../../apps/server/prisma/migrations/20261011090000_resume_drafts/migration.sql)。

当前 `ResumeDraft.resumeId` 同时是主键和指向 `Resume.id` 的外键：

- 主键：不能为空且不能重复，一份简历最多一条当前草稿。
- 外键：必须指向存在的简历，不允许悬空草稿。
- 事务创建：外键不保证每份简历一定有草稿，创建接口把简历和草稿一起创建，避免只完成其中一步。
- `updatedBy` / `updatedAt`：最近操作者与时间，不能替代完整历史。

### 6.1 删除是否会影响复制出来的简历

Owner 顾虑：外键指向已存在 Resume，删除那份记录后，复制出来的是否也会丢失？随后想到该表是草稿，删除简历及对应草稿似乎合理。

校准：外键引用的是「本草稿所属的新简历」，并非复制来源。复制后的 B 拥有自己的 Resume 和 ResumeDraft，当前模型没有 B 依赖 A 的来源外键；删除 A 不会因为这个归属外键而删除 B。

删除动作取决于引用动作，不能只看到外键就推断级联：

| 动作 | 父记录被物理删除时 |
| --- | --- |
| 当前 `onDelete: Restrict` | 有草稿引用时阻止删除简历 |
| `onDelete: Cascade` | 自动删除引用它的草稿；当前未采用 |
| `onDelete: SetNull` | 将外键置空，要求字段可空；当前未采用 |

本轮没有简历删除 API。`Resume.deletedAt` 表达软删除，标记字段而非执行 SQL DELETE，不触发外键删除动作；本人草稿接口会过滤已软删除简历。未来物理清理需另行设计删除顺序、历史/分享关联和事务，不能直接认为「删简历会自动删草稿」。

### 6.2 改为独立草稿主键的练习

练习：ResumeDraft 新增自动生成的 id 作为主键，resumeId 只保留普通外键，还能保证一份简历最多一条当前草稿吗？

Owner 回答：不能；是否要把 resumeId 与新增 resume_draft_id 关联？

校准：归属关联已经由 resumeId 外键承担，需要补的是 `resumeId @unique`。独立主键保证每条草稿身份不同；外键保证简历存在；唯一约束保证同一 resumeId 不重复。

教学候选示例，不是本轮实际表结构变更：

```prisma
model ResumeDraft {
  id       String @id @default(cuid())
  resumeId String @unique
  resume   Resume @relation(fields: [resumeId], references: [id], onDelete: Restrict)
}
```

上面只展示关键约束，省略 document 等字段；配套 Resume 反向关系也需存在。当前复用 resumeId 作为主键已经满足需要，无须额外增加 id。

仅建 `@@unique([resumeId, id])` 不够：`draft-1/resume-A` 与 `draft-2/resume-A` 是不同组合，两条都可以写入。要限制的是 resumeId 本身唯一。

待 Owner 巩固：如果只保留 id 主键与 resumeId 外键，没有 resumeId 唯一约束，连续写入 `id=draft-1, resumeId=resume-A` 与 `id=draft-2, resumeId=resume-A`，数据库会接受几条？为什么？

### 6.3 Owner 复述：关系字段与草稿变化

Owner 进一步复述：`id` 可以理解为一条文档记录的身份，`resumeId` 表示它属于哪份简历，`@unique` 表示同一份简历只能对应一条草稿；如果两个草稿 ID 不同但 `resumeId` 都是 `resume-A`，可能是在操作同一份简历内容。

校准：前半段正确，但需要区分数据库记录与记录里的正文。`ResumeDraft.id` 标识草稿表中的一行；`resumeId` 是真正的外键列；`resume` 是 Prisma 关系字段，方便读取所属的 `Resume`，不是简历正文列；正文存放在 `document` JSONB 中。`onDelete: Restrict` 也不是“删除时把简历内容删除”，而是父级 `Resume` 仍被草稿引用时阻止物理删除。

没有 `resumeId @unique` 时，`draft-1/resume-A` 与 `draft-2/resume-A` 会被数据库接受为两行，因为主键不重复且外键都指向存在的 `resume-A`。第二个 ID 只是另一条记录的身份，不自动表示“内容变了”，也不是自动发布；只有应用明确写入不同的 `document`、历史快照或 revision 语义，才能说明它代表了什么业务变化。

当前产品选择的是“一份简历一条当前草稿”，所以继续使用 `resumeId` 同时作为主键和外键；将来做历史快照时，再把模型扩展为独立草稿 ID、多条记录和明确的历史版本字段。

## 7. 博客取材与后续追加

### 7.1 共享契约练习：字段形状与跨字段规则

进入共享契约学习时，Owner 对下面的能力数据进行了判断：未声明的 `extraField` 是多余字段，`score: 8` 超过 0～5 量尺，`items` 可能需要至少一项，并将前两类问题都归为字段错误。

校准结果如下：

| 数据 | 结论 | 原因 |
| --- | --- | --- |
| `extraField` | 错误 | `z.strictObject` 不允许 schema 未声明字段 |
| `groupId: 'backend'` | 错误 | 字符串格式本身合法，但 `superRefine` 要求它引用当前 `groups` 中真实存在的 ID；这里只有 `frontend` |
| `score: 8` | 错误 | `ratingScale.max` 为 5，评分超出统一量尺；这是跨字段业务规则 |
| `items: []` | 合法 | 当前只设置最多 20 项，没有 `min(1)`；用户可以先建空分组 |
| `dimensions: []` | 合法 | 当前只设置最多 20 项，没有 `min(1)`；可以暂不配置评分维度 |

因此，`extraField` 属于字段形状/未知字段错误；`groupId` 的格式检查通过但引用关系失败；`score` 属于跨字段规则错误。`items` 和 `dimensions` 的空数组不是错误，不能把“数组字段存在”误读成“数组必须非空”。

这轮还为 `packages/common/src/resume/capabilities.ts` 与 `document.ts` 补充了 TSDoc，明确记录运行时 Zod 校验、编译期 TypeScript 类型、模块联合类型、跨字段规则、并发版本和未评分 `null` 的职责边界。后来发现数据库使用 Prisma cuid、编辑器使用 UUID，而旧 ID 上限为 20，于是将共享 ID 上限统一为 100，并补充回归测试与 OpenAPI 同步；`@rs/common` 类型检查、16 项测试和目标文件格式检查均通过。

可从本次学习提炼以下文章主题，Owner 独立组织叙事，不把候选功能写成已完成事实：

1. 从技能文字到通用能力模型：固定字段职责、自定义内容与稳定 ID。
2. 多份简历怎样存：关系表承载身份、JSONB 承载内容，逻辑空间与物理容量的区别。
3. 三种版本为什么不同：结构升级、并发保存与发布快照。
4. 一份简历一条草稿：主键、外键、唯一约束和删除动作。
5. 后续待学：接口、鉴权、并发实现、前端保存状态、测试与交付。

持续记录建议：每轮追加「问题 → Owner 原理解 → 代码依据 → 校准 → 取舍 → 练习结果」。错误理解和 AI 讲解不清处保留，并标明纠正，不改写成从一开始就理解正确的开发故事。
