## 一、迁移的三份信息，各自回答什么？

| 对象 | 回答的问题 |
|---|---|
| `schema.prisma` | Prisma 模型现在想表达什么？ |
| `migrations/*/migration.sql` | 数据库应该怎样一步步变成目标结构？ |
| 真实数据库 | 当前真正存在、正在生效的结构是什么？ |

还有一份辅助记录：数据库里的 **`_prisma_migrations`**。

它记录哪些迁移执行过、是否失败，以及文件校验和等信息。

### 前端类比

可以近似理解为：

````text
Schema       → 当前源码中的模型声明
迁移文件      → 版本化升级脚本
真实数据库    → 线上运行状态
迁移记录表    → 部署执行记录
````

**“部署记录显示完成”不等于“运行状态从未被人手动修改”。** 所以迁移记录和实际结构要分开看。

## 二、两个验证场景，不能只测一个

### 场景 1：空库重放

从一个空数据库开始，按顺序执行全部迁移。

它验证：

> 新开发者、新测试环境，能否从零搭建数据库？

### 场景 2：已有库升级

保留旧结构和旧数据，只应用后续迁移。

它验证：

> 已有用户的数据，能否安全进入新版本？

| 验证 | 常见问题 |
|---|---|
| 空库重放 | 旧迁移依赖了本不存在的数据、空表边界处理错误 |
| 已有库升级 | 数据不满足新约束、转换失败、删除造成数据丢失 |

**空库能成功，不代表旧数据能升级；旧库能运行，也不代表空库能重建。**

## 三、用你的 `setval` 问题理解修复边界

根据你转述的情况，历史迁移中有：

````sql
SELECT setval(
  'resumes_id_seq',
  (SELECT COALESCE(MAX(id), 0) FROM resumes)
);
````

可能出现：

````text
已有库：表里有数据 → MAX(id) 大于零 → 成功
空数据库：表里没数据 → 设置为零 → 失败
````

所以，**同一条迁移可以在旧环境成功，在新环境失败。**

### 为什么不能只新增一条修复迁移？

````text
旧迁移 A → 空库执行失败，停在这里
新迁移 B → 根本执行不到
````

新迁移可以调整已有环境的序列，却不能自动修复这个空库重放问题。

这是本节最重要的判断：

> **先确认问题发生在哪一步，再判断修复代码有没有机会执行。**

## 四、历史迁移能不能改？

默认纪律是：

> **已经共享或部署的迁移，不随意改；通常用新迁移修正。**

原因是数据库记录了迁移文件的 **checksum（校验和）**。可以把它理解成文件内容的指纹。

文件改了，指纹就变了：

````text
数据库记录：执行的是旧文件
仓库现在：同名文件已经变成新内容
````

但你这个问题又说明：**只追加迁移也不一定能解决所有情况。**

### 按环境决定，不机械套规则

| 情况 | 处理方向 |
|---|---|
| 迁移还没共享、没在重要环境应用 | 可以修订后重新验证 |
| 只有可丢弃的开发库应用过 | 协调修订历史，并重建这些开发库，通常较简单 |
| 有不能丢弃的数据环境应用过 | 需要制定兼容与历史协调方案，不能直接改文件或 reset |
| 空库无法重放，但已有库正常 | 必须同时解决“新库重建”和“旧库记录”的问题 |

对于最后两种情况，可能涉及受控修订历史或重新基线化等方案。**现在不用学操作细节，只要知道这不是一条命令能安全解决的事。**

另外，改历史迁移中的注释也会改变文件内容，同样可能改变 checksum。

## 五、五个命令，只记语义边界

| 命令 | 核心用途 | 不要误解成 |
|---|---|---|
| `migrate dev` | 开发时生成、应用迁移并检查历史 | 生产部署命令 |
| `migrate deploy` | 执行已有的待应用迁移 | 根据 Schema 自动生成变更 |
| `migrate status` | 检查迁移历史状态 | 完整数据库结构检查 |
| `migrate diff` | 比较两个来源的结构 | 比较业务数据，或检测全部 PostgreSQL 特性 |
| `migrate resolve` | 调整特定迁移的记录状态 | 自动执行、撤销或修复 SQL |

特别记住：

- **`resolve --applied` 不会替你执行 SQL。**
- **`resolve --rolled-back` 不会替你撤销 SQL。**
- **`reset` 会丢数据，不是通用修复按钮。**

`diff` 的参数随 Prisma 版本变化，真正使用时看本项目版本的 `--help`，不用现在背。

## 六、遇到迁移问题，按这份清单调查

### 第一步：确认连接的是哪个环境

- [ ] 本地、测试还是生产？
- [ ] 数据是否可以丢弃？
- [ ] 是否需要备份或恢复保障？

### 第二步：确认问题类型

- [ ] 某条迁移 SQL 执行失败？
- [ ] 迁移已经执行，但文件后来被改了？
- [ ] 有尚未应用的迁移？
- [ ] 真实结构被手动修改，出现漂移？

**这四种情况不能用同一种方式处理。**

### 第三步：查看三个证据

1. 出错的 `migration.sql`。
2. `migrate status` 和必要的迁移执行记录。
3. 数据库实际结构与相关数据。

迁移失败时，还要确认是否已经执行了部分操作，**不能默认失败就代表什么都没发生**。

### 第四步：分别验证

- [ ] 隔离空库重放。
- [ ] 在旧数据副本上验证升级。
- [ ] 检查关键约束、外键和默认值。
- [ ] 必要时使用 diff；CHECK 等特性还要查看数据库原生定义。

### A2 最后记住四句话

> **迁移记录正常，不等于实际结构一致。**  
> **已有库能用，不等于空库能重放。**  
> **新增迁移，不能修复执行不到它之前的失败。**
