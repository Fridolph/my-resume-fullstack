## 一、这份文档要解决什么

「知道」和「做出来」之间的缺口，实测出来往往不是知识缺口，而是**两个能力**：

1. **切分**：面对一个功能，不知道第一个文件该动哪个；
2. **验收**：不知道"做到哪一步算对"，于是只能一口气写完再看能不能跑。

所以本文只做两件事：

- 给一条**能逐级停**的阶梯（每级都有产物 + 验收命令）；
- 给一套**能自己演练**的方法（复演真实提交 + 给别人的提交拆步）。

> 判断标准不是"我理解审计了"，而是"**给我一个别的功能，我能说出第一步动哪个文件、以及怎么验证它对**"。

## 二、七步阶梯（速查表，建议打印）

| 步 | 问自己**一句**话 | 产出 | 验收入口 | 跳过的后果 |
| --- | --- | --- | --- | --- |
| ① 语义 | **这件事在回答什么问题？** | 一句话 + 字段清单 + 非目标 | 能对着句子指出每个字段的必要性 | 字段漏了 → **快照补不回来** |
| ② 表结构 | 能不能**不动表**？ | `schema.prisma` + `migration.sql` | `migrate diff` 为空；空库能重放 | 漂移；或白改一次迁移 |
| ③ 契约 | **调用方写入的形状**是什么？ | 共享字典 + 白名单 | 字典有动作；白名单能通过 `pick` | 契约被代码拖着走，加动作就要改已上线方法 |
| ④ 服务 | **调用方希望怎么调**？哪些字段必填？ | Service + Module + 单测 | 单测断言映射正确 | 靠自觉传参 → "记了等于没记" |
| ⑤ 接入 | **同事务还是最终一致？快照在哪一步取？** | Service 改动 + 事务 | 单测断言"同一个事务句柄" | 业务成了审计没成（无人负责） |
| ⑥ 读取 | 谁可以看？ID 怎么传进来？ | Controller + 权限键 | 403 用例；ID 四处一致 | 越权 / 审计行串不到日志 |
| ⑦ 验证 | 这个保证是**类型给的**还是**约定给的**？ | 单测 + 覆盖率测试 + 真库集成 | 三层各自能证明上一层证明不了的 | 看起来测过了，其实什么都没验 |

**核心性质**：每一级只验证上一级的假设。**跳级必返工。**

三个"倒过来会怎样"：

1. **先写服务、后写契约** → 字典的形状会被代码牵着走；等你发现"这个动作还要记 `wasDefault`"时，已经上线的方法签名得改，调用点全改。
2. **先接接入、后定事务边界** → 你会先写出"删除成功后补一条审计"（最终一致），等发现要强一致时，`remove()` 得从"一条 DELETE"重构成"事务 + 先读后删"，测试也全要改。
3. **先写代码、后想验证** → 你会得到一张"看着全绿"的质量门。本仓真发生过：测试文件被删光，`pnpm test` 仍 0 退出。

### 题

1. 为什么 `resource_id` 是 `TEXT` 而不是 `INTEGER`？
2. 为什么 `pickAuditMetadata` 在"一个字段都没留下"时返回 `undefined`，而不是 `{}`？
3. `record()` 为什么要求传 `transaction`？为什么**类型系统挡不住**误传？

<details><summary>参考答案（先自己答，再展开）</summary>

**Q1** —— `resumes.id` 是自增整数，`users.id` 是 cuid 字符串。一张表要装下两类资源（以及将来新增的类型），只能统一成文本。
代价：失去数据库级的类型约束（没法靠列类型保证"这列一定是数字"）。
**不能省的判断**：如果只有一类资源，这条就不成立 —— **判据永远绑定当前约束，不是通则**。

**Q2** —— `{}` 会让"这个动作本来就没有额外信息"与"有信息但被白名单裁光了"长得一样。
排查时前者是正常的、后者说明**白名单太窄**（该加字段）。落 `NULL` 才能区分。
细节：`pickAuditMetadata` 返回 `undefined` → Prisma 写 JSONB 时为 `NULL`。

**Q3** —— 强一致要求审计与业务在同一个事务里，而事务客户端只能由调用方传入（`$transaction` 的回调参数）。
类型挡不住的原因：`Prisma.TransactionClient = Omit<PrismaClient, '$connect'|'$disconnect'|'$on'|'$use'|'$extends'>`
（Prisma 7.10 实测）。**它仍然保留 `$transaction` 与全部模型委托**，所以 `PrismaService` 结构上完全满足它 → 可赋值。
所以这条靠**调用约定 + 集成测试**兜（断言"业务抛错时审计行也不存在"）。

</details>

</details>

## 七、自测题库（12 题，分三组）

> 建议：先答，再展开。答不出的题，回到对应章节读注释，**不要直接背答案**。

### A 组 · 概念边界

**Q1** 审计 / 日志 / 备份，三者各解决什么？哪两个**不能**互相替代，为什么？

<details><summary>答案</summary>

| | 回答什么 | 归宿 |
| --- | --- | --- |
| 日志 | 系统**出了什么事**（谁调了什么、多慢、错在哪） | stdout |
| 审计 | 谁对**哪条业务数据**做了什么 | 数据库表 |
| 备份 | 数据**怎么回到过去** | 备份介质 |

- **审计 ≠ 备份**：审计只记"删了哪一份、谁删的"，**不留正文** → 不能恢复内容。
- **审计 ≠ 日志**：日志丢了不影响追责统计；审计丢一条可能就是那条删除。
- 判据：**与业务同生共死 + 要按业务对象反查 → 进库；否则 → stdout。**

</details>

**Q2** 为什么审计表对 `Resume` 和 `User` **都不**挂外键？`CASCADE` 与 `SET NULL` 各破坏什么？

<details><summary>答案</summary>

- `CASCADE`：删简历/删号那一刻，这条"谁删的"记录**一起被删** → 审计等于没有。
- `SET NULL`：记录留下，但"删的是**哪一份**"永久丢失 → 同样回答不了问题。
- 替代：**值引用 + 快照**（`resourceId` 当值存、`resourceSnapshot` / `actorSnapshot` / `actorRoleKeys` 保可读性）。
- 代价：失去数据库级引用完整性；对审计来说"指向已不存在资源"是**正常状态**。

</details>

**Q3** 为什么 `actorRoleKeys` 必须在**写入时**快照，而不能查询时 join `user_roles`？

<details><summary>答案</summary>

角色会变。事后 join 得到的是**现在的角色**，而追责问的是"他**当时**是什么身份"。
同理 `actorSnapshot.nickname`：账号软删后仍能 join，但真被清掉就 join 不到了。

</details>

### B 组 · 机制

**Q4** `record()` 要求传 `transaction`，`list()` 不需要。类型能挡住误传吗？挡不住的话怎么兜？

<details><summary>答案</summary>

- `record` 参与业务事务（强一致）；`list` 是独立只读路径。
- **挡不住**：`Prisma.TransactionClient = Omit<PrismaClient, '$connect'|'$disconnect'|'$on'|'$use'|'$extends'>`（Prisma 7.10 实测），**它仍保留 `$transaction` 和全部模型委托**，所以完整的 `PrismaService` 结构上完全满足它。
- 兜法：**调用约定 + 集成测试**（断言"业务抛错时审计行也不存在"）。
- 可选的硬手段：运行时断言传入对象**没有** `$connect` / `$disconnect`（这两项恰在 deny list 里，而完整 client 有）—— 能区分。**本项目未采用**，属于"知道有这个选项"。

> ⚠️ 我的一个错误直觉（留作反面教材）：以为 `$transaction` 也被 Omit 掉、可以用 `'$transaction' in tx` 判断。**实测：Prisma 7 的 denylist 里没有 `$transaction`。**

</details>

**Q5** `remove()` 为什么要"先读再删"，而 `create()` 不需要？给一条判据。

<details><summary>答案</summary>

判据：**快照的时机风险 = "这条信息在动作之后是否还在"**。

- `remove`：`name` / `revision` / `sectionCount` / `wasDefault` 都在被删的行里 → 删完不可得。
- `create`：审计要的 `id` 是**创建后**才有的，而 `name` / `locale` 来自入参 → 没有"删除前"那种时机问题。

（这句话直接来自 `11b13b0` 的提交信息。）

</details>

**Q6** 事务里 `updateMany` 返回 `count: 0`，若不抛错会发生什么？为什么比"报错"更糟？

<details><summary>答案</summary>

事务照常提交：**一个什么都没改的事务 + 一条"我删了 X"的审计**。
比报错更糟的原因是**静默**：报错至少显式，而这种状态在数据库里看起来完全合法，事后无法区分"真的删了"与"审计写了但没删"。

</details>

**Q7** `pickAuditMetadata` 返回 `undefined` 而不是 `{}`，对排查有什么实际差别？

<details><summary>答案</summary>

`NULL` = "这个动作本来就没有额外信息"；`{}` = "有信息但被裁光了"（**可能说明白名单太窄**）。
两者混同后，你无法判断"要不要把某个字段加进白名单"。

</details>

**Q8** 白名单为什么放 `packages/common` 而不是只放 `apps/server`？

<details><summary>答案</summary>

两端要同一份：server 写入时校验、admin 渲染时要显示"删除了简历"。
各写一份 → 必然漂移（一处加了动作，另一处不认识，页面露出英文常量 `resume.delete`）。
符合 `AGENTS.md` §4.6 判据：纯常量 + 纯函数，能脱离 Vue/Nuxt 运行。

</details>

### C 组 · 判断

**Q9** 草稿自动保存（2.5 秒一次）要不要写审计？依据哪条判据？

<details><summary>答案</summary>

**不写**。Owner 定的分层策略：**破坏性/不可逆 → 同事务强一致；可重放/高频 → 不审计或只记元数据**。
2.5 秒一次会把审计表迅速撑大，且它可被 `revision` 追溯；每次复制全文还会把 PII 带进审计。

</details>

**Q10** 用户说"我误删了简历，你们有审计，能恢复吗？"你怎么答？

<details><summary>答案</summary>

**不能。** 审计只存快照（`name` / `revision` / `sectionCount`），**不留 `document` 正文** —— 它回答"谁删的"，不回答"原来长什么样"。
要能恢复，需要的是另一套能力：软删 / 版本快照 / 数据库备份（且三者用途不同，见 `00.md` E2）。
顺便：**不要把"有审计"说成"可恢复"**，那是把责任边界说糊了。

</details>

**Q11** `PENDING` 覆盖率测试解决什么问题？它抓到过什么真实问题？

<details><summary>答案</summary>

解决 **"忘了写审计"** —— 新增删除接口时没人提醒你加审计，等到追责时才发现那个动作从未记录过，而**快照补不回来**。
第一问：字典里每个动作要么接线、要么显式在 `PENDING`；第二问：接线后必须从清单移除（防止清单腐烂）。
真实抓到：`resume.create` 字典里有、但只接了 delete / setDefault → 立 #55 → `11b13b0` 补上。
判据：**把"忘"变成红灯，把"欠着"变成有意识的欠账。**

</details>

**Q12** 新增一个"导出简历"的审计动作，七步里哪几步必须做？哪步可以跳？

<details><summary>答案</summary>

- **①语义**：导出算不算要追责的动作？（先答这句再写代码）
- **③契约**：加 `resume.export` 键 + metadata 白名单（如 `format`）
- **④服务**：加 `recordResumeExport`（语义化方法）
- **⑤接入**：若导出在事务里写库则同事务；纯读导出可以不写审计，只写日志
- **⑥**：需要 `requestId` 就传 `@TraceId()`
- **⑦**：单测 + 覆盖率测试会**自动**逼你把它从 `PENDING` 移除
- **② 可跳**：`action` 是 `VARCHAR`，加动作不需迁移 —— 除非你要新增**独立列**（那就要走迁移）

</details>

## 九、常见卡点手册（遇到就查这里）

| 症状 | 先问这一句 | 动作 |
| --- | --- | --- |
| 不知道从哪开始 | 这件事回答的一句话是什么？ | 写一句话 + 字段清单，**先不碰代码** |
| 想直接建表 | 能不能不动表？ | 现有字段装得下就不迁移 |

| 快照该在什么时候取 | 这条信息在动作后还在吗？ | 不在 → 先读再动作 |
| 不知道测什么 | 这个保证是**类型**给的还是**约定**给的？ | 约定 → 写断言（如"同一个事务句柄"） |
