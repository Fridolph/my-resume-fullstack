# B2：动态模块、配置与生命周期

**项目场景：JWT、Prisma、Logger 初始化。**

这一节最终要能回答：

> **配置从哪里来？谁用配置创建服务？资源何时准备好？程序退出时谁负责释放？**

---

## 一、动态模块：根据配置，决定怎样注册依赖

B1 中，我们看到的是固定模块：

````ts
@Module({
  providers: [PrismaService],
  exports: [PrismaService],
})
export class PrismaModule {}
````

但有些模块需要由使用者提供配置，比如：

- JWT：签名密钥、过期时间。
- Logger：日志级别、脱敏规则。
- 数据库客户端：连接配置。

因此会出现：

````ts
JwtModule.register({
  secret: '仅作演示，不要硬编码真实密钥',
  signOptions: { expiresIn: '15m' },
})
````

可以理解成：

> “请按照这份配置，生成这个模块的注册信息。”

所谓**动态模块**，通常就是一个方法返回 `DynamicModule` 对象，其中描述需要注册的 Provider、导出的能力等信息。

**它不是“每个请求动态创建一个模块”。**

### `register`、`forRoot` 是特殊语法吗？

不是，它们都是模块作者定义的普通静态方法，名称是社区约定。

| 常见名称 | 通常表达的意图 |
|---|---|
| `register` | 为某次模块使用提供配置 |
| `forRoot` | 配置应用级的基础能力 |
| `forFeature` | 为某个功能模块注册局部能力 |

**实际行为要看对应库的实现，不能只凭名字判断。**

## 二、为什么需要 `registerAsync`？

直接配置时，值已经在手边：

````ts
JwtModule.register({
  secret: process.env.JWT_SECRET,
})
````

但项目通常希望配置集中管理、启动时校验，而不是到处读取环境变量。

这时可能写成：

````ts
JwtModule.registerAsync({
  imports: [ConfigModule],
  inject: [ConfigService],
  useFactory: (config: ConfigService) => ({
    secret: config.getOrThrow<string>('JWT_SECRET'),
    signOptions: { expiresIn: '15m' },
  }),
})
````

这里三个字段分别负责：

| 字段 | 作用 |
|---|---|
| `imports` | 引入提供配置依赖的模块 |
| `inject` | 告诉 Nest 工厂函数需要哪些依赖 |
| `useFactory` | 使用这些依赖生成模块配置 |

### ConfigService 为什么能进入函数参数？

不是因为参数写了 `ConfigService` 类型，Nest 就自动猜出来了。

关键是：

````ts
inject: [ConfigService]
````

Nest 根据这里的依赖标识找到实例，再按顺序传入工厂函数。

````text
ConfigModule 提供并导出 ConfigService
    ↓
Nest 解析 inject 中的依赖
    ↓
调用 useFactory(configService)
    ↓
得到 JWT 配置
    ↓
供 JwtService 初始化使用
````

这就是 B1 的依赖注入，应用到了**配置工厂**上。

### 带 Async，就必须写 async 吗？

**不必须。**

工厂既可以直接返回配置，也可以返回 Promise。只有确实需要等待异步操作时，才需要 `async`。

## 三、配置：尽早发现错误，不要等请求进来才发现

通常会在应用入口模块中配置：

````ts
ConfigModule.forRoot({
  isGlobal: true,
})
````

它可以读取环境变量，以及按配置加载 `.env` 等来源，并提供 `ConfigService`。

`isGlobal: true` 表示注册后，其他模块通常不用反复导入它，就能注入它公开的 Provider。

但要分清：

> **全局可用，不等于配置已经正确。**

例如：

- JWT 密钥缺失。
- 数据库地址错误。
- 日志级别填写了不支持的值。

### 建议原则

**必需配置应尽量在启动阶段校验，缺失就明确失败。**

`getOrThrow()` 可以帮助发现缺失值，但完整的配置校验还需要处理格式、类型和允许范围等问题。

不要为了让程序启动，在生产环境给 JWT 密钥随便设置一个固定兜底值。

## 四、生命周期：构造对象，不等于资源已经准备好

创建一个 Service 和建立数据库连接，是两件不同的事。

简单区分：

| 阶段 | 主要职责 |
|---|---|
| `constructor` | 接收依赖，初始化简单字段 |
| `onModuleInit` | 模块依赖就绪后，执行初始化 |
| `onApplicationBootstrap` | 所有模块初始化完成后，执行应用级准备 |
| 关闭钩子 | 清理客户端、连接等资源 |

### 为什么不直接在 constructor 里连接数据库？

因为构造函数不能被 Nest 当作可等待的异步初始化过程。

在里面启动一个异步连接但不等待，可能导致：

````text
服务对象已经创建
    ↓
应用继续启动
    ↓
连接还没有准备好
````

生命周期钩子可以返回 Promise，Nest 会在相应阶段等待它。

### Prisma 示例

以下是在 `PrismaService extends PrismaClient` 中的一种常见写法：

````ts
async onModuleInit() {
  await this.$connect()
}

async onModuleDestroy() {
  await this.$disconnect()
}
````

注意两个边界：

- Prisma 也支持在第一次查询时自动连接，**并非必须手动 `$connect()`**。
- Prisma 版本、驱动适配器和项目封装可能影响资源管理方式，不能机械复制所有项目的写法。

显式连接的一个好处是：**可以在启动时更早暴露连接问题。**

## 五、关闭钩子与优雅退出

程序关闭，不应该只理解成“进程没了”。

理想情况下，需要：

````text
收到关闭通知
    ↓
协调停止接收新请求、处理在途工作
    ↓
释放数据库客户端等资源
    ↓
退出进程
````

Nest 提供的主要关闭钩子，顺序为：

````text
onModuleDestroy
    ↓
beforeApplicationShutdown
    ↓
应用连接关闭
    ↓
onApplicationShutdown
````

其中，**应用连接关闭不等于所有自定义资源都会自动释放**。你创建的资源仍需要明确管理。

### 什么时候会触发？

- 显式调用并等待 `app.close()`。
- 启用关闭钩子后，接收到支持的关闭信号。

通常在启动入口中设置：

````ts
const app = await NestFactory.create(AppModule)
app.enableShutdownHooks()
await app.listen(3000)
````

但这不是万能保障：

- 强制终止，如 `SIGKILL`，不会给程序执行清理的机会。
- 容器或部署平台需要留出足够的退出时间。
- “所有在途请求都处理完再退出”需要结合 HTTP 适配器和部署策略确认，不能仅靠这行代码假定已经实现。

现在只记住：**正常关闭要有清理路径，强制退出不能依赖钩子。**

## 六、Logger 等基础模块为什么要避免重复初始化？

这里把原清单里的“不能重复注册”校准一下：

> **不是语法上绝对不能重复，而是不应在没有明确意图时重复初始化应用级基础模块。**

例如，不要在每个业务模块里都随手调用：

````ts
LoggerModule.forRoot(...)
````

根据库的实现，重复初始化可能造成：

- 多套配置。
- 多个实例或资源。
- 重复日志。
- 难以确定哪份配置在生效。

常见设计是：

````text
根模块 / 基础设施模块
    ├── 配置 Config
    ├── 初始化 Logger
    └── 注册 Prisma

业务模块
    └── 注入、复用已公开的能力
````

**初始化一次、按需复用**是起点；若确实要多个独立实例，应使用库明确支持的方式。

# B2 的整体图

````text
启动入口 main.ts
    ↓
Nest 创建应用
    ↓
读取并校验配置
    ↓
配置工厂通过 DI 获得 ConfigService
    ↓
生成 JWT、Logger 等模块配置
    ↓
创建 Provider，执行初始化钩子
    ↓
完成应用级初始化，开始监听请求
    ↓
正常关闭时执行清理钩子
````

这是概念顺序，不代表所有模块之间存在一条严格串行的初始化链。**有依赖时，应通过依赖关系表达，不要依靠“碰巧谁先执行”。**

## 三道简短自测

1. `registerAsync` 中的 `useFactory` 没有写 `async`，一定有问题吗？
2. `useFactory(config: ConfigService)` 能获得配置服务，主要依靠参数类型，还是 `inject` 和模块依赖注册？
3. 为什么数据库连接这类异步初始化，更适合放在生命周期钩子，而不是构造函数里？

这三题答清楚，B2 的基本机制就稳了；项目初始化链路的阅读和验证先留作后续实操。
