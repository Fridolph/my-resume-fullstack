# B1：NestJS 依赖注入与 Provider 作用域

这节重点回答三个问题：

1. **Service 是谁创建的？**
2. **为什么其他模块不能随便使用它？**
3. **为什么不能把当前用户存在 Service 的实例字段里？**

---

## 一、依赖注入：不自己创建，而是声明“我需要什么”

假设 `ResumeService` 需要访问数据库。

自己管理依赖，可能写成：

````ts
class ResumeService {
  private readonly prisma = new PrismaService()
}
````

这会让 `ResumeService` 同时承担两个职责：

- 处理简历业务；
- 决定怎么创建数据库服务。

NestJS 中通常写成：

````ts
@Injectable()
export class ResumeService {
  constructor(
    private readonly prisma: PrismaService,
  ) {}
}
````

意思是：

> “我需要一个 PrismaService，请框架提供给我。”

这个机制叫 **依赖注入（Dependency Injection，DI）**。

### 前端类比

有点像通过 Vue 的 `provide / inject` 或 React Context 获得共享能力，而不是每个组件自己创建一份。

但 NestJS 还会负责依赖解析、实例创建和生命周期管理，不能完全等同。

### `@Injectable()` 不等于注册完成

通常还需要：

````ts
@Module({
  providers: [ResumeService],
})
export class ResumeModule {}
````

你可以简单记成：

- `@Injectable()`：让这个类具备被 Nest 管理和注入的条件。
- `providers`：把它注册到模块的依赖管理中。

---

## 二、Module 的三个字段，建立依赖边界

这是初学 NestJS 最容易混的部分：

| 字段 | 含义 |
|---|---|
| `providers` | 本模块注册哪些服务 |
| `exports` | 本模块向外提供哪些服务或依赖 |
| `imports` | 本模块引入哪些模块的公开能力 |

例如数据库模块：

````ts
@Module({
  providers: [PrismaService],
  exports: [PrismaService],
})
export class PrismaModule {}
````

简历模块：

````ts
@Module({
  imports: [PrismaModule],
  providers: [ResumeService],
  controllers: [ResumeController],
})
export class ResumeModule {}
````

依赖关系是：

````text
PrismaModule
  ├── 注册 PrismaService
  └── 导出 PrismaService
             ↓
ResumeModule 导入 PrismaModule
             ↓
ResumeService 可以注入 PrismaService
````

### 为什么不能直接在每个模块都注册 PrismaService？

因为重复注册同一个类，可能让不同模块各自创建实例。

对于 PrismaService 这类管理数据库客户端的服务，容易造成不必要的客户端或连接资源重复。

**通常让一个模块负责注册，其他模块通过导入复用。**

这也解释了一个重要边界：

> 默认单例，不是“这个类在整个进程里无论怎么注册，都永远只有一个对象”。

## 三、作用域：这个实例会被谁复用？

NestJS 的常见 Provider 作用域有三种：

| 作用域 | 实例复用方式 | 现在的建议 |
|---|---|---|
| **DEFAULT** | 注册的 Provider 通常在应用生命周期内复用 | 默认优先使用 |
| **REQUEST** | 每个请求创建自己的实例 | 有明确需要时使用 |
| **TRANSIENT** | 不同消费者获得独立实例 | 暂时知道即可 |

### 1. DEFAULT：默认单例

普通写法：

````ts
@Injectable()
export class ResumeService {}
````

在常见注册方式下，多个请求会使用同一个 `ResumeService` 实例：

````text
请求 A ─┐
请求 B ─┼──→ 同一个 ResumeService
请求 C ─┘
````

这不是问题。**业务服务复用实例，本来就是正常设计。**

问题出在：你把某个请求的数据存在共享实例中。

---

## 四、为什么不能把当前用户存进 Service 字段？

下面这种写法有风险：

````ts
@Injectable()
export class ResumeService {
  private currentUserId: string

  async save(userId: string) {
    this.currentUserId = userId
    await this.someAsyncWork()

    return this.saveFor(this.currentUserId)
  }
}
````

两个请求可能交错执行：

````text
A：currentUserId = 用户 A
A：遇到 await，等待

B：currentUserId = 用户 B

A：恢复执行，读取 currentUserId
A：读到用户 B
````

结果可能是日志串用户，甚至业务操作使用了错误身份。

### “Node.js 不是单线程吗？”

常见 Node.js 服务中，JavaScript 回调通常在同一个线程执行，但 **异步请求仍然可以交错推进**。

`await` 等待期间，其他请求可以运行。

所以：

> **单线程，不等于一次只处理一个完整请求。**

### 正确的默认做法：用参数或局部变量

````ts
async save(userId: string, resumeId: number) {
  await this.someAsyncWork()

  return this.saveFor(userId, resumeId)
}
````

这里的 `userId` 属于本次函数调用，不会被另一请求改写。

---

## 五、不是“Service 不能有状态”

更准确的规则是：

> **共享单例 Service，不应使用共享可变字段保存请求专属状态。**

对照看：

| 实例字段 | 是否通常合适 |
|---|---|
| 注入的 PrismaService | 合适 |
| Logger 引用 | 合适 |
| 初始化后的只读配置 | 合适 |
| 当前请求的 userId | 不合适 |
| 当前正在编辑的 resumeId | 不合适 |
| 设计明确的共享缓存 | 可以，但需考虑一致性和资源限制 |

数据库客户端可以共享，**不代表每个请求的事务客户端或事务状态也可以存在共享字段里**。

你的简历项目中，优先采用：

````text
Guard 验证身份
    ↓
Controller 获取可信用户信息
    ↓
通过参数传给 Service
    ↓
Service 使用局部变量完成业务
````

## 六、Request Scope 能解决这个问题吗？

可以让每个请求使用独立实例：

````ts
@Injectable({ scope: Scope.REQUEST })
export class RequestContextService {}
````

此时：

````text
请求 A → 实例 A
请求 B → 实例 B
````

但不要为了避免串数据，把所有 Service 都改成 Request Scope。

### 它有两个成本

1. **每个请求都要创建相关实例。**
2. **作用域会沿依赖链传播。**

例如：

````text
ResumeController
    ↓
ResumeService
    ↓
RequestContextService（REQUEST）
````

依赖 Request Scope Provider 的服务及其上游消费者，通常也需要按请求实例化。

因此，本来只想增加一个“当前用户服务”，可能影响整条依赖链。

**默认单例 + 参数传递，通常是更简单的起点。**

---

## 七、日志为什么不用每层都传 requestId？

业务身份和日志关联信息，可以采用不同方式。

| 信息 | 常见处理方式 |
|---|---|
| userId，参与权限和业务判断 | 显式传参，边界清楚 |
| requestId，用于日志关联 | 请求上下文自动获取 |

Node.js 的 **AsyncLocalStorage（ALS）** 可以沿异步调用链保存上下文：

````text
请求 A：上下文 requestId = A
  └── Controller → Service → 日志

请求 B：上下文 requestId = B
  └── Controller → Service → 日志
````

它不需要把所有 Service 改成 Request Scope。

`nestjs-pino` 就利用这类机制关联请求日志。现在只需知道：

> **单例服务也可以读取当前请求的上下文，不等于把请求数据放进单例字段。**

ALS 也不是跨所有后台任务永久传播的机制；队列任务等场景需要另行传递关联信息。

---

# 本节记住五句话

1. **依赖注入：声明需要的依赖，由 Nest 创建和提供。**
2. **providers 注册，exports 公开，imports 引入模块能力。**
3. **默认服务实例会被多个请求复用。**
4. **请求专属数据放参数、局部变量或请求上下文，不放共享可变字段。**
5. **Request Scope 按需使用，不是默认最佳选择。**
