# A1：PostgreSQL 序列、自增 ID 与 `setval`

这一节先不修改项目迁移。我们用独立实验搞清楚：

> **自增 ID 是谁生成的？序列为什么会和表里的数据不同步？空表上的 `setval` 为什么会失败？**

学完后，你应该能解释这个问题，并准确预测下一次插入的 ID。

---

## 一、先建立心智模型：表和序列是两个对象

假设有一张简历表：

| id | title |
|---|---|
| 1 | 前端工程师简历 |
| 2 | 全栈工程师简历 |

很多人会自然理解成：

> 插入下一条时，数据库计算 `MAX(id) + 1`，得到 3。

**PostgreSQL 的常见自增机制不是这样工作的。**

它使用一个独立的数据库对象——**序列（Sequence）**——发放编号。

````text
序列：负责发号
    ↓
INSERT：向序列领取编号
    ↓
表：把编号与业务数据一起保存
````

### 前端类比：一个独立的 ID 生成器

可以近似理解为：

````ts
let counter = 0

function nextId() {
  counter += 1
  return counter
}

const rows = []

rows.push({ id: nextId(), title: '前端简历' })
````

这里：

- `counter` 对应序列状态；
- `rows` 对应表中数据。

如果手工写入：

````ts
rows.push({ id: 100, title: '导入的简历' })
````

`counter` 不会自动变成 100。

**数据库中，显式插入 ID 也可能绕过序列，让两者不同步。**

这个类比只帮助理解“两个独立状态”。真正的 PostgreSQL 序列还能处理并发发号，不是普通 JavaScript 变量。

---

## 二、自增、序列、主键：不是同一个概念

先把三个职责分开：

| 概念 | 职责 |
|---|---|
| 序列 | 生成编号 |
| 自增默认值 | 插入未提供 ID 时，调用序列 |
| 主键约束 | 保证 ID 唯一且非空 |

因此：

> **序列负责生成候选值，主键负责检查这个值能不能存进去。**

序列不会每次先查表，保证生成值不存在。序列状态错误时，它仍然可能生成一个已有 ID，随后被主键约束拒绝。

另外：

- 主键不一定自增，也可以使用 UUID。
- 自增编号不一定连续。
- Prisma 的 `autoincrement()` 是模型声明，实际数据库实现应查看迁移 SQL。

## 三、准备一个独立实验

**请在专门的练习数据库执行，不要连接项目库或生产库。**

下面创建一张实验表：

````sql
CREATE TABLE a1_sequence_lab (
  id serial PRIMARY KEY,
  title text NOT NULL
);
````

这里的 `serial` 是 PostgreSQL 的一种便捷写法，大致会安排：

1. 一个整数列；
2. 一个关联序列；
3. 一个调用序列的默认值。

现代 PostgreSQL 也提供 identity 列。本节用 `serial`，方便观察机制，不代表你的项目一定采用相同建表方式。

### 查看实际关联的序列

````sql
SELECT pg_get_serial_sequence('a1_sequence_lab', 'id');
````

默认环境中，结果通常类似：

````text
public.a1_sequence_lab_id_seq
````

**后面的实验假设得到这个名称。如果你的返回值不同，请替换。**

这也是项目排查时的好习惯：查真实关联，而不是猜序列名称。

## 四、实验一：插入时怎样领取编号？

执行：

````sql
INSERT INTO a1_sequence_lab (title)
VALUES ('第一份简历')
RETURNING id, title;
````

结果应当是：

| id | title |
|---|---|
| 1 | 第一份简历 |

再插入一条：

````sql
INSERT INTO a1_sequence_lab (title)
VALUES ('第二份简历')
RETURNING id, title;
````

ID 应当是 2。

### 查看序列状态

````sql
SELECT last_value, is_called
FROM public.a1_sequence_lab_id_seq;
````

此时通常得到：

| last_value | is_called |
|---|---|
| 2 | true |

两个字段是本节重点：

- `last_value`：序列记录的值；
- `is_called`：是否将这个值视为已经调用、已经发放。

在我们这个默认步长为 1 的实验序列中：

````text
last_value = 2
is_called = true
    ↓ 下一次 nextval
返回 3
````

## 五、三个函数，重点掌握两个

| 函数 | 作用 |
|---|---|
| `nextval` | 领取下一号码，并推进序列 |
| `setval` | 设置序列状态 |
| `currval` | 查看当前数据库会话最近从该序列领取的号码 |

### 1. `nextval`：真的会领走一个号码

````sql
SELECT nextval('public.a1_sequence_lab_id_seq');
````

前面已插入两条，因此这里返回 3。

注意：**你虽然没有插入记录，但 3 已经被领取了。**

下一次正常插入通常得到 4，而不是 3。

所以不要为了“查看下一号码”，随意在项目库调用 `nextval`。它不是只读查询。

### 2. `currval`：不是查询表中的最大 ID

````sql
SELECT currval('public.a1_sequence_lab_id_seq');
````

它返回的是**当前会话**最近领取的值。

如果当前会话从未调用该序列的 `nextval`，它会报错。它不代表其他会话领取的最新 ID，也不是 `MAX(id)`。

当前阶段知道这个边界即可。

---

## 六、`setval` 的关键：第三个参数

### 情况 A：把 10 当成已经发放

````sql
SELECT setval('public.a1_sequence_lab_id_seq', 10, true);

SELECT nextval('public.a1_sequence_lab_id_seq');
````

返回：

````text
11
````

含义：

````text
状态设为 10
10 已经发放
下次继续发 11
````

### 情况 B：把 10 当成下一次要发放的值

````sql
SELECT setval('public.a1_sequence_lab_id_seq', 10, false);

SELECT nextval('public.a1_sequence_lab_id_seq');
````

返回：

````text
10
````

含义：

````text
状态设为 10
10 尚未发放
下次直接发 10
````

### 省略第三个参数呢？

````sql
SELECT setval('public.a1_sequence_lab_id_seq', 10);
````

等价于第三个参数使用 `true`。下一次通常返回 11。

**记忆方式：**

> `true`：这个号码用过了。  
> `false`：这个号码留给下一次。

以上预测针对本实验的默认步长。序列可以配置其他步长，不能在所有项目里都机械地理解成“加一”。

## 七、为什么空表上 `setval(..., 0)` 会失败？

先清空练习表，并重置序列：

````sql
TRUNCATE TABLE a1_sequence_lab RESTART IDENTITY;
````

**这会删除实验表里的全部数据。只用于练习环境。**

看这段常见写法：

````sql
SELECT setval(
  'public.a1_sequence_lab_id_seq',
  (SELECT COALESCE(MAX(id), 0) FROM a1_sequence_lab)
);
````

逐层展开：

### 第一步：空表上的 `MAX(id)`

结果为 `NULL`，不是 0。

### 第二步：`COALESCE`

`COALESCE` 返回参数中第一个非 `NULL` 的值：

````sql
COALESCE(NULL, 0)
````

因此得到 0。

### 第三步：设置序列

最终变成：

````sql
SELECT setval('public.a1_sequence_lab_id_seq', 0);
````

但这个普通正向序列的默认最小值是 1，所以会报“超出序列边界”之类的错误。

**不是 PostgreSQL 不能生成零，而是这个序列的配置不允许零。**

---

## 八、空表与非空表怎样分别处理？

我们希望：

| 表状态 | 下一次插入的 ID |
|---|---|
| 空表 | 1 |
| 最大 ID 是 8 | 9 |

针对**正整数 ID、默认步长 1**的场景，可以这样写：

````sql
SELECT setval(
  'public.a1_sequence_lab_id_seq',
  COALESCE(MAX(id), 1),
  MAX(id) IS NOT NULL
)
FROM a1_sequence_lab;
````

### 空表

````text
MAX(id) = NULL
设置值 = 1
is_called = false
下一次返回 1
````

### 非空表，最大 ID 为 8

````text
MAX(id) = 8
设置值 = 8
is_called = true
下一次返回 9
````

**这里真正重要的不是背 SQL，而是同时设置两个状态：值是多少，这个值是否已经发放。**

### 使用边界

这不是可以随时在生产执行的“通用修复按钮”。

- 如果允许零或负数 ID，需要重新检查边界。
- 如果序列步长或配置不同，需要调整方案。
- 如果还有并发写入，读取 `MAX(id)` 与修改序列之间可能发生竞争。
- 序列当前值可能已经高于表中最大值，直接回拨未必合理。

它更适合**受控迁移、数据导入完成后、没有竞争写入的场景**。

## 九、实验二：手动导入 ID，为什么会撞主键？

重置练习表：

````sql
TRUNCATE TABLE a1_sequence_lab RESTART IDENTITY;
````

显式插入：

````sql
INSERT INTO a1_sequence_lab (id, title)
VALUES (1, '手动导入的简历');
````

这次提供了 ID，没有使用默认发号机制。

再执行：

````sql
INSERT INTO a1_sequence_lab (title)
VALUES ('正常创建的简历');
````

序列尝试发出 1，但表里已经存在 1，于是主键冲突。

完整链路是：

````text
手动插入 id = 1
    ↓
序列仍准备发 1
    ↓
正常插入领取 1
    ↓
主键约束拒绝重复值
````

这说明：

> **“数据成功导入”与“自增状态正确”是两项不同的验收。**

在隔离环境中调整序列后，再插入验证，才算闭环。

## 十、实验三：事务回滚，为什么 ID 没退回？

再次重置：

````sql
TRUNCATE TABLE a1_sequence_lab RESTART IDENTITY;
````

执行：

````sql
BEGIN;

INSERT INTO a1_sequence_lab (title)
VALUES ('最终会回滚的简历')
RETURNING id;

ROLLBACK;
````

插入时领到了 ID 1，但记录被回滚了。

再插入：

````sql
INSERT INTO a1_sequence_lab (title)
VALUES ('真正保存的简历')
RETURNING id;
````

通常得到 ID 2。

### 为什么？

PostgreSQL 的 `nextval` 领取号码后，**不会因为调用它的事务回滚而归还号码**。

这有利于并发发号，也意味着：

- 回滚可能产生空号；
- 插入失败可能产生空号；
- 删除记录会留下空号。

**ID 不连续不是数据丢失的充分证据，也不是需要“修复”的错误。**

另外，`setval` 的修改同样不会通过普通事务回滚恢复。不要觉得：

> “我包一个 BEGIN，试错以后 ROLLBACK 就安全了。”

序列实验仍然必须使用隔离数据库。
