## 一、先校准原反馈中的三个点

避免我们带着不准确的前提继续学。

### 1. 新迁移无法修复“旧迁移导致空库重放失败”

如果迁移顺序是：

````text
迁移 A：setval(..., 0) → 执行失败
迁移 B：修正序列
````

空库会在 A 停下，**根本执行不到 B**。

所以这件事不能简单按“新增修正迁移”处理。需要调查哪些环境已经应用旧迁移，再决定是否协调修订历史、重建可丢弃的开发库，或采用重新基线化等方案。

**“已部署迁移尽量不修改”是重要纪律，但不是绕过实际执行顺序的万能规则。**

### 2. 模块边界、聚合边界、事务边界不必完全相等

三者分别属于：

- **模块边界**：代码组织与依赖管理。
- **聚合边界**：业务一致性的建模。
- **事务边界**：一次原子数据库操作的范围。

它们应该协调，但不能机械画等号。

### 3. 乐观并发不是“数据库不加锁”

条件更新依然会使用数据库内部的锁机制。

准确说是：**应用使用版本条件检测冲突，而不是先显式锁住记录再完成业务操作。**

这些问题都会纳入下面的学习清单。

# 三、详细学习清单

## 阶段 A：先让数据库迁移可靠

### A1. 序列、自增 ID 与 `setval` ⭐ 第一项

**项目切入点：历史迁移空库重放失败。**

学习清单：

- [ ] 自增 ID 的值从哪里来。
- [ ] 序列与表中 `MAX(id)` 为什么是两个独立状态。
- [ ] `nextval`、`setval`、`is_called` 的含义。
- [ ] 空表和非空表如何安全初始化序列。
- [ ] 为什么删除记录、事务回滚后 ID 可能不连续。
- [ ] 手工导入 ID 后，为什么可能出现主键冲突。
- [ ] 如何查找列实际关联的序列，避免硬编码猜名字。

**实操：**

在隔离数据库中验证：

````text
空表 → 调整序列 → 插入第一条记录
有数据 → 调整序列 → 插入下一条记录
事务回滚 → 再插入 → 观察 ID
````

**验收：**

能解释：

> 为什么 `setval(seq, 1, false)` 的下一次返回 1，而 `setval(seq, 1, true)` 通常返回 2？

**预计：2–3 小时。**

---

### A2. 迁移排查与历史修复决策

**项目切入点：旧迁移已经应用，但新环境无法重放。**

学习清单：

- [ ] Schema、迁移文件、真实数据库的职责。
- [ ] `_prisma_migrations` 与 checksum。
- [ ] 五个迁移命令的语义边界。
- [ ] 空库重放与已有库升级，为什么必须分别验证。
- [ ] 新迁移能修复什么、不能修复什么。
- [ ] 什么时候可以重建开发库，什么时候不能。
- [ ] `resolve` 为什么不会执行或撤销 SQL。
- [ ] Prisma diff 对 CHECK 等数据库特性的检测边界。

**实操：**

先做调查表：

| 环境 | 是否已应用问题迁移 | 数据能否丢弃 | 当前结构 |
|---|---|---|---|
| 本地开发 | 待确认 | 待确认 | 待确认 |
| 其他开发者 | 待确认 | 待确认 | 待确认 |
| 测试/生产 | 待确认 | 通常不能随意丢弃 | 待确认 |

然后写修复方案，而不是先改 SQL。

**验收：**

- 空库能重放完整历史。
- 已有环境有明确处理路径。
- 关键约束和外键经数据库原生信息验证。
- 修复决策与风险被记录。

**预计：3–5 小时，不含环境协调。**

# 四、每一项我们怎么学？

固定采用五步，不直接跳到“给一份代码”：

| 步骤 | 内容 |
|---|---|
| ① 场景 | 当前项目为什么需要它 |
| ② 概念 | 前端类比 + 后端机制 |
| ③ 实验 | 最小代码或 SQL，观察真实行为 |
| ④ 项目应用 | 对照你的实现和边界 |
| ⑤ 验收 | 自测题、测试结果、笔记与导图 |

建议笔记结构：

````text
docs/learning/backend/
├── checklist.md
├── A1-sequences.md
├── A2-migrations.md
├── B1-di-scopes.md
└── ...
````

每篇只要求记录：

- 我原来怎么理解；
- 正确机制是什么；
- 实验结果；
- 项目中如何使用；
- 还有哪些问题没解决。

## 五、现在就从哪里开始？

**第一项：A1「PostgreSQL 序列、自增 ID 与 setval」。**

但我们分成两步：

1. **先做独立实验，理解机制。**
2. **再调查项目旧迁移，决定修复策略。**

这样不会一边对序列还不熟，一边直接修改迁移历史。

你的学习顺序可以直接记为：

> **A1 → A2 → B1 → B2 → C1 → C2 → D1 → D2 → E1 → E2 → F1 → F2 → G1**

实际开发遇到上传、删除或日志问题时，我们允许提前学习对应项；完成后回到主线。**这份清单的作用是保证知识补齐，不是限制项目推进。**
