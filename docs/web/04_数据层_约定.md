# 数据层约定（Pinia Colada + `$api`）

> 定义 `apps/admin` / `apps/web` 的数据获取约定：请求层、缓存层与错误处理的边界。
> 2026-10-07 起数据层统一用 `@pinia/colada`；模板遗留的 **alova 上传实例已于 2026-10-08 完成迁移**（原生 XHR + colada mutation）。

## 1. 分层与职责

```text
组件 / 页面
  └─ composables/useXxxQuery.ts   ← 组合 colada：key、query/mutation、失效策略
       └─ apis/xxx.ts             ← 纯请求函数：调 $api（收口在函数内），不持有状态
            └─ plugins/api.ts（在 packages/ui；注入 $api：鉴权头 / 解包 / 公共错误处理）
```

- **组件不直接发请求**：页面只用 composable，拿 `data` / `status` / `error`。
- **`apis/` 只管取数**：不缓存、不 toast、不管 loading；**它不认识 colada**（只调 `$api`）
  —— 所以命令式调用、上传、非缓存场景都能直接复用它。
- **`composables/` 不认识 `$fetch` 细节**：只调 `apis/` 的纯函数，把结果交给 colada。
  两者唯一的接触面就是"把纯函数传进 `useQuery` / `useMutation`"，不是互相 import 实现。
- **请求层只管协议**：解包统一响应，其余抛归一化错误（策略见 [05*请求错误处理*设计.md](05_请求错误处理_设计.md)）。
- **缓存策略只在 composable**：`staleTime`、失效、乐观更新都在这一层。

> **为什么请求层与缓存层不合并成一个封装**：两者换实现的理由不同（换 http 客户端 / 换缓存库），
> 混在一起会互相绑死；而 `useApiQuery(url, params)` 那类"URL 驱动"的通用封装还会让 key 从 URL 推导、
> 失效范围说不清、业务语义丢失、且无法分层测试。**保持区分**，用 §4 的方式收口。

## 2. 响应契约

唯一来源是 `packages/common`（`~/types/api` 只做类型转发）。**成功与失败同形状，靠 `code` 区分**：

```ts
{ code: number, data: T | null, message: string, timestamp: string, traceId?: string, errorCode?: string }
```

- 用 `isApiSuccess(payload)` 判断成功（**不要**写死 `code === 200`）→ `$api` 解包 `data` 返回；
- 其余 → 抛归一化后的错误（带 `code` / `errorCode` / `traceId` / `path`），并触发 `api:error[:code]` hook；
- 前端**按 `errorCode` 分支，不解析 `message`**；`traceId` 是排查入口（报给后端可定位这次请求）。

> 错误的归一化、默认策略（**公共错误默认自动处理**：401 清会话引导登录，403/404/5xx/网络中断统一提示）
> 与按接口跳过（`{ silent: true }`）见 [05_请求错误处理_设计.md](05_请求错误处理_设计.md)。

## 3. query key 规范

集中在 `app/lib/query-keys.ts`，结构为 `[scope, ...segments]`：

```ts
queryKeys.resume.draft() // ['resume', 'draft']
queryKeys.resume.published('zh') // ['resume', 'published', 'zh']
```

- `scope` 与业务域同名；域内细分放 segments，便于按前缀批量失效。
- 不在组件里手写 key 数组，避免失效范围对不上。

## 4. 收口与失效：`defineQuery` / `defineMutation`

### 4.1 query：`defineQuery` 作"域入口"

**为什么要收口**：若每个调用点各写 `useQuery({ key, query, staleTime })`，样板会重复，
且容易出现"两处 key 写得不一样"。`defineQuery` 让工厂**只建一次**（与 store 同语义），
任意页面调用都复用同一实例 —— 调用点只关心数据，不关心 key 与缓存策略。

⚠️ **用在哪一类查询上**（Owner 定的分工）：**频繁但不常变**的才进 colada 缓存 —— 简历查看、用户信息、
授权信息。**"每次都要最新"的不该进来**（如 health 心跳：已改用 `useAsyncData`，见 `apis/health.ts` 的注释）。

将来的写法（仍然只在这里建一次，调用点不关心 key 与缓存策略）：

```ts
// composables/useResumeQuery.ts —— 这个域的**唯一读取入口**
export const useResumeQuery = defineQuery(() => {
  const { state, ...rest } = useQuery({
    key: queryKeys.resume(),
    query: fetchResume,
    staleTime: 30_000,
  })

  return { ...rest, data: computed(() => unref(state)?.data ?? null) }
})
```

```ts
// 调用点
const { data, isLoading } = useResumeQuery()
```

一次性取数（心跳这类，不进缓存）则直接：

```ts
const { data: health, refresh } = await useAsyncData('health', fetchHealth)
```

⚠️ `defineQuery` 返回的是**函数**（要调用才拿到实例），别当成对象直接用。

### 4.2 mutation：`defineMutation` + 把"失效谁"写进定义

失效的**归属**是 mutation 自己的定义，不是每个调用点 —— 调用方不需要记得刷新：

```ts
export const usePublishResume = defineMutation(() => {
  const cache = useQueryCache()
  const { mutateAsync, ...rest } = useMutation({
    mutation: publishResume,
    onSuccess: () => cache.invalidateQueries({ key: queryKeys.resume.published() }),
  })

  return { ...rest, publish: mutateAsync }
})
```

- 只有在确实要服务端最新值时才 `refresh()`，不用它替代失效策略；
- key 一律来自 `lib/query-keys.ts`（§3），不在调用点手写数组。

### 4.3 错误在 colada 层怎么落

- **公共错误**：请求层已默认提示（401 清会话引导登录，403/404/5xx/网络中断统一提示），调用点**不需要**每次自己弹；
- **mutation**：要额外处理时在 `onError` 里做（如字段级报错落到表单，而不是飘全局提示）；
- **query**：**没有** per-query `onError` → 用返回的 `error` 渲染 **inline 错误态**；
- 两种情况拿到的都是 §2 的归一化错误（`code` / `errorCode` / `traceId` 齐全）。

## 5. 上传 / 进度 / 取消（已落地：原生 XHR + colada mutation）

- **为什么不用 `$api` / fetch**：colada 与 `$api` 都基于 fetch，**拿不到上传进度**、也无法取消一个已发出的请求体；
  XHR 的 `upload.onprogress` + `abort()` 才能同时满足「进度条」与「取消」。
- **分层**：
  - `apis/files.ts` 的 `uploadFiles` —— 纯请求函数（原生 XHR、进度回调、`AbortSignal`、按统一响应契约解包（`isApiSuccess`）、取消抛 `AbortError`）；
  - `composables/useFileUploader.ts` —— colada `useMutation` 管状态（`uploading` / `progress` / `uploaded` / `error`），并保留校验与 `abort()`；
  - `composables/useUploadFile.ts` —— 遗留薄包装（仍可用，新代码请用 `useFileUploader`）。
- **约定**：
  - 进度用 `FileUploadProgress`（`{ loaded, total, percent }`）暴露，不使用 `ref<number>` 这种丢信息的形状；
  - 上传请求**不可复用**进行中的请求（否则进度 / 取消会对错文件）——`useFileUploader` 每次上传前先 `abort()` 上一次；
  - 用户取消不算失败：`isAbortError` 统一识别（`packages/common/src/api/request.ts`）。

## 7. 已知边界

- 鉴权：token 存 cookie（`my-resume.token`），请求层注入 `Authorization: Bearer`；登录 mutation 随 auth 模块落地。
