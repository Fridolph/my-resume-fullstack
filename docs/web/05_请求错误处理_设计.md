## 1. 现状与缺口

**已具备**（不需要重做）：

```text
组件/页面
  └─ composables/useXxxQuery.ts   colada：key / staleTime / 失效策略
       └─ apis/xxx.ts             纯请求函数（只调 $request）
            └─ plugins/httpRequest.ts   装配 $request：baseURL / 鉴权头 / 解包 / 抛 ApiError

上传是**独立一条路**（要进度 + 取消，fetch 做不到）：
  apis/files.ts（原生 XHR：onprogress + abort）→ useFileUploader（colada mutation）
```

> ⚠️ 曾经用过的 **alova 已在 DAO-005 移除**；现在常规请求是 `$fetch.create`，上传是原生 XHR。

**缺口（全部集中在"错误抛出去之后"）**：

| #   | 缺口                  | 证据                                                                                                                           |
| --- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 1   | 没有统一的错误提示    | `applyApiErrorHooks` 只 `callHook('api:error:401')`，而**全仓只有 demos 页监听** → 真实业务里错误只在 console 或直接抛给调用方 |
| 2   | 无法按接口定制        | 没有"这个请求别打扰我"的声明方式（心跳、预取、探测类）                                                                         |
| 3   | 401 无人处理          | 没有人清会话 / 引导重新登录                                                                                                    |
| 4   | 没按 `errorCode` 分支 | 新契约要求"按 `errorCode` 分支、不解析 `message`"，现实现只按数值 `code`                                                       |
| 5   | `traceId` 被丢弃      | 后端成功/失败都带 `traceId`（排查入口），前端没用                                                                              |
| 6   | 文档过期              | `docs/web/04_数据层_约定.md` §2 仍写旧契约 `{ success: true, … }`                                                                           |

## 2. 分层：装配留 plugin，策略进 utils

```text
apis/xxx.ts                     纯请求（$request）
plugins/httpRequest.ts          装配：baseURL / 鉴权 / 解包 / 抛归一化错误 / 触发 hook
utils/apiError.ts               ★策略：归一化 + code/errorCode → 文案与动作（纯函数，可单测）
composables/useApiErrorToast.ts ★调用方显式要提示时才用
```

**为什么 `$request` 不搬进 `utils/$request.ts`**：它的创建必须
`provide` 到 Nuxt 上下文，并读 `runtimeConfig` 与 `useCookie` —— 搬进纯 utils 后还得把这些
手动穿进去，等于绕一圈。**"装配"与"策略"是两件事**，分开后策略可脱离 Nuxt 测试、可被两端复用。

## 3. 归一化契约

所有错误（业务错误 / HTTP 错误 / 网络中断 / 超时）都归一成同一个形状：

```ts
export interface NormalizedApiError {
  /** 业务码（`packages/common` 的 `code`；网络失败时为 0） */
  code: number
  /** 细粒度错误码（如 `AUTH.Token:expired`）—— **按它分支，不解析 message** */
  errorCode?: string
  /** 后端原始 message（排查用，不直接展示给用户） */
  message: string
  /** 链路追踪：报给后端能在日志里定位这一次请求 */
  traceId?: string
  /** 后端给的请求路径（失败体里有） */
  path?: string
  /** 连响应都没拿到（断网 / 超时 / CORS） */
  isNetworkError: boolean
}
```

配套纯函数（`utils/apiError.ts`）：

```ts
isNormalizedApiError(err): err is NormalizedApiError
normalizeApiError(err): NormalizedApiError           // 任意 err → 统一形状
resolveApiErrorMessage(err): string                  // code / errorCode → 用户可读文案
resolveApiErrorAction(err): 'none' | 'redirect-login' // 需要做的副作用
```

## 4. 策略：**默认静默**（Owner 选定）

默认行为只有两件事：**归一化** + **触发 hook**。**不弹任何提示**。

```ts
/** 一处配置：需要自动提示/自动处理时改这里，不要在组件里散写 */
export const API_ERROR_POLICY: Record<number, { notify: boolean; action: ApiErrorAction }> = {
  400: { notify: false, action: 'none' },
  401: { notify: false, action: 'none' }, // ← 建议接后端后改成 { notify: true, action: 'redirect-login' }
  403: { notify: false, action: 'none' },
  404: { notify: false, action: 'none' },
  409: { notify: false, action: 'none' },
  500: { notify: false, action: 'none' },
  0: { notify: false, action: 'none' }, // 网络失败
}
```

**文案走映射表，不解析 `message`**（对齐 `packages/common` 的约定）：

| 来源                | 用法                                                         |
| ------------------- | ------------------------------------------------------------ |
| `errorCode`（优先） | 精确原因，如 `AUTH.Token:expired` → "登录已过期，请重新登录" |
| `code`（兜底）      | 粗粒度类目，401/403/404/5xx 各自的默认文案                   |
| `message`（最后）   | 仅在上两者都没命中时兜底展示（不用于分支判断）               |

**按接口定制**（类型安全，不用 `as any`）：

```ts
await $request('/health', { silent: true }) // 该请求**连 hook 都不触发**
await $request('/resume/publish', { errorPolicy: 'manual' }) // 完全不接管，调用方自己 try/catch
```

**调用方想提示时**（显式，而非自动）：

```ts
const { show } = useApiErrorToast()

try {
  await publish()
} catch (err) {
  show(err) // 按策略表给出文案；带上 traceId（便于用户报错时提供）
}
```

## 5. 为什么"默认静默"（取舍）

自动弹提示的三个反例，正好是这个项目会遇到的：

1. **表单校验错误要落到字段上**，不是飘一个 toast —— 自动弹会重复提示；
2. **后台预取 / 轮询失败**（如心跳、SSR 取数降级）不该打扰用户；
3. "什么错都弹一下"会让**真正的错误失去重要性**，用户对 toast 逐渐免疫。

但**静默 ≠ 不管**：归一化统一了错误形状、hook 保留了接入点、`traceId` 随时可拿 ——
需要提示或跳转时，改 §4 那张表的一行即可，不用动调用点。

> ⚠️ **唯一建议例外**：接后端 auth 后把 **401 打开**（`notify + redirect-login`）。
> 不处理它，用户会一直停在"请求失败"的页面上而不知道要重新登录。

## 7. 验收

1. 400 / 401 / 403 / 404 / 409 / 5xx / 网络中断：**归一化字段齐全**（含 `traceId`、`errorCode`）；
2. **默认不弹任何提示**（跑一遍失败请求，页面上除调用方自己处理外无 toast）；
3. `{ silent: true }` 的请求**不触发 hook**；
4. `useApiErrorToast().show(err)` 文案正确（按 `errorCode` 优先命中）；
5. 把 401 策略打开后：清会话 + 引导登录（收尾项，可留到接后端时验）。
