# 请求错误处理设计（`$api` / 归一化 / 策略）

> 状态：**已实施（2026-10-09）**，两端同构；演练场见 `/demos/request`（admin）
> 关联：[04*数据层*约定.md](04_数据层_约定.md)（数据层分层）、`packages/common`（响应契约）、`docs/server/01_API_约定.md`（后端视角）
> 决策记录：
> 1. **装配留 plugin、策略进纯函数**（策略可脱离 Nuxt 测试、两端复用）；
> 2. **公共错误默认自动处理**（Owner 2026-10-09 修订，取代早先的"默认静默"）：401 → 清 token + 引导登录；
>    403 / 404 / 5xx / 网络中断 → 统一提示（带 traceId）；**400 / 409 不自动提示**（表单与业务冲突就地提示更合适）；
>    按接口跳过用 `{ silent: true }`；
> 3. 请求层**唯一一处**位于 `packages/ui/app/plugins/api.ts`，注入 `$api`（两端零代码）—— 见 §4 末尾说明
>    为什么不是"替换全局 `$fetch`"。

## 1. 现状与缺口（**实施前**的历史记录，保留以便回溯）

**当时已具备**：

```text
组件/页面
  └─ composables/useXxxQuery.ts   colada：key / staleTime / 失效策略
       └─ apis/xxx.ts             纯请求函数（只调 $request）
            └─ plugins/httpRequest.ts   装配 $request：baseURL / 鉴权头 / 解包 / 抛 ApiError

上传是**独立一条路**（要进度 + 取消，fetch 做不到）：
  apis/files.ts（原生 XHR：onprogress + abort）→ useFileUploader（colada mutation）
```

**缺口（全部集中在"错误抛出去之后"）**：

| #   | 缺口                  | 证据                                                                                                                           |
| --- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 1   | 没有统一的错误提示    | `applyApiErrorHooks` 只 `callHook('api:error:401')`，而**全仓只有 demos 页监听** → 真实业务里错误只在 console 或直接抛给调用方 |

| 4   | 没按 `errorCode` 分支 | 新契约要求"按 `errorCode` 分支、不解析 `message`"，现实现只按数值 `code`                                                       |
| 5   | `traceId` 被丢弃      | 后端成功/失败都带 `traceId`（排查入口），前端没用                                                                              |
| 6   | 文档过期              | `docs/web/04_数据层_约定.md` §2 仍写旧契约 `{ success: true, … }`                                                              |

## 2. 分层：装配留 plugin，策略进 utils

```text
packages/common/src/api/*        纯逻辑：契约类型 / 常量 / 归一化 / 策略 / 文案 / 请求头（两端复用、可单测）
packages/ui/app/plugins/api.ts    ★唯一的请求层：注入 `$api`（鉴权头 / 解包 data / 公共错误默认处理）
apps/*/app/apis/*.ts              ★唯一的取数入口：函数内部收口 `$api`（实例细节不外泄）
页面 / composable                 useAsyncData（一次性）或 useQuery（缓存型）→ 调 apis/* 的函数
```

**为什么 `$api` 不搬进 `utils/$api.ts`**：它的创建必须
`provide` 到 Nuxt 上下文，并读 `runtimeConfig` 与 `useCookie` —— 搬进纯 utils 后还得把这些
手动穿进去，等于绕一圈。**"装配"与"策略"是两件事**，分开后策略可脱离 Nuxt 测试、可被两端复用。

## 3. 归一化契约

所有错误（业务错误 / HTTP 错误 / 网络中断 / 超时）都归一成同一个形状：

```ts
export interface NormalizedApiError {
  /** 业务码（`packages/common` 的 `code`；网络失败时为 0） */
  code: number
  /** 细粒度错误码（如 `AUTH.Token:expired`）—— **按它分支，不解析 message** */
  errorCode?: string
  /** 后端原始 message（排查用，不直接展示给用户） */
  message: string
  /** 链路追踪：报给后端能在日志里定位这一次请求 */
  traceId?: string
  /** 后端给的请求路径（失败体里有） */
  path?: string
  /** 连响应都没拿到（断网 / 超时 / CORS） */
  isNetworkError: boolean
}
```

配套纯函数（`packages/common/src/api/error.ts`，框架无关、可单测）：

```ts
isNormalizedApiError(err): err is NormalizedApiError
toNormalizedApiError(payload, httpStatus?): NormalizedApiError  // 响应体 → 统一形状（请求层用）
normalizeApiError(err): NormalizedApiError                      // 任意 err → 统一形状
resolveApiErrorPolicy(err): ApiErrorPolicy                      // 该不该提示 / 要不要跳登录
resolveApiErrorMessage(err): string                             // errorCode 优先 → code → message
resolveApiErrorDetail(err): string                              // 带 traceId 的完整文案
buildApiErrorHookNames(err): string[]                           // ['api:error', 'api:error:404', ...]
```

## 4. 策略：**公共错误默认自动处理**（Owner 2026-10-09 修订）

默认行为 = **归一化 + 触发 hook + 按表处理**。这条表**两端完全一致**，所以放在共享包里
（`packages/common/src/api/constants.ts`）：

```ts
/** 一处配置，不要在各端各写一份 */
export const API_ERROR_POLICY: Record<number, ApiErrorPolicy> = {
  [NETWORK_ERROR_CODE]: { notify: true, action: 'none' }, // 网络中断
  400: { notify: false, action: 'none' }, // 参数错误 → 留给调用方
  401: { notify: true, action: 'redirect-login' }, // 清 token + 引导登录
  403: { notify: true, action: 'none' },
  404: { notify: true, action: 'none' },
  409: { notify: false, action: 'none' }, // 业务冲突 → 就地提示更合适
  500: { notify: true, action: 'none' },
}
```

**文案走映射表，不解析 `message`**（对齐 `packages/common` 的约定）：

| 来源                | 用法                                                         |
| ------------------- | ------------------------------------------------------------ |
| `errorCode`（优先） | 精确原因，如 `AUTH.Token:expired` → "登录已过期，请重新登录" |
| `code`（兜底）      | 粗粒度类目，401/403/404/5xx 各自的默认文案                   |
| `message`（最后）   | 仅在上两者都没命中时兜底展示（不用于分支判断）               |

**按接口定制**（类型安全，不用 `as any`）：

```ts
await $api('/health', { silent: true }) // 本次**不提示、也不触发 hook**
await $api('/resume/publish', { errorPolicy: 'manual' }) // 同上，语义上强调"调用方自己管"
```

**401 之后去哪登录**：请求层清掉 token 并触发 `api:unauthorized`，跳转目标由各端用
`runtimeConfig.public.loginPath` 声明（admin = `/login`；web 不配 → 只提示，宿主自行接管）。

**为什么不是"替换全局 `$fetch`"**：Nuxt 把自动导入的 `$fetch` 生成为 `#build/fetch.mjs` 的
**模块常量**（`export const $fetch = globalThis.$fetch`，求值时快照一次），而 Nuxt 内部早于任何插件
import 它 —— 插件里替换 `globalThis.$fetch` 对页面里的 `$fetch` 无效（实测：页面 `$fetch` 仍打默认
baseURL）。Nuxt 官方的自定义入口就是 `provide`，故收口为 `$api`。

## 5. 取舍：哪些自动、哪些留给调用方

表里 `notify: false` 的两行（400 / 409）不是遗漏，而是"就地提示更合适"：

1. **表单校验错误要落到字段上**，不是飘一个 toast —— 再弹一次是重复信息；
2. **业务冲突**（409）要让用户看到当前状态再决定下一步；
3. 反过来，"什么错都弹一下"会让**真正的错误失去重要性**，用户对 toast 逐渐免疫。

而**调用点表达不清楚的**（鉴权失效、权限不足、资源不存在、服务端异常、网络中断）统一交给请求层 ——
这正是"两端同一套"的价值：新页面不必重新决定这些事，也不会有人漏掉。

> 之前一度定为"默认静默"，实践证明会让 401 变成"页面卡住但没人知道要重新登录"，故修订为现在的策略。

**⚠️ 实测抓到的坑（重要，类型检查发现不了）**：

> **在 ofetch 的 `onResponse` 里 `throw`，不会再走 `onResponseError`。**

所以"只在 `onResponseError` 里触发 hook"会漏掉**业务失败**那一大类（HTTP 200/404 但业务码非 2xx）——
也就是最常发生的一类错误。修法：抽出唯一的 `emitApiError()` 出口，`onResponse` 与 `onResponseError` **都**调它。
（这个问题是演练场第 ③ 项验证抓出来的。）

**另一处顺带修正**：`applyApiErrorHooks` 原计划放 `utils/apiError.ts`，但它的签名与 `NuxtApp` 类型不兼容
——于是把 hook 触发移回 plugin（那里本来就是 Nuxt 环境），`utils/apiError.ts` 因此保持"纯函数"，
分工反而更干净。

**同日二次整理（消除重复 + 消除多余抽象）**

第一版把它做成了 `createRequestClient()` 工厂 + 各端 `plugins/httpRequest.ts` 装配，还额外造了一个
`$request` 自定义实例 —— 层数多且没有换来简化。整理后：

| 层           | 位置                             | 内容                                                                                                                                                                                               |
| ------------ | -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **纯逻辑**   | `packages/common/src/api/`       | `constants`（`API_CODE` / `TOKEN_COOKIE_KEY` / `NETWORK_ERROR_CODE` / 策略表 / 文案表）、`types`、`response`、`error`（归一化 + 策略 + 文案）、`request`（`buildRequestHeaders` / `isAbortError`） |
| **请求层**   | `packages/ui/app/plugins/api.ts` | 只有一处：注入 `$api`（`$fetch.create` + 拦截 + 公共错误处理）。**两端零代码**，layer 的 plugins 由 Nuxt 自动加载                                                                                  |
| **取数入口** | `apps/*/app/apis/*.ts`           | 每个域一个函数，内部收口 `$api`；页面完全不感知实例                                                                                                                                                |
| **类型扩展** | `apps/*/app/types/api.d.ts`      | `$fetch` 的 `silent` / `errorPolicy`                                                                                                                                                               |

一并删掉：`utils/requestContext.ts`（`resolveRequestContext` / `getApiErrorData` 零使用；
`createApiError` / `getApiErrorMessage` / `applyApiErrorHooks` 已被取代）、admin 的 `utils/request.ts`
（`isAbortError` 移入 common）、`useApiErrorToast`（错误默认自动处理，不再需要调用方手动 show）、
`useHealthQuery`（心跳不该进缓存）。

> ⚠️ **为什么不是"替换全局 `$fetch`"**（最初想这么做，实测走不通）：Nuxt 把自动导入的 `$fetch` 生成为
> `#build/fetch.mjs` 的**模块常量**
>
> ```js
> if (!globalThis.$fetch) globalThis.$fetch = _$fetch.create({ baseURL: baseURL() })
> export const $fetch = globalThis.$fetch // ← 求值时快照一次
> ```
>
> 而 Nuxt 内部**早于任何插件**就 import 了它 —— 所以插件里 `globalThis.$fetch = client` 对页面里的
> `$fetch` 无效（实测：页面 `$fetch` 仍打默认 baseURL，请求 404）。**Nuxt 官方的自定义入口就是 `provide`**，
> 因此收口为 `$api`。
>
> ⚠️ `packages/ui` 必须显式声明 `"@template/common": "workspace:*"` —— 否则 TS 解析不到，会连带报出一堆无关错误。
>
> 重构后**行为零回归**：11 项真浏览器验证全部通过。

## 7. 验收

1. 400 / 401 / 403 / 404 / 409 / 5xx / 网络中断：**归一化字段齐全**（含 `traceId`、`errorCode`）；
2. **默认不弹任何提示**（跑一遍失败请求，页面上除调用方自己处理外无 toast）；
3. `{ silent: true }` 的请求**不触发 hook**；
4. `useApiErrorToast().show(err)` 文案正确（按 `errorCode` 优先命中）；
5. 把 401 策略打开后：清会话 + 引导登录（收尾项，可留到接后端时验）。

## 8. 不做 / 待定

- **不做**自动重试与 token 静默刷新 —— 与后端 auth（P2）一起设计；
- **不做**全局 loading —— colada 已有 `status`，页面自己用；
- **待定**：admin 是否直接用同一份 `apiError`（P1 两端统一时定；现在两端各有一份 `requestContext.ts`，是"第三次出现再抽包"的既有约定）。
